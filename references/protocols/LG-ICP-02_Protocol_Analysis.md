## 2. CRC 분석

### 2.1 CRC 알고리즘

- **CRC-16/XMODEM** (poly=0x1021, init=0x0000, Big-Endian)
- 계산 범위: **전체 프레임** (Sync `0x56`부터 CRC 직전까지)
- **요청(valid)과 응답(invalid) 모두 동일한 CRC 알고리즘** 사용

### 2.2 "invalid" 표시 원인

```
lgcp-valid.jsonl:   CRC 전부 PASS (1,135/1,135 = 100%)
lgcp-invalid.jsonl: CRC 대부분 PASS (4,174/4,180 = 99.9%)
```

"invalid"로 분류된 이유는 CRC 오류가 아니라, **파서가 요청 프레임(plen=26) 기준으로만 CRC를 검증**했기 때문으로 추정됩니다. 응답 프레임은 plen이 다양(39~49바이트)하여 파서의 CRC 계산 범위가 맞지 않았을 가능성이 높습니다.

실제 CRC 불일치 6건은 모두 `cmd=0x0444` 또는 파싱 오류 프레임이며, 이는 프레임 경계 식별 오류(연속된 프레임이 하나로 합쳐짐)로 인한 것입니다.

## 3. 프레임 구조

```
56 [LEN] 04 [DA 4B] 04 [SA 4B] [CMD 2B] [SEQ0] [PLEN] [PAYLOAD] [SEQ1] [CRC16]
```

| 필드 | 크기 | 설명 |
|------|------|------|
| Sync | 1B | `0x56` 고정 |
| Length | 1B | 프레임 전체 길이 |
| DA prefix | 1B | `0x04` (주소 타입) |
| DA | 4B | 목적지 주소 |
| SA prefix | 1B | `0x04` (주소 타입) |
| SA | 4B | 출발지 주소 |
| CMD | 2B | 명령어 |
| SEQ0 | 1B | 시퀀스 번호 (송신측) |
| PLEN | 1B | 페이로드 길이 |
| Payload | PLEN B | 데이터 |
| SEQ1 | 1B | 시퀀스 번호 (응답측) |
| CRC16 | 2B | CRC-16/XMODEM (Big-Endian) |

## 6. 데이터 인코딩: (레지스터, 속성값) 쌍 구조

### 6.1 기본 인코딩 규칙

Payload는 **(레지스터 ID, 속성 바이트)** 쌍의 연속으로 구성됩니다. 속성 바이트의 상위 니블이 데이터 형식을 결정합니다:

| 속성 상위 니블 | 형식 | 길이 | 설명 |
|---------------|------|------|------|
| `0x0_` | 일반 값 | 2B | `[Reg] [0x0V]` — 하위 니블 V가 값 |
| `0x4_` | 불리언/플래그 | 2B | `[Reg] [0x4V]` — bit0이 ON/OFF |
| `0x5_` | **확장 값** | **3B** | `[Reg] [0x5_] [Value]` — 다음 바이트가 실제 값 (0~255) |
| `0x8_` | 단축 값 | 2B | `[Reg] [0x8V]` — 하위 4비트(0~15) = 값 |
| `0x9_` | **확장 값** | **3B** | `[Reg] [0x9_] [Value]` — 다음 바이트가 실제 값 (0~255) |
| `0xC_` | 플래그/모드 | 2B | `[Reg] [0xCV]` — 상태 플래그 |
| `0xD_` | **확장 값** | **3B** | `[Reg] [0xD_] [Value]` — 다음 바이트가 실제 값 |

**핵심**: `0x5_`, `0x9_`, `0xD_` 인코딩은 **3바이트**를 사용하여 값 범위를 0~255로 확장합니다. 이 때문에 동일한 데이터를 전송해도 payload 길이가 달라집니다.

### 6.2 예시: plen=26 vs plen=27

```
plen=26 (4비트): ... 18 41  18 88  29 c0 ...    ← capacity = 8 (4비트)
plen=27 (확장):  ... 18 41  18 90 11  29 c0 ...  ← capacity = 17Hz (8비트)
```

Pair `(0x18, 0x88)` → 상위니블 8 = 단축 값, 하위니블 = 8 (용량 8단계)
Pair `(0x18, 0x90, 0x11)` → 상위니블 9 = 확장 값, 다음 바이트 0x11 = 17Hz

## 7. 레지스터 맵 (요청/제어용)

### 7.1 상태 요청 (cmd=0x0204, 컨트롤러 → 실내기)

| Pair # | 레지스터 | 속성 범위 | 의미 |
|--------|----------|-----------|------|
| 0 | `0x11` | `0x00`/`0x01` | 난방 요구 신호 (bit0: 요구 ON) |
| 1 | `0x10` | `0xC0`/`0xC1` | 실외기 연동 (bit0: 활성) |
| 2 | `0x18` | `0x00` | 고정 파라미터 |
| 3 | `0x1A` | `0xC0`/`0xC1` | 냉매 회로 상태 (bit0: 운전) |
| 4 | `0x13` | `0x00`/`0x01` | 압축기 운전 확인 |
| 5 | `0x13` | `0x40` | 고정 |
| 6 | `0x13` | `0xC0`~`0xC6` | 운전 모드 (C0=일반, C1=난방, C3=제상) |
| 7 | `0x16` | `0x00` | 고정 |
| 8 | `0x18` | `0x40`/`0x41` | **전원 ON/OFF** (bit0: ON) |
| 9 | `0x18` | `0x80`~`0x8F` / `0x90+V` | **압축기 용량** (4비트 또는 확장Hz) |
| 10 | `0x29` | `0xC0` | 고정 |
| 11 | `0x1D` | `0xC0` | 고정 |

### 7.2 제어 명령 (cmd=0x0201, 컨트롤러 → 실내기)

0x0201은 **변경할 레지스터만 선택적으로 전송**합니다 (+ 마지막 2바이트 CRC).

| 대상 | 페이로드 예시 | 의미 |
|------|-------------|------|
| Unit 65/66 | `18,41 18,88 29,c0 [CRC]` | 전원 ON + 용량 8단계 |
| Unit 65/66 | `18,41 18,84 29,c0 [CRC]` | 전원 ON + 용량 4단계 (기동) |
| Unit 67 | `18,40 18,80 29,c0 [CRC]` | **전원 OFF** + 압축기 정지 |
| Unit 67 | `18,41 18,90,11 29,c0 [CRC]` | 전원 ON + **17Hz** (확장) |
| Unit 67 | `18,41 18,90,3C 29,c0 [CRC]` | 전원 ON + **60Hz** (확장) |
| Unit 67 | `18,41 18,90,78 29,c0 [CRC]` | 전원 ON + **120Hz** (확장) |
| Unit 67 | `10,c0 13,01 13,40 13,c0 [CRC]` | 실외기 연동 모드 설정 |
| Unit 67 | `11,00 [CRC]` | 난방 요구 해제 |
| Broadcast | `15,80 [CRC]` | 전체 제어 (상세 미확인) |
| Broadcast | `11,81 10,50 [CRC]` | 전체 운전 모드 설정 |

**발견된 확장 주파수 값 (0x90+V)**:

| Unit | 확장 Hz 값 |
|------|-----------|
| #1 (0x65) | 20, 40, 60, 120 Hz |
| #2 (0x66) | 16, 18, 20, 40, 60, 120 Hz |
| #3 (0x67) | 17, 19, 20, 60 Hz |

응답은 요청과 다른 레지스터 세트를 사용합니다:

| Offset | 레지스터 | 인코딩 | 값 범위 | 의미 |
|--------|----------|--------|---------|-----------|
| 0-1 | `0x60` | `0xC0`/`0xC1` | 플래그 | **전원 상태** (C0=OFF, C1=ON) |

| 8-9 | `0x62` | `0x40`/`0x41` | 플래그 | **냉매 밸브 개폐** (41=열림, 40=닫힘) |

| 13-14 | `0x6F` | `0x81` | 고정 | - |
| 15-16 | `0x6F` | `0xC0` | 고정 | - |
| 17-19 | `0x74` | `0x90` + V | 고정 0x19 | ~~실내 온도~~ **고정값** (항상 25, 온도 아님) |

### 8.4 Keep-alive (cmd=0x0604)

- 방향: 컨트롤러 → 브로드캐스트 (`ffffffff`)
- 주기: 약 30초
- Payload: `0x02` (1바이트 고정)
- 용도: 네트워크 존재 확인/연결 유지

## 9. 실내기별 운전 패턴 분석

### 9.1 실내기 #1 (0x65) — 연속 운전

- 10:52에 전원 ON → 캡처 종료까지 계속 ON 유지
- 압축기 용량이 8단계 기준으로 미세 변동 (4~13)
- 인버터 압축기가 부하에 따라 주파수를 미세 조정하는 패턴
- 제어 명령 확인: `18,41 18,88 29,c0` (ON + 8단계)가 주기적으로 전송됨

### 9.2 실내기 #2 (0x66) — 연속 운전 + 제상 사이클

- 11:53에 Byte[13]=C3 진입 → **제상(Defrost) 사이클** 시작
- 11:56에 전원 OFF, 약 22분간 Byte[13]=C3 유지
- 12:17에 정상 복귀 (C0)
- **제상 중 Byte[13]**: C6 → C3으로 전환되는 과도 상태 관측

### 9.3 실내기 #3 (0x67) — 주기적 ON/OFF + 확장 주파수 제어

가장 복잡한 제어 패턴. **확장 Hz 인코딩**이 주로 이 유닛에 사용됨:

```
Phase 1: 전원 ON (0201: 18,41 18,90,11 29,c0)  → 17Hz 기동
Phase 2: 주파수 상승 (0201: 18,41 18,90,14)     → 20Hz
Phase 3: 난방 가동 (b1=01, b3=c1)
Phase 4: 최대 운전 (b7=c1, b9=01, b13=c1)       → ~60Hz
Phase 5: 전원 OFF (0201: 18,40 18,80 29,c0)     → 정지
Phase 6: 대기 (~4~5분)
→ Phase 1로 복귀 (약 10~12분 주기)
```

## 10. 제어 명령 요약 (역공학 결과)

### 10.1 전원 제어

```
전원 ON:  cmd=0x0201, payload = [18 41 18 8V 29 c0 CRC]  (V=용량단계)
전원 OFF: cmd=0x0201, payload = [18 40 18 80 29 c0 CRC]
```

### 10.2 압축기 주파수 제어

```
4비트 단축: [18 8V]        → V = 0~F (0=정지, 4=최소, 8=보통, F=최대)
8비트 확장: [18 90 HH]     → HH = 주파수(Hz), 실측값: 16~120Hz
```

### 10.3 운전 모드 설정

```
일반 모드:  [13 c0]
난방 모드:  [13 c1]
제상 모드:  [13 c3] (자동 전환)
```

### 10.4 실외기 연동

```
실외기 활성화: [10 c1] [1a c1] [13 01]
실외기 비활성: [10 c0] [1a c0] [13 00]
```

## 11. 설정 온도 레지스터 (온도 변경 이벤트 분석)

### 11.1 데이터셋

- **파일**: `lgcp-invalid-온도변경.jsonl` (45 레코드, 13:30:39 ~ 13:32:14, 약 2분)
- **이벤트**: 실내기 #3(0x67)에서 설정 온도를 **25°C → 30°C**로 변경

### 11.2 설정 온도 레지스터: `0x64`

실내기 #3(Unit 67)의 plen=41 응답에서 **레지스터 0x64**가 설정 온도를 보고합니다.

**인코딩 규칙**:
```
속성 = 0x8V (단축 4비트 인코딩)
설정 온도(°C) = (V & 0x0F) + 15
```

**관측값**:

| 속성값 | 하위 니블 (V) | 계산 | 설정 온도 |
|--------|-------------|------|----------|
| `0x8A` | 10 (0xA) | 10 + 15 | **25°C** |
| `0x8B` | 11 (0xB) | 11 + 15 | **26°C** (과도 상태) |
| `0x8F` | 15 (0xF) | 15 + 15 | **30°C** |

**유효 범위**: 0x80(15°C) ~ 0x8F(30°C), 총 16단계 (15~30°C)

### 11.3 온도 변경 시퀀스 (시간순)

```
13:30:39~58  정상 폴링 (Unit 67 응답에 reg 0x64 = 0x8A = 25°C)
                       팬모터 ~40Hz 운전 중

13:30:59     [0x0201] Unit 67 → 컨트롤러
             payload: 64,8B  (26°C — 과도값, 리모컨 조작 시작)

13:31:01     [0x0201] Unit 67 → 컨트롤러
             payload: 64,8F  (30°C — 최종 설정값 도달)

13:31:02     [0x0201] 컨트롤러 → Unit 67
             payload: 10,C1  18,41  18,89  29,C0
             의미: 실외기 활성화 + 전원 ON + 압축기 용량 9단계 + 고정

13:31:03~    정상 폴링 재개 (Unit 67 응답에 reg 0x64 = 0x8F = 30°C)
             팬모터 주파수 40Hz → 90Hz로 상승
```

### 11.4 핵심 발견

1. **Unit 67이 마스터/서모스탯 역할**: 온도 변경은 Unit 67만이 `0x0201`로 컨트롤러에 보고하며, 다른 유닛(65, 66)은 레지스터 0x64를 응답에 포함하지 않습니다.
2. **실내기 → 컨트롤러 방향의 0x0201**: 리모컨에서 온도를 변경하면 실내기가 능동적으로 컨트롤러에 설정값을 전달합니다 (폴링 응답이 아닌 이벤트 기반 전송).
3. **과도 상태 존재**: 25°C에서 30°C로 변경 시 중간값(26°C)이 약 2초간 관측됩니다. 리모컨의 버튼 조작 과정이 그대로 반영되는 것으로 보입니다.
4. **컨트롤러의 즉각 응답**: 온도 변경 보고를 받은 컨트롤러는 약 1초 내에 압축기 용량을 재설정(`18,89` = 9단계)하고, 이후 실내기 팬모터 주파수가 40Hz → 90Hz로 상승합니다.

### 11.5 온도 설정 제어 명령 (추정)

온도를 설정하려면 다음과 같은 명령을 전송할 수 있을 것으로 추정됩니다:

```
cmd = 0x0201
payload = [64 8V CRC]
V = 설정온도(°C) - 15    (15°C → V=0, 30°C → V=F)
```

| Y | 모드 | 한글 |

| 1 | 제습 | Dehumidify |

### 12.4 `0x71` — 풍속 응답 레지스터

plen=44 확장 응답의 byte[30-31]에서 `0x71`이 현재 풍속을 보고합니다:

| `71` 값 | 풍속 | 비고 |
|---------|------|------|
| `0x00` | - | 미설정/과도 상태 |
| `0x01` | 약풍 (1단) | |
| `0x02` | 중풍 (2단) | |
| `0x03` | 강풍 (3단) | 추정 (직접 관측은 폴링 주기 사이에 빠져나감) |
| `0x04` | 초강 (4단) | 추정 (동일) |
| `0x05` | 자동 | |

- `71`은 `64,50`보다 업데이트가 느림 (plen=44 응답 주기 ~20~30초)
- Unit 65는 항상 `71,00` (슬레이브 유닛 — 풍속 미보고)
- Unit 67만 비영 값 보고 (마스터/서모스탯 역할)

### 12.5 모드 변경 이벤트 시퀀스

### 12.6 온도 감소 시 컨트롤러 동작 비교 (lgcp-valid2.jsonl)

| 항목 | 온도 증가 (25→30°C) | 온도 감소 (30→25°C) |
|------|---------------------|---------------------|
| 압축기 용량 | 9단계 (증가 지시) | 4단계 (감소 지시) |
| 실외기 | 활성화 (`10,C1`) | 비활성화 (`10,C0`) |

| 냉매 밸브 (62,4_) | 0x41 (열림 유지) | 0x41 → 0x40 (닫힘 전환) |

### 12.7 모드 변경 시 `77,E0` 마커

난방↔다른 모드 간 **큰 전환**(compressor 상태가 바뀌는 경우)에서만 `77,E0`로 시작하는 대형 이벤트(plen=30~32)가 전송됩니다. 송풍→냉방, 냉방→자동 같은 중간 전환에는 작은 이벤트(plen=15~20)만 전송됩니다.

## 13. 제어 명령 요약 (최종)

### 13.1 설정 온도 제어

```
온도 설정: cmd=0x0201, payload = [64 8V CRC]
  V = 설정온도(°C) - 15
  예: 25°C → [64 8A], 30°C → [64 8F]
  범위: 15°C (0x80) ~ 30°C (0x8F)
```

### 13.2 풍속 제어

```
풍속 설정: cmd=0x0201
  이벤트 레지스터: [64 50 XY]  (X=풍속, Y=모드)
  응답 레지스터:   [71 0V]     (V=풍속 단계)

  풍속 단계: 1=약풍, 2=중풍, 3=강풍, 4=초강, 5=자동
```

### 13.3 운전 모드 제어

```
모드 설정: cmd=0x0201
  이벤트 레지스터: [64 50 XY]  (X=풍속, Y=모드)

  모드 코드: 0=냉방, 1=제습, 2=송풍, 3=자동, 4=난방

  예: 난방/약풍   → [64 50 14]
      냉방/자동풍 → [64 50 50]
      송풍/강풍   → [64 50 32]
```

### 13.4 복합 제어 (모드 + 온도 + 풍속)

```
모드 전환 이벤트: cmd=0x0201, Unit67 → 컨트롤러
  payload = [64 50 XY] [64 8T] [71 0F] [기타 레지스터] [CRC]

  XY = (풍속단계 << 4) | 모드코드
  T  = 설정온도(°C) - 15
  F  = 풍속단계 (0x71 중복 전송)

  예: 난방 25°C 약풍 → [64 50 14] [64 8A] [71 01]
```

### 13.5 전원 및 압축기 제어 (기존)

```
전원 ON:  [18 41 18 8V 29 C0]  (V=용량단계)
전원 OFF: [18 40 18 80 29 C0]
압축기 4비트: [18 8V]         V=0~F
압축기 확장:  [18 90 HH]      HH=Hz (16~120)
운전 모드:    [13 C0]=일반, [13 C1]=난방, [13 C3]=제상
실외기 활성:  [10 C1], 비활성: [10 C0]
```

## 16. 실내 온도 센서 분석 (확정)

### 16.1 실내 온도 레지스터: `0x61` attr `0x9_`

**기존 오류**: reg `0x74` (attr `0x90+V`)를 실내 온도로 추정했으나, 캡처 데이터 분석 결과 **모든 프레임에서 고정값 0x19 (=25)**를 보고하여 실내 온도가 아님을 확인.

**실제 실내 온도**: plen=44 확장 응답의 reg `0x61` attr `0x9_` (3바이트 확장 인코딩)

**인코딩 공식** (확정, 제조사 앱 검증 완료):
```
실내 온도(°C) = (157V - V² - 796) / 162    (0.5°C 단위 반올림)
```

NTC 열저항의 비선형 특성으로 인해 단순 선형 공식 `(A-V)/B`는 전 구간에서 작동하지 않음.
3개 기준점 (V=119→23°C, V=110→27°C, V=101→30°C)으로 도출한 2차 다항식 사용.

**검증 데이터** (제조사 앱 대비):

| ext (V) | 공식 결과 | 반올림 | 앱 온도 | 일치 |
|---------|----------|--------|---------|------|
| 120 | 22.49 | 22.5 | 23.0 | ±0.5 |
| 119 | 23.00 | 23.0 | 23.0 | ✓ |
| 118 | 23.50 | 23.5 | 23.5 | ✓ |
| 117 | 23.98 | 24.0 | 24.0 | ✓ |
| 116 | 24.44 | 24.5 | 24.5 | ✓ |
| 114 | 25.33 | 25.5 | 25.5 | ✓ |
| 112 | 26.18 | 26.0 | 26.0 | ✓ |
| 111 | 26.58 | 26.5 | 26.5 | ✓ |
| 110 | 26.96 | 27.0 | 27.0 | ✓ |
| 109 | 27.34 | 27.5 | 27.5 | ✓ |
| 108 | 27.70 | 27.5 | 27.5 | ✓ |
| 107 | 28.04 | 28.0 | 28.0 | ✓ |
| 106 | 28.38 | 28.5 | 28.5 | ✓ |
| 102 | 29.68 | 29.5 | 29.5 | ✓ |
| 101 | 29.97 | 30.0 | 30.0 | ✓ |

**정확도**: 16개 중 14개 정확 일치, 2개 ±0.5°C (경계값 양자화 차이)

**특징**:
- 0.5°C 단위 해상도 (반올림: `round(raw*2)/2`)
- plen=44 확장 응답에서만 보고됨 (plen=41에는 없음)
- reg 0x61의 다른 인코딩: attr `0xD0+V`는 배관 온도 1 (V/2 = °C)
- 유효 범위: V=95~130 (약 20~33°C, 일반 실내 HVAC 운전 범위)

### 16.2 3바이트 확장 인코딩 타입 (확정)

속성 바이트의 상위 니블이 다음 중 하나면 **3바이트 확장** ([reg, attr, ext]):

| 상위 니블 | 형식 | 확인 상태 |
|-----------|------|-----------|
| `0x1_` | 3바이트 확장 | 확인됨 (0x62 0x10+V = 배관 온도 2) |
| `0x5_` | 3바이트 확장 | 확인됨 (0x64 0x50+XY = 풍속+모드) |
| `0x9_` | 3바이트 확장 | 확인됨 (0x61 0x90+V = 실내 온도, 0x18 0x90+Hz = 압축기) |
| `0xD_` | 3바이트 확장 | 확인됨 (0x61 0xD0+V = 배관 온도 1, 0x62 0xD0+V = 팬모터 Hz) |

## 17. 제어 명령 상태 분리

### 17.1 문제

cmd=0x0201 (제어 명령) 프레임에도 센서 관련 레지스터(실내 온도, 배관 온도 등)가 포함될 수 있으나, 이 값은 **제어 대상 디바이스의 실제 센서 값이 아님**. 제어 명령의 페이로드를 그대로 디바이스 상태에 병합하면 잘못된 센서 값이 표시됨.

### 17.2 해결 방법

제어 명령(cmd=0x0201)과 상태 응답(cmd=0x0204)의 페이로드를 분리 처리:

| 프레임 타입 | 대상 디바이스 | 병합 범위 |
|------------|-------------|-----------|
| `0x0201` (제어) | DA (목적지) | **제어 필드만**: power, power_state, set_temp, fan_speed, mode |
| `0x0204` (상태) | SA (출발지) | **모든 필드**: 센서값 + 제어값 + 상태 플래그 |
| `0x0604` (Keep-alive) | 무시 | - |

### 17.3 구현

```
// 제어 명령은 제어 필드만 병합
if cmd == 0x0201:
    target = frame.DA
    mergeControlFields(target, decoded)  // power, set_temp, mode, fan_speed만

// 상태 응답은 전체 병합
if cmd == 0x0204:
    source = frame.SA
    mergeAllFields(source, decoded)      // 모든 센서값 + 제어값
```
