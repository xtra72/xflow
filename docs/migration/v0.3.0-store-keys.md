# Store v0.3.0 마이그레이션 가이드

> SPEC-STORE-003 v0.3.0 BREAKING 변경에 대한 운영자 가이드. 본 문서는 v0.2.0 yaml을 v0.3.0 형식으로 업데이트하는 단계별 절차를 제공한다.

## 빠른 체크리스트

업그레이드 전 다음 항목을 확인:

- [ ] yaml 파일에서 `allow_dynamic_keys` 검색 (grep으로 검출)
- [ ] manual 모드(`allow_dynamic_keys: false`) 사용 중인 store agent 식별
- [ ] 각 정적 키의 expected Go value type 사전 결정 (data_type 매핑)
- [ ] frontend (SPEC-WEB-005) 업데이트 일정과 동기화 계획

## 변경 요약

| 항목 | v0.2.0 | v0.3.0 |
|------|--------|--------|
| 동적 키 허용 플래그 | `allow_dynamic_keys: bool` | `registration_type: enum (manual\|auto)` |
| 정적 키 data type | 없음 (any) | `data_type: enum (6종)` |
| 정적 키 semantic 분류 | tags 안에 `type=...` | `metric_type: string` 1급 필드 |
| API 응답 (GET /keys) | string 배열 + 별도 tags 맵 | 객체 배열 |
| API 필터 | `?tag=` only | `?tag=` + `?data_type=` + `?metric_type=` + `?registration=` (AND) |
| 신규 에러 | — | 4종 (TypeMismatch, UnsupportedValueType, InvalidDataType, InvalidMetricType) |

## yaml 마이그레이션

### 패턴 1: 단순 모드 변경 (대부분의 경우)

**Before (v0.2.0)**:

```yaml
agents:
  - type: store
    name: "system-store"
    config:
      allow_dynamic_keys: false   # 또는 true (default)
      keys:
        - key: "indoor:1:room_temp"
          tags:
            room: "1"
            type: "temperature"   # tags 안에 의미 분류
```

**After (v0.3.0)**:

```yaml
agents:
  - type: store
    name: "system-store"
    config:
      registration_type: "manual"     # bool → enum (or "auto")
      keys:
        - key: "indoor:1:room_temp"
          data_type: "float"          # 추가 필수 (manual 모드)
          metric_type: "temperature"  # tags의 type=temperature를 1급 필드로 승격
          tags:
            room: "1"                 # 나머지 tags는 그대로
```

### 패턴 2: 빈 설정 + auto 모드

**Before (v0.2.0, 또는 default)**:

```yaml
agents:
  - type: store
    name: "system-store"
    config:
      # allow_dynamic_keys 생략 → default true
```

**After (v0.3.0, default 그대로 호환)**:

```yaml
agents:
  - type: store
    name: "system-store"
    config:
      # registration_type 생략 → default "auto" (자동 등록 + 첫 쓰기에서 data_type 추론)
```

이 경우 yaml 변경 불필요하다.

### 패턴 3: 다양한 data_type 키

```yaml
registration_type: "manual"
keys:
  - key: "device:event"
    data_type: "json"           # struct/map/slice 형태
    metric_type: "event"
    tags:
      kind: "telemetry"

  - key: "sensor:bytes"
    data_type: "bytes"          # raw binary
    tags: {}

  - key: "ack:flag"
    data_type: "boolean"
    tags: {}
```

## data_type 매핑 표

| Go 값 타입 | yaml `data_type` |
|-----------|------------------|
| `bool` | `"boolean"` |
| `int`, `int8`..`int64`, `uint`..`uint64` | `"int"` |
| `float32`, `float64` | `"float"` |
| `string` | `"string"` |
| `[]byte` | `"bytes"` |
| `map[string]any`, `[]T`, struct (json-marshalable) | `"json"` |
| `nil`, `chan`, `func` | (auto 모드에서 ErrUnsupportedValueType) |

## 부팅 실패 시나리오

### 시나리오 1: `allow_dynamic_keys` 잔존

```text
Error: store config: 'allow_dynamic_keys' is removed in v0.3.0; use 'registration_type: manual|auto' instead
```

**해결**: yaml에서 `allow_dynamic_keys`를 제거하고 `registration_type`을 추가한다.

### 시나리오 2: manual 모드 + data_type 누락

```text
Error: store config: keys[N].data_type is required in manual mode (must be one of: int, float, string, boolean, bytes, json)
```

**해결**: 해당 정적 키 엔트리에 적절한 `data_type`을 추가한다.

### 시나리오 3: 잘못된 enum 값

```text
Error: store config: data_type "decimal" is invalid (must be one of: int, float, string, boolean, bytes, json)
```

**해결**: 위 매핑 표를 참조하여 올바른 enum 값을 사용한다.

### 시나리오 4: 잘못된 metric_type 형식

```text
Error: store config: metric_type "room.temp" is invalid (must match ^[a-zA-Z0-9_-]+$)
```

**해결**: `metric_type` 값에서 점/공백/콜론/유니코드 문자를 제거한다.

## 운영 체크리스트

배포 전 grep으로 마이그레이션 누락 검출:

```bash
# yaml 파일 전체 검사
grep -rn "allow_dynamic_keys" config/ deploy/ --include="*.yaml" --include="*.yml"
# 결과가 비어있어야 함

# manual 모드 키들이 data_type을 가지는지 검사
yq eval '.agents[] | select(.type=="store") | .config | select(.registration_type=="manual") | .keys[] | select(.data_type == null) | .key' your-config.yaml
# 결과가 비어있어야 함
```

## API 클라이언트 마이그레이션

### `GET /api/v1/store/{name}/keys` 응답

**v0.2.0 형식**:

```json
{
  "count": 2,
  "keys": ["indoor:1:room_temp", "indoor:1:humidity"],
  "tags": {
    "indoor:1:room_temp": {"room": "1", "type": "temperature"},
    "indoor:1:humidity": {"room": "1", "type": "humidity"}
  }
}
```

**v0.3.0 형식**:

```json
{
  "count": 2,
  "keys": [
    {
      "key": "indoor:1:humidity",
      "registration": "manual",
      "data_type": "float",
      "metric_type": "humidity",
      "tags": {"room": "1"}
    },
    {
      "key": "indoor:1:room_temp",
      "registration": "manual",
      "data_type": "float",
      "metric_type": "temperature",
      "tags": {"room": "1"}
    }
  ]
}
```

**TypeScript 타입 변경 예시**:

```typescript
// v0.2.0
type StoreKeysResponse = {
  count: number;
  keys: string[];
  tags?: Record<string, Record<string, string>>;
};

// v0.3.0
type StoreKeyObject = {
  key: string;
  registration: "manual" | "auto";
  data_type: "int" | "float" | "string" | "boolean" | "bytes" | "json";
  metric_type: string;
  tags: Record<string, string>;
};
type StoreKeysResponse = {
  count: number;
  keys: StoreKeyObject[];
};
```

### 신규 필터 사용 예시

```bash
# 단일 axis
curl "https://api/v1/store/main/keys?data_type=float"
curl "https://api/v1/store/main/keys?metric_type=temperature"
curl "https://api/v1/store/main/keys?registration=auto"

# 다축 AND 결합
curl "https://api/v1/store/main/keys?registration=manual&metric_type=temperature&tag=room:1"
```

## 알려진 차이

### `?metric_type=` 빈 값

- **SPEC 명시**: 빈 결과 반환 (전체 반환 아님)
- **현재 구현**: no-op passthrough (모든 키 반환)
- **영향**: 0 (metric_type이 항상 normalize되어 빈 문자열 키가 존재 불가)
- **계획**: 다음 SPEC 갱신에서 SPEC을 구현에 맞춰 정렬

## Auto 모드 type pinning

v0.3.0에서 `registration_type: "auto"` 모드는 키의 첫 쓰기에서 `data_type`을 추론하여 **영구 고정**한다. 후속 쓰기는 같은 타입이어야 하며, 다른 타입은 `ErrTypeMismatch`로 거부된다.

```go
// 첫 쓰기: 자동으로 data_type="int" 등록
store.Set(ctx, "sensor1", 42)

// 후속 쓰기: 타입 일치 → 성공
store.Set(ctx, "sensor1", 100)

// 후속 쓰기: 타입 불일치 → ErrTypeMismatch
store.Set(ctx, "sensor1", "broken")  // string은 거부됨
```

타입 변경이 필요한 경우 키를 삭제하고 재등록한다 (`DELETE /api/v1/store/{name}/keys/{key}`).
