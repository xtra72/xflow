## 개요 (Overview)

### 이 SPEC 이 바꾸지 않는 것부터 적는다 — 그것이 이 SPEC 의 크기다

- **좌표계를 바꾸지 않는다.** 요소 기하는 여전히 정수 캔버스 단위이고(`canvasConfig.ts` 머리말
  §좌표계가 정수인 이유), 캔버스 밖 배치는 여전히 합법이며 clamp 되지 않는다(가정 A5).
- **`CanvasProjection { stage, canvas }` 는 두 칸 그대로다.** 006 이 상자를 둘로 지으면서도
  이 계약을 지켰고, 008 도 지킨다.
- **기하 쓰기는 여전히 `patchNodeGeometry` 한 함수를 지난다.** 008 이 더하는 자료(경로 명령
  목록)는 **기하가 아니므로 그 통로를 지나지 않으며**, 지나면 안 된다(불변식 J2).
- **좌표 공간을 넘는 자리는 여전히 `stagePoint` 하나다.** 스크래치패드의 끌어놓기는 그 함수를
  **더 부르되 두 번째 함수를 만들지 않는다**(§끌어놓기는 어느 공간에서 판정하는가).
- **백엔드 변경 0.** 카탈로그는 코드 내장이고 배치 결과는 불투명 JSON config 안에 들어간다.
  스크래치패드는 **config 에 아예 들어가지 않는다**(§스크래치패드는 어디에 사는가).
- **`PanelSettingsDialog.tsx` 에 캔버스 표면을 더하지 않는다**(006 불변식 I7). 팔레트도
  스크래치패드도 도크가 그리고, 도크는 포털로 이미 그 자리에 있다. **재는 자는 행 수가
  아니라 `panels/canvas/` 수입 허용목록이다**(0.3.0 — 근거는 §HISTORY 0.3.0 이 소유한다).

> **0.1.0~0.2.0 의 문장(폐기 · 남긴다)**: "**한 줄도 자라지 않는다**(오늘 8,371행 — 실측)".
> 행 수 등식은 불변식의 **대리**였고, 캔버스와 무관한 두 줄(패널 색상 자유 입력)에 울린 뒤
> 시험에서만 8,373 으로 재기준되어 이 문서와 갈라졌다.

**설계가 `CanvasSize` 의 뜻을 바꾸거나, `projection` 을 세 칸으로 넓히거나, config 스키마를
백엔드가 아는 형상으로 만드는 쪽으로 흘렀다면 그것은 길을 잘못 든 것이며 되짚어야 한다.**

### 무엇을 바꾸는가 — 둘이고, 둘은 서로 다른 층이다

**① 도형 카탈로그.** 오늘 팔레트가 내는 것은 넷뿐이다 — `PALETTE_KINDS = ['rect',
'ellipse', 'line', 'text']`(`CanvasEditDock.tsx:134`). 사용자가 내민 화면에는 묶음마다 수십
개의 도형이 있고, 그 대부분은 **넷의 합성으로 만들어지지 않는다**. 008 은 다섯 번째 원시형
`path` 를 들이고, 그 위에 **일반 · 기본 · 화살표 세 묶음 30종**을 코드 내장 카탈로그로 얹는다.

**② 스크래치패드.** 사용자가 캔버스에서 조립한 것을 **끌어다 저장해 두고 되쓰는 자리**다.
카탈로그가 "우리가 준 재료" 라면 스크래치패드는 "당신이 만든 재료" 이며, 그래서 사는 곳도
다르다 — 카탈로그는 코드에, 스크래치패드는 **그 사람의 기기**에 산다(§스크래치패드는 어디에
사는가).

### 왜 새 번호인가 — 006 의 로드맵이 이 일을 004 에 배정해 두었다

`SPEC-CANVAS-006/plan.md` §후속 SPEC 로드맵(709–713행)은 이렇게 적어 두었다:

> **SPEC-CANVAS-004 — 설비 심볼 라이브러리 (= 사용자의 ①)**: "팔레트에 다양한 모형들과
> 종류별 그룹" 은 **이 SPEC 의 주제 그 자체**다 … **새 번호를 따지 않는다.**

**그 문장은 오늘 사용자가 낸 요구에 대해 참이 아니며, 이 SPEC 이 그 판단을 뒤집는다.** 근거
셋을 이름으로 적는다.

1. **주제가 다르다.** 004 의 주제는 **설비 심볼**이고, 그 심볼의 존재 이유는 "규칙이 부품을
   지목할 수 있어야 '밸브 열림 = 몸통이 초록으로 + 스템이 열린 자리로' 가 001 의 규칙 표만으로
   표현되기 때문" 이다(004 §중심 설계 결정). 즉 004 가 파는 것은 **상태**다. 사용자가 내민
   화면의 일반·기본·화살표는 상태를 나르지 않는다 — 그것은 **장식과 구조**이며, 한 도형이
   **통째로 하나의 스타일**을 입는다.
2. **004 의 중심 결정이 이 도형들을 표현하지 못한다.** 004 는 심볼을 `rect`/`ellipse`/`line`/
   `text` 의 합성으로 정의했다. 그 정의로 밸브는 만들어지지만 **구름 · 별 · 육각형 · 원통 ·
   문서(하단 파형) · 말풍선 · 초승달**은 만들어지지 않는다. 넷 중 어느 것도 임의의 닫힌
   윤곽을 그리지 못하기 때문이다. 사용자의 화면에 있는 것 대부분이 그 부류다.
3. **004 를 쓰지 않는다는 뜻이 아니다.** 008 이 더하는 `path` 는 004 의 `group` 이 담을 수
   있는 **또 하나의 부품 종류**가 된다 — 004 가 스스로 적어 둔 문("훗날 `kind: 'image'` 부품이
   필요해지면 group 이 그 그릇이다")이 그대로 성립한다. **역할 분담은 이렇게 갈린다: 윤곽과
   장식은 008 의 `path` 가, 상태를 나르는 조립체는 004 의 `group` 이 맡는다.**

번호를 새로 따는 대신 004 에 얹는 길도 있었다. **기각한다** — 004 는 아직 한 줄도 구현되지
않았고 제 스키마가 이미 낡았으며(아래 §004 의 스키마는 오늘 낡아 있다), 그 위에 30종 카탈로그와
스크래치패드를 얹으면 004 는 **캐스케이드 4단 법칙 · 중첩 투영 · 복합 프레임 키 · 부품 단위
규칙 · 경로 원시형 · 카탈로그 · 스크래치패드**를 한 번에 배달해야 하는 SPEC 이 된다. 그것은
착수할 수 없는 크기다.

### 004 의 `group` 에 기대지 않는다 — 이 SPEC 의 중심 결정

스크래치패드는 **여러 요소로 조립한 것을 하나로 저장했다가 되놓는다.** 형상만 보면 그것은
정확히 004 의 `group` 이고, **004 는 구현되지 않았다.** 이 의존을 어떻게 끊는지가 이 SPEC 의
무게중심이다.

세 갈래가 있었다.

**(a) 008 이 `group` 스키마를 구현하고 004 가 그 위에 카탈로그를 얹는다.** 기각한다. 004 의
`group` 은 필드 셋이 아니라 **법칙 하나**를 함께 가져온다 — 파생 우선 4단 캐스케이드
(REQ-06), `opacity` 곱셈 예외, 중첩 투영 3종(`projectBoxIn`/`projectLineIn`/`projectPointIn`),
복합 프레임 키(`groupId/partId`)와 그에 따른 트윈 장부 개편, 부품 단위 히트(`CanvasHit.partId`).
그 가운데 **스크래치패드가 요구하는 것은 하나도 없다.** "저장한 것을 다시 놓는다" 는 요구는
캐스케이드도 부품 규칙도 부품 히트도 쓰지 않는다. 남의 SPEC 의 주제를 이 SPEC 의 전제 조건으로
끌어오는 것은 값이 맞지 않는다.

**(b) 004 를 먼저 보낸다.** 기각한다. 사용자가 오늘 낸 요구는 설비 심볼이 아니고, 004 는 위
크기의 SPEC 이며, 게다가 제 스키마가 낡아 착수 전 개정이 필요하다(아래). 순서를 바꾸면 오늘의
요구가 그 개정 뒤로 밀린다.

**(c) 채택 — 스크래치패드는 중첩 없는 요소 목록을 저장하고, 놓기는 형제 요소들을 옮겨
찍는다(평평한 붙여넣기).** 저장된 항목의 몸체는 `CanvasElement[]` 이며 **컨테이너 노드가
아니다.** config 스키마는 이 축에서 **한 글자도 넓어지지 않는다.**

**(c) 가 치르는 값을 숨기지 않는다.** 여덟 요소짜리 항목을 놓으면 요소 목록에 여덟 줄이
생기고, 그것을 **통째로 지울 단추가 없다**(목록 편집기의 삭제는 행 단위다). 완화는 하나뿐이고
그것으로 충분하다 — **놓은 직후 만들어진 id 전부를 선택으로 세운다.** 오버레이의 무리 이동은
선택된 **모든** 요소에 같은 캔버스 단위 델타를 더하므로(`CanvasEditOverlay.tsx` 의 `bases`
조립), 놓자마자 한 덩어리로 끌린다. 정렬 · 순서 · 방향키 미세 이동도 같은 선택 위에서 그대로
돈다.

**004 가 나중에 착륙하면 저장된 항목은 어떻게 되는가 — 한 바이트도 바뀌지 않는다.** 저장 형상이
`CanvasElement[]` 이고 `GroupElement.parts` 의 타입이 정확히 `CanvasElement[]` 이기 때문이다.
004 가 오면 스크래치패드는 **놓기 방식 하나를 더 얻을 뿐**이다("그룹으로 놓기"), 저장 형상을
갈지 않는다. 반대 방향은 성립하지 않는다 — 지금 `group` 을 저장 형상으로 삼으면, 아직 배달되지
않았고 아래 이유로 **개정이 예정된** 스키마 위에 이 SPEC 의 영속 자료를 얼려 두게 된다.

#### 004 의 스키마는 오늘 낡아 있다 (정찰로 확인 · 본 SPEC 은 004 를 수정하지 않는다)

`SPEC-CANVAS-004/spec.md` §config 스키마 확장(346–347행)은 그룹 기하를 **"스테이지 정규화
(0..1)"**, 부품 기하를 **"그룹 박스 로컬 정규화(0..1)"** 로 적고, §환경(190행)은 001 의 기하를
**"정규화(0..1) 기하"** 로 적는다. **그 셋 다 오늘 참이 아니다** — SPEC-CANVAS-002 0.8.0 이
좌표계를 정수 캔버스 단위로 옮겼고(커밋 `1704e89c`), 코드 주석의 같은 거짓말은 이미 걷혔다
(커밋 `5dfb3996` "좌표가 정규화라던 낡은 주석 셋을 사실로 되돌린다"). 004 의 문서만 남았다.

이 사실은 (a) 를 기각하는 근거를 하나 더 준다: **008 이 004 의 `group` 을 구현하려면 먼저
004 를 개정해야 한다.** 그 개정은 004 의 몫이다. 본 SPEC 은 다른 SPEC 문서를 수정하지 않고
후속 편집 대상으로만 적는다(plan.md §로드맵 정합).

### 카탈로그에는 새 원시형이 필요하다 — 그리고 그 근거는 004 안에 이미 있다

004 의 중심 결정은 **"심볼은 기존 원시형의 합성"** 이고, 그 결정은 제 주제 안에서 옳다. 밸브는
몸통(선 둘) + 스템(선) + 손잡이(사각형)이며, 규칙이 `stem` 을 이름으로 지목할 수 있어야 하므로
**부품이 나뉘어 있는 것 자체가 요구**다.

**그 결정은 008 의 주제로 옮겨 오지 않는다.** 구름 하나를 rect/ellipse/line 으로 만들면 부품이
여덟 개인데 그 여덟은 서로 다른 상태를 나르지 않는다 — 그저 **하나의 윤곽**이며, 사용자는 그것
하나에 색을 입힌다. 부품으로 쪼개면 색을 여덟 번 입혀야 하고, 겹친 타원의 이음매가 선으로
드러나며, 요소 목록이 여덟 배로 길어진다. **별 · 육각형 · 팔각형 · 십자 · 사다리꼴 · 화살표**는
그마저도 되지 않는다 — 네 원시형 중 어느 것도 임의의 다각형 윤곽을 그리지 못한다.

그래서 다섯 번째 원시형 **`path`** 를 들인다. 한 요소가 **하나의 윤곽**이고, 그 윤곽 전체가
**하나의 스타일**을 입으며, 001 의 규칙 표가 오늘 rect 에 하는 일을 그대로 한다.

**그 대가를 정직하게 적는다: 규칙은 경로의 안쪽을 지목하지 못한다.** 004 가 이미지를 기각하며
든 근거 넷 가운데 **살아남는 것이 정확히 이 하나**다. 그리고 이 SPEC 의 범위 안에서 그것은
결함이 아니다 — 상태를 나르는 조립체는 004 의 `group` 이 맡기로 위에서 갈랐기 때문이다.
경로로 만든 밸브를 상태로 바꾸려는 사람은 004 를 기다려야 하며, 이 SPEC 은 그 사실을 감추지
않는다(위험 R6).

#### 004 가 이미지를 기각한 근거 넷 가운데 셋은 경로에 닿지 않는다

004 §중심 설계 결정이 (B) 이미지/SVG 를 기각하며 든 것을 하나씩 대조한다. **정찰로 확인한
것이지 추정이 아니다.**

| 004 가 든 근거 | 경로에 닿는가 | 확인 |
|---|---|---|
| 규칙이 심볼 **내부를 지목하지 못한다** | **닿는다** | 경로도 통째로 하나의 스타일이다. 위 문단이 그 값을 적었다 |
| `drawImage` 를 들이면 **비동기 로드·디코드·캐시 수명주기가 rAF 루프로 들어온다**(001 REQ-05 유휴 정지와 정면 충돌) | **닿지 않는다** | 경로 명령은 동기 기하다. `closePath`/`bezierCurveTo` 는 값을 돌려주지도, 기다리지도 않는다. 프레임을 예약하지 않으므로 유휴 정지는 **한 줄도 바뀌지 않는다** |
| 자산은 **인증 헤더가 필요해** JSON→data-URL 왕복이 붙는다 | **닿지 않는다** | 경로는 config 안의 숫자다. 자산 API 를 쓰지 않는다 |
| `svgAsset.ts` 의 제약(인라인 금지 · `preserveAspectRatio` 가 CSS 를 이긴다 · `naturalWidth` 를 믿을 수 없다)을 물려받는다 | **닿지 않는다** | SVG 문서를 읽지 않는다. 경로 명령은 이 저장소가 발행하는 자료이며 브라우저의 SVG 파서를 지나지 않는다 |

그래서 004 의 기각은 **문을 닫는 결정이 아니었고**, 008 은 그 문 가운데 셋이 열려 있는 쪽으로
들어간다.

### `DrawContext2D` 에 더하는 것은 둘이고, 그 둘이 왜 그 둘인가

오늘 그 인터페이스가 가진 것은 이렇다(`drawElement.ts:59–88`, 실측):

```
save · restore · setTransform · beginPath · rect · ellipse · moveTo · lineTo ·
stroke · fill · fillText · measureText · clearRect · fillRect
+ fillStyle · strokeStyle · lineWidth · globalAlpha · font · textAlign · textBaseline
```

**다각형은 오늘 이미 그려진다.** `beginPath` → `moveTo` → `lineTo`×N → `fill`/`stroke` 가 전부
있다. 30종 가운데 **23종이 다각형뿐**이므로, 그 23종에 필요한 인터페이스 변경은 **없다** — 다만
하나가 걸린다(아래 `closePath`).

**더하는 것 (1) — `closePath(): void`.** `fill()` 은 부분 경로를 암묵적으로 닫으므로 채움에는
없어도 된다. **선에는 없으면 안 된다** — 마지막 정점에서 첫 정점으로 `lineTo` 로 돌아가면 그
자리는 **이음(join)이 아니라 두 끝점**이라 두께 2px 이상에서 별의 뾰족한 꼭짓점에 홈이 파인다.
"채우면 멀쩡한데 선만 그으면 한 꼭짓점이 이상하다" 는 화면에서만 드러나는 부류다.

**더하는 것 (2) — `bezierCurveTo(cp1x, cp1y, cp2x, cp2y, x, y): void`.** 30종 가운데 **7종**
(둥근 사각형 · 문서 · 원통 · 말풍선 · 액터 · 구름 · 곡선 화살표)이 곡선을 요구한다.

**더하지 않는 것과 그 이유.**

- **`quadraticCurveTo`** — 2차 베지어는 3차로 **정확히** 표현된다(`c1 = p0 + 2/3(q−p0)`,
  `c2 = p1 + 2/3(q−p1)`). 근사가 아니라 항등이므로 더하면 순수한 중복이다.
- **`arcTo`** — 둥근 모서리를 위해 있는 함수지만, 4분원은 3차 베지어로 `k = 4/3·(√2−1) ≈
  0.5523` 제어점 오프셋에서 **최대 반경 오차 0.027%** 로 근사된다. 캔버스 최대 축(100,000
  단위)의 둥근 모서리에서도 27 단위, 실사용 크기(수백 단위)에서는 **0.1 단위 미만** — 장치
  픽셀 하나보다 훨씬 작다. 그리고 `arcTo` 는 **접선 기반**이라 "모서리 규칙" 이 하나 더
  생긴다: 같은 코너를 두 가지 방식으로 적을 수 있게 되고, 카탈로그 30종이 그중 어느 쪽으로
  적혔는지 읽는 사람이 매번 확인해야 한다.
- **`arc` · 경로 안에서의 `ellipse` 재사용** — `ellipse` 는 이미 있고 부분 호(시작·끝 각)도
  받는다. **쓰지 않는다.** 첫째, 그 함수는 현재 점에서 호 시작점까지 **직선을 하나 몰래 긋는다**
  (canvas 명세) — 경로를 잇는 두 번째 규칙이 생긴다. 둘째, 초승달처럼 **반시계 방향** 호가
  필요한 도형은 오늘의 7인자 시그니처(반시계 인자 없음)로 표현되지 않으므로 결국 시그니처를
  넓혀야 한다. 셋째, `ellipse` 는 `kind:'ellipse'` 요소의 "상자에서 나온 온전한 타원" 이라는
  역할을 이미 갖고 있고, 그 역할에 경로 조각이라는 두 번째 역할을 얹으면 읽는 사람이 호출
  자리마다 어느 쪽인지 가려야 한다.
- **`drawImage`** — 001 REQ-05 · 004 REQ-05 의 금지 조항이며 007(벡터 이미지 가져오기)의 몫이다.
  008 은 그 금지에 손대지 않는다.
- **`clip` · `lineJoin` · `lineCap` · `setLineDash`** — 앞의 하나는 이 SPEC 이 쓰지 않고, 뒤의
  셋은 **기하 축이 아니라 스타일 축**이다. 들이면 `ElementStyle` 이 넓어지고 규칙 패치와
  004 의 캐스케이드가 함께 넓어진다. 008 의 주제가 아니다.

**정리하면 산술이 이렇다: 30종 중 23종은 인터페이스 변경 0, 7종이 `bezierCurveTo` 하나를
요구하며, 30종 전부가 선을 온전히 닫으려면 `closePath` 하나를 요구한다. 합이 둘이고, 둘 다
동기다.** 인터페이스의 최소성은 장식이 아니라 하중을 받는 성질이므로(그 최소성이 있어서 렌더
경로 전량이 jsdom 없이 기록 스텁으로 검증된다), 셋째 멤버를 더하려는 설계는 되짚어야 한다.

### 히트 테스트 — 바운딩 박스가 아니다

오늘 `canvasHitTest.hitsElement` 가 아는 것은 넷이다(브리핑은 셋이라 했으나 실측은 넷 —
`text` 가 실측 글자 폭으로 만든 상자를 쓴다): `rect` 는 상자, `ellipse` 는 **타원 방정식**,
`line` 은 점–선분 거리, `text` 는 글자 상자.

경로의 판정을 **바운딩 박스로 두는 안을 기각한다.** 그 기각의 근거는 새로 지어낼 필요도 없다 —
같은 파일이 타원에 대해 이미 적어 두었다: *"박스 모서리의 빈 곳을 눌러도 잡히면 겹쳐 놓은
요소의 선택이 눈에 보이는 그림과 어긋난다."* 별의 오목한 사이, 십자의 겨드랑이, 화살표 꼬리
양옆은 그 문장이 말하는 바로 그 빈 곳이며, 카탈로그 30종 가운데 그런 오목 지역을 가진 것이
**12종**이다.

**채택 — 명령 목록을 평탄화한 폴리라인 위에서 판정한다.**

```
잡힌다 ⟺ (다각형 내부인가: nonzero winding)  또는  (어느 변까지의 거리 ≤ max(선 두께/2, 6px))
```

**이 결정이 만드는 것 하나를 이름으로 적는다 — 경로의 소비자가 둘이 된다.** 렌더는 진짜 3차
베지어를 그리고, 히트는 평탄화한 폴리라인을 훑는다. 이 저장소가 "두 번째 측정원을 만들지
않는다" 로 여러 번 막아 온 형상과 **같은 부류**이므로, 갈라짐을 **수로 묶는다**:

- 단일 출처는 **명령 목록**이고, 두 소비자는 **같은 투영 함수**(`projectPathPoints`)를 지난다.
  다른 것은 마지막 한 걸음(곡선을 그대로 그릴 것인가, 잘게 나눌 것인가)뿐이다.
- 평탄화 허용 오차 `FLATTEN_TOLERANCE_PX = 0.5` 는 집기 여유 `HIT_TOLERANCE_PX = 6` 의
  **1/12** 이다. 즉 렌더와 히트의 최대 어긋남은 사용자가 이미 받고 있는 여유의 8%보다 작으며,
  **어긋남이 여유보다 커지는 순간 그것은 결함이 아니라 상수의 잘못**이다(불변식 J4).

**기각한 안 — `ctx.isPointInPath`.** 브라우저가 정확히 이 판정을 해 준다. 그러나
`canvasHitTest.ts` 는 머리말에서 **"DOM 무의존이다 — `document`/`window`/
`CanvasRenderingContext2D`/`measureText` 를 참조하지 않는다"** 를 계약으로 못박았고, 그 계약
덕에 히트 판정 전량이 jsdom 없이 단위 시험된다. 게다가 판정 때마다 경로를 **다시 발행**해야
하므로 발행 자리가 둘이 된다. 값이 맞지 않는다.

**비용은 어디에 붙는가.** 평탄화는 **프레임당이 아니라 포인터 사건당** 1회다 — 오늘의 선형
순회(가정 A10 · 위험 R9)와 같은 축이며, 공간 색인도 캐시도 도입하지 않는다.

#### 이 절의 적용 범위 — **점 판정**이다 (0.2.0 정정)

이 절의 제목("바운딩 박스가 아니다")은 오늘 읽으면 **저장소 전체의 규율**처럼 들린다. 그렇지
않다. **이 절은 한 점에 무엇이 걸리는가**에 대한 결정이며, 그 결정의 근거 두 줄(오목한 지역의
빈 곳을 눌러도 잡히면 그림과 어긋난다 · 평탄화 오차가 집기 여유의 1/12 이다)은 **점**에 대해
참이다.

**004 0.4.0 이 그 이웃에 사각 판정을 세웠다** — `canvasMarquee.ts`(REQ-09 · 영역 선택). 그
모듈은 **한 사각형에 무엇이 통째로 드는가**를 답하고, **의도적으로 잉크가 아니라 윤곽선 상자를
본다.** 008 의 결정과 정반대로 보이지만 **모순이 아니다.**

| | 점 판정(`canvasHitTest`) | 사각 판정(`canvasMarquee`) |
|---|---|---|
| 묻는 것 | 이 점에 무엇이 걸리는가 | 이 사각형에 무엇이 통째로 드는가 |
| 재는 것 | **잉크**(평탄화한 폴리라인) | **윤곽선 상자** |
| 여유 | 집기 여유 `HIT_TOLERANCE_PX` 로 **부풀린다** | **더하지 않는다**(더하면 경계에 걸친 것이 끌려온다) |
| 판정 횟수 | **포인터 사건당 1회**(가정 A10) | **손이 움직이는 내내** |
| 그룹을 잡는 법 | **부품으로**(004 REQ-08) | **제 상자로**(004 REQ-09) |

**두 모듈이 다른 자를 쓰는 것은 정확도의 타협이 아니라 판정 빈도의 차이에서 나온다.** 008 이
제 비용을 "포인터 사건당 1회" 로 못박았는데 마키가 같은 자를 쓰면 그 예산이 한 자릿수
곱해진다 — 008 이 `ctx.isPointInPath` 를 기각하며 "판정 때마다 경로를 다시 발행해야 한다" 를
근거로 든 것과 **같은 종류의 셈**이다.

**그리고 여유(`HIT_TOLERANCE_PX`)를 두 뜻으로 읽지 않기 위해 두 판정이 한 파일에 살지
않는다** — 점 판정은 "잡을 수 있는가" 라 여유를 더해 **부풀리고**, 사각 판정은 "완전히
들었는가" 라 여유를 더하면 **경계에 걸친 것까지 끌려온다.** 같은 상수가 반대 방향으로 쓰인다.

**008 은 사각 판정을 소유하지 않는다**(004 의 주제다). 이 절이 적는 것은 **제 규율이 어디까지
말하는가** 하나다 — **범위를 밝히지 않은 규율은 이웃 모듈에 대해 거짓이 된다.**

### 경로 자료는 값인가 참조인가 — 값이다

카탈로그에서 도형을 놓을 때 **명령 목록을 config 에 복사해 넣을 것인가**, `catalog_id` 만 적고
렌더가 코드에서 찾아 쓸 것인가.

**채택 — 복사(값).** 004 가 스탬핑을 고른 그 결정을 그대로 따른다. 이유 넷:

1. **결손 참조라는 실패 모드가 생기지 않는다**(004 의 근거 2 와 같다). 참조라면 관용 파서가
   "정의를 못 찾은 경로" 정책을 발명해야 한다.
2. **대시보드는 살아 있는 도면이 아니라 문서다**(004 의 근거 3). 카탈로그를 고쳐도 이미 놓인
   도형은 조용히 달라지지 않는다.
3. **한 패널 안에 두 배치 의미를 만들지 않는다.** 004 가 값이고 008 이 참조면 사용자는 "어느
   도형이 앱 갱신에 따라 바뀌는가" 를 외워야 한다.
4. **스크래치패드가 그 형상을 강제한다.** 사용자가 조립한 항목에는 `catalog_id` 가 없다. 참조
   방식이면 한 항목 안에 참조와 값이 섞여 파서가 정책을 둘 갖게 된다.

**대가: config 가 커진다.** 다각형 한 개 ≈ 8~12 점 ≈ **150~250B**(001 요소 한 건과 같은
자릿수), 곡선 도형 한 개 ≈ **300~500B**. 대시보드 snapshot PUT 상한은 **256KB**이고 그 예산은
**대시보드 전체가 공유한다**(`internal/api/handler/dashboard.go:44`, 실측). 가정 A4 가 이
축을 정량으로 다루고 인수 기준 AC-E5 가 실측으로 확인한다.

**출처 기록은 남기되 렌더는 읽지 않는다.** 경로 요소는 `catalog_id` 를 들고 있고, 그 값은
**요소 목록에서 이름을 보이는 데에만** 쓴다("구름" vs 정체 모를 "경로"). 값이 없거나 카탈로그에
없는 id 여도 그림은 완전하다 — 004 REQ-02 의 `symbol` 출처 기록과 같은 규율이다.

### 경로 로컬 좌표는 정수다 — 0..10000 격자

경로 명령의 좌표는 **요소 상자 안의 로컬 좌표**여야 한다(그래야 상자를 늘리면 도형이 함께
늘어난다 — 004 가정 A7 과 같은 규칙). 두 안이 있었다.

**기각 — 정규화 분수(0..1).** `canvasConfig.ts` 의 좌표 규율은 오늘 **하나**다: 유한하면
정수로 반올림, 아니면 폴백(`coordinate()`). 분수를 들이면 그 파일에 **두 번째 수치 규율**이
생기고, 머리말이 못박은 "여기서 죄는 것은 자릿수뿐" 이 거짓이 된다. 둘이 되는 규율은 갈라진다.

**채택 — `PATH_LOCAL_EXTENT = 10000` 격자 위의 정수.** 기존 `coordinate()` 를 그대로 재사용한다.
양자화 오차는 `상자 길이 ÷ 10000` 캔버스 단위다 — 100 단위짜리 도형에서 **0.01 단위**로 캔버스
자체의 양자(1 단위)보다 **두 자릿수 작다**. JSON 크기도 정수가 더 작다(`552` 3자 vs `0.5523`
6자).

**로컬 좌표는 clamp 하지 않는다.** 말풍선의 꼬리처럼 상자 밖으로 삐져나가는 형상이 있으며,
캔버스 밖 저술을 자르지 않는 그 규율(가정 A5)과 같은 이유다.

**그리고 이것은 캔버스 좌표가 아니다.** 격자에 붙지 않고, 정렬의 대상이 아니며, 무엇보다
**`patchNodeGeometry` 를 지나지 않는다** — 그 함수가 쓰는 것은 요소의 `geometry`(상자)뿐이다.
경로 명령을 기하 쓰기 통로로 넣는 설계는 불변식 J2 를 깬다.

### 스크래치패드는 어디에 사는가

**저장 항목은 그 사람이 만든 저술이지 대시보드의 내용이 아니다.** 네 자리를 검토했다.

**기각 — 패널 config.** 셋이 걸린다. (1) **되쓰지 못한다** — 항목이 그 패널 안에만 있으므로
다른 캔버스 패널에서 꺼낼 수 없고, 그러면 "재사용 재료" 라는 목적이 사라진다. (2) **남의
예산을 먹는다** — 256KB 는 대시보드 전체가 공유하는데 스크래치패드는 화면에 그려지지도 않는
도구 상태다. (3) **대시보드를 **보는** 사람에게 내려간다** — 남의 작업 서랍이 뷰어의 페이로드에
실린다. 006 이 불변식 I19·I20 을 세우게 만든 그 부류의 경계 흐림이다.

**기각 — 대시보드 snapshot.** (1)(2) 는 같고, 하나가 더 있다: 서버에 저장되는 순간 그것은
**개인 서랍이 아니라 그 대시보드를 여는 모두의 공용 카탈로그**가 된다. 그것은 다른 요구이며,
지금 정하면 되돌리기 어렵다(§이연 — 공용 카탈로그).

**기각 — 사용자별 서버 저장(신규 엔드포인트 또는 사용자 설정 테이블).** 기기를 옮겨도 따라오는
유일한 안이다. 그러나 004 · 005 · 006 이 나란히 지켜 온 **백엔드 변경 0** 을 깬다. 그 값을
이 SPEC 의 크기 안에서 치를 이유가 없다 — 되돌릴 수 없는 결정이 아니라 **나중에 얹을 수 있는**
결정이기 때문이다(§이연).

**기각 — 저장하지 않음(세션 메모리).** draw.io 의 스크래치패드는 남는다. 새로고침 한 번에
조립한 것이 사라지면 그 자리는 서랍이 아니라 임시 접시다.

**채택 — 기기 지역 영속(`localStorage`), 전용 store 와 전용 키(`xflow-canvas-scratchpad`).**
이 저장소에는 이미 같은 기구가 돌고 있다 — `uiStore` 가 zustand `persist` 로 `xflow-ui` 키에
쓰며, 그 `partialize` 주석이 스스로 범위를 못박아 두었다: **"기기별 환경설정만 영속한다."**

**그 store 에 얹지 않고 옆에 세우는 이유 둘.** (1) 스크래치패드는 **환경설정이 아니라 저술**
이므로, 얹는 순간 그 파일이 스스로 그은 경계가 흐려진다. (2) `xflow-ui` 블롭은 부팅 때 테마를
읽으려고 **매번 통째로 역직렬화된다.** 도형 서랍을 그 안에 넣으면 첫 그림이 서랍 크기만큼
늦어진다. 서랍은 도크가 열릴 때 처음 읽히면 된다.

**대가를 정확히 적는다.** (1) **다른 브라우저 · 다른 기기로 따라가지 않는다.** (2) 브라우저
저장소를 비우면 **사라진다.** (3) 시크릿 창에서는 창을 닫을 때 사라진다. 셋 다 사용자에게
보이는 성질이므로 화면이 말해야 한다(REQ-06 · AC-06).

**예산.** `localStorage` 는 출처당 대략 5MB 이고 그 몫을 `xflow-ui` 와 나눠 쓴다. 항목 수 상한
**50**, 총 바이트 상한 **256KB** 를 두고, 넘으면 **거절하고 말한다** — 조용히 버리거나 오래된
것을 몰래 지우지 않는다. 이 저장소가 침묵을 결함으로 다뤄 온 규율 그대로다.

### 끌어놓기는 어느 공간에서 판정하는가

오버레이는 누름을 받으면 **루트에 포인터를 잡는다**(`host.setPointerCapture?.(event.pointerId)`).
그래서 손이 스테이지 밖 도크 위로 가도 `pointermove`/`pointerup` 은 **여전히 오버레이로 온다** —
도크의 DOM 은 그 사건을 **받지 못한다.** 이것이 이 기능의 형상을 정한다.

- **놓임 판정은 오버레이의 `pointerup` 안에서, 클라이언트 좌표로** 한다: 드롭 존 노드의
  `getBoundingClientRect()` 안에 `clientX/Y` 가 드는가. **스테이지 산술이 아니다.**
  `projection` 을 보지 않고, `stage.width` 로 나누지 않는다. 그러므로 **좌표 공간을 넘는
  자리는 여전히 `stagePoint` 하나뿐**이다(불변식 J7).
- **드롭 존의 강조는 드롭 존 자신이 입는다.** 포인터가 도크 위에 있음을 오버레이가 알고 내려
  보낸다. **캔버스 위에는 아무것도 그리지 않는다** — 그 이유는 아래 §I23 이다.
- **스크래치패드는 복사이지 이동이 아니다.** 드롭이 성립하면 끌던 요소들의 기하를 드래그
  시작값(`drag.bases`)으로 **되돌린다.** 되돌림도 `patchNodeGeometry` 를 지난다(쓰기 통로는
  하나다). 되돌리지 않으면 서랍에 넣었을 뿐인데 캔버스의 도형이 도크 쪽으로 밀려나 있다.
- **끌기에는 끌지 않는 등가물이 있다.** WCAG 2.2 SC 2.5.7(Dragging Movements)은 끌기로만 되는
  조작을 금지한다. 그래서 도크에 **"선택 항목 저장" 단추**가 함께 서며, 그것은 편의가 아니라
  **요구**다(REQ-03).

### I23 — 그려지는 자리에 손잡이가 닿는가

006 0.7.0 이 세운 원리다: **표시 층이 그려지는 자리에는 그 층을 다스리는 손잡이가 닿아야
한다.** 006 은 표시 층 셋을 조건 없이 그리면서 컨트롤 전부를 `dockHost !== null` 뒤에 두어 그
원리를 깼고, **어떤 시험도 울리지 않았다 — 두 조건이 같은 자리에서 비교된 적이 없었기 때문**
이다. 008 은 그 함정을 세 갈래로 대조한다.

1. **팔레트와 스크래치패드는 표시 층이 아니라 컨트롤이고, 도크에만 산다.** 도크가 없으면
   **드롭 존도 없고 목록도 없다.** 층과 손잡이의 렌더 조건이 **같은 한 값**이므로 I23 은
   **형상으로** 지켜진다 — 새 떠 있는 줄을 세울 이유가 없다.
2. **그래서 캔버스 위에 드래그 강조를 그리지 않는다.** 그것을 그리면 대시보드(도크 없음)에서
   포인터를 끌 때 **다스릴 수 없는 표시 층**이 생긴다. 006 이 배달한 결함과 정확히 같은
   형상이다.
3. **놓인 경로 도형은 새 비대칭을 만들지 않는다.** 경로는 rect/ellipse/line 과 **같은 컨트롤**
   (선택 · 드래그 · 8핸들 · 목록 편집기 · 정렬 · 순서)로 다스려지며, 그 컨트롤은 006 M7 이
   작업 영역까지 넓혀 둔 그대로 대시보드에서도 닿는다. 팔레트가 대시보드에 없는 것은 006
   0.7.0 이 다섯 중 넷에 대해 **그대로 두기로 결정한** 기존 비대칭이며, 008 은 그것을 **넓히지도
   좁히지도 않는다.**

이 셋을 **시험이 비교하게** 만든다(시험 규율 D10 · AC-E9).

### 범위 — 무엇이 들어오고 무엇이 안 들어오는가

**들어온다:** `path` 원시형 · 카탈로그 30종(일반 10 · 기본 12 · 화살표 8) · 접히는 묶음 팔레트 ·
스크래치패드(저장 · 놓기 · 이름 · 지우기) · 기기 지역 영속.

**들어오지 않는다:**

- **정점 편집기**(정점을 끌고, 점을 넣고 빼고, 베지어 손잡이를 다루는 일). 사용자가 고르지
  않았다. §이연이 값을 적는다.
- **순서도 · ER · UML 묶음.** 사용자가 물렸다. §기각한 안이 이유를 적는다.
- **연결선.** 위 셋의 전제 조건이며 별개의 주제다(§이연).
- **004 의 `group`**, 부품 단위 규칙, 캐스케이드. 004 의 주제다.
- **영역 선택(마키).** 004 의 주제다(004 REQ-09 · 0.2.0 추가) — 008 이 세운 §히트 테스트는
  **점 판정**에 대한 결정이며, 사각 판정은 그 이웃에 따로 선다(§이 절의 적용 범위).
- **SVG 가져오기.** 007 의 주제다.
- **취소/되돌리기.** 이 패널에 오늘 없으며 008 이 만들지 않는다(위험 R8).

### 기각한 안 — 순서도 · ER · UML (사용자가 물린 것을 왜 "행이 더 많은 목록" 으로 보지 않는가)

사용자에게 여섯 묶음을 내밀었고 셋(일반 · 기본 · 화살표)을 골랐다. **나머지 셋은 30종을 60종으로
늘리는 일이 아니다.**

순서도의 본체는 상자가 아니라 **상자 사이의 연결선**이다. ER 의 본체는 **관계(선 + 카디널리티
표식)** 이고, UML 의 본체는 **관계(상속 삼각형 · 합성 마름모 · 점선 의존)** 이다. 그 셋은
전부 **두 도형 사이의 관계를 나르는 객체**를 요구하며, 그 객체는:

- 도형 위에 **접합점(anchor)** 을 가져야 하고,
- 도형을 옮기면 **따라 붙어 다시 경로를 잡아야** 하며,
- 화살촉 · 선 종류 · 라벨을 제 모델로 가져야 한다.

**이 SPEC 은 그중 아무것도 주지 않는다.** 연결선 없이 순서도 상자만 주면 사용자는 상자들을
`line` 으로 잇게 되고, **그 선은 상자를 옮겨도 따라오지 않는다.** 그것은 반쯤 되는 기능이
아니라 **잘못된 약속**이다. 그래서 그 셋은 연결선 SPEC 뒤로 미룬다(§이연).

### 이연 — 무엇을 미루고, 미룬 것이 무엇을 치를지

**(1) 경로 정점 편집기 (제안했고 사용자가 고르지 않았다).** 미룬 것의 값을 적는다.

- **핸들 모델이 바뀐다.** 오늘 `CanvasHandleId` 는 문자열 리터럴 합집합
  (`'nw'|'n'|…|'p1'|'p2'|'font'`)이고 `handlesFor(kind)` 는 **고정 목록**을 돌려준다. 정점
  핸들은 개수가 도형마다 다르므로 그 합집합이 **매개변수를 가진 id**(`vertex:17`)로 바뀌어야
  하고, 그러면 `handleRole` · `handleDragState` · `resizeBox`/`resizeLine` 의 분기 전부가 그
  형상 위에 다시 선다.
- **제어점 손잡이가 정점당 둘 더 붙는다.** 그러면 "부드러운 점 / 꺾인 점" 개념이 필요하고, 그
  개념은 명령 목록에 **저장 필드 하나를 더 요구한다.**
- **점을 넣고 빼는 몸짓에 키보드 등가물이 없다.** SC 2.5.7 이 그 등가물을 요구하는데,
  "선분 위 어느 지점에 점을 넣는가" 를 키보드로 말하는 법은 오늘 이 패널에 없다.
- **되돌리기가 없다.** 도형 하나를 옮기는 실수와 윤곽을 망가뜨리는 실수는 회복 비용이 다르다.

**008 이 그 SPEC 을 위해 해 두는 일 하나:** 명령 목록을 **참조가 아니라 값으로** config 에
넣기로 한 결정(위)이 곧 정점 편집기의 전제다. 참조였다면 편집기가 먼저 "카탈로그에서 떼어내기"
를 발명해야 했다. 예약 번호 **SPEC-CANVAS-009**(산문 예약, 파일 없음).

**(2) 연결선.** 순서도 · ER · UML 의 전제. 예약 번호 **SPEC-CANVAS-010**(산문 예약, 파일 없음).

**(3) 공용/사용자별 카탈로그.** 기기 지역 저장을 서버로 올리는 일. 008 의 저장 형상이
`CanvasElement[]` + 상자이므로 그대로 전송 가능한 값이며, 올릴 때 정해야 하는 것은 **자료가
아니라 소유권**(개인인가 대시보드인가 조직인가)이다. 그 질문은 백엔드 변경을 부르므로 별도
SPEC 이다.

### 백엔드 변경 0 · config 스키마 무변경(형상)

- 카탈로그는 **코드 내장 TS 모듈**이다. 배치 결과는 패널 `config` 안의 요소 하나이며, `config`
  는 Go 쪽에서 불투명 JSON(`json.RawMessage`)이다. **신규 엔드포인트도, 전송 계층 변경도 없다.**
- `config` 의 **필드 이름은 하나도 늘지 않는다.** `elements[]` 원소에 `kind: 'path'` 갈래가
  더해질 뿐이며, 그것은 001 이래 관용 파서가 다루는 축이다.
- 스크래치패드는 config 에 **들어가지 않는다.** 그러므로 대시보드 페이로드는 항목을 저장해도
  **한 바이트도 늘지 않는다**(불변식 J5 · AC-E8).

## 요구사항 (Requirements — EARS)

### REQ-01 — 경로 원시형과 그 자료 모델 (Ubiquitous)

시스템은 **항상** 다섯 번째 요소 종류 `path` 를 두고, 그 요소를
`{ id, kind:'path', geometry: BoxGeometry, path: PathCommand[], catalog_id?, …공통필드 }` 로
두어야 한다. 공통 필드(`style`·`text`·`binding`·`rules`·`tween`·`numeric`·`decimals`·`unit`)는
**001 의 것과 같아야 하며**, 새 필드를 만들지 않아야 한다.

시스템은 **항상** 경로 명령을 네 종류(`M`·`L`·`C`·`Z`)로만 두고, 그 좌표를 **요소 상자 로컬
정수**(공칭 범위 0..`PATH_LOCAL_EXTENT`)로 두어야 한다. 로컬 좌표를 **clamp 하지 않아야 한다**.

시스템은 **항상** `CanvasElement` 를 넓히되 `RectElement`/`EllipseElement`/`LineElement`/
`TextElement` 의 정의를 **바꾸지 않아야 한다**.

시스템은 **항상** `DrawContext2D` 에 **`closePath` 와 `bezierCurveTo` 만** 더해야 하며, 그
인터페이스에 **비동기 멤버 · 이미지 멤버 · 폰트 로딩 멤버를 두지 않아야 한다**.

시스템은 **항상** 경로 로컬 → 스테이지 px 투영을 **한 함수**(`projectPathPoints`)로 두고,
렌더와 히트 테스트가 **그 함수를 함께** 써야 한다.

시스템은 **항상** `catalog_id` 를 표시·감사용으로만 두고 **렌더 경로가 그 값을 읽지 않아야
한다** — 결측이거나 모르는 값이어도 그림은 완전해야 한다.

### REQ-02 — 카탈로그에서 도형을 놓는다 (Event-Driven)

**WHEN** 사용자가 팔레트의 카탈로그 도형 하나를 누르면 **THEN** 시스템은 그 정의의 명령 목록을
**독립된 사본**으로 실은 `path` 요소 하나를 만들어 `elements[]` **끝**에 덧붙여야 한다(끝 =
맨 위).

**WHEN** 요소가 만들어지면 **THEN** 시스템은 id 발급 · 계단 오프셋 · 씨앗 스타일을
**`canvasElementFactory` 의 그 한 입구**로 처리해야 한다 — 팔레트가 자기 생성 규칙을 갖지
않아야 한다(002 가정 A7).

**WHEN** 카탈로그 도형이 놓이면 **THEN** 그 요소는 **일반 요소와 구별 없이** 편집 가능해야
한다: 선택 · 드래그 · 8핸들 크기 조절 · 정렬 · 붙임 · 순서 · 목록 편집기의 기하·스타일·문구·
바인딩·규칙 전부가 rect 와 같은 수단이어야 한다.

**WHEN** 도형을 놓은 뒤 카탈로그 정의가 바뀌더라도 **THEN** 시스템은 이미 놓인 요소를 갱신하지
**않아야 한다**(값이지 참조가 아니다).

**WHEN** 팔레트가 그려지면 **THEN** 카탈로그는 **묶음별로** 보여야 하고, 각 칸은 **실제 렌더
경로로 그린 미리보기 + i18n 이름**이어야 한다 — 별도 썸네일 이미지도, 별도 렌더 경로도 만들지
않아야 한다.

### REQ-03 — 스크래치패드에 저장한다 (Event-Driven)

**WHEN** 사용자가 캔버스에서 고른 요소들을 끌어 도크의 드롭 존 안에서 손을 떼면 **THEN**
시스템은 그 선택의 **사본**을 스크래치패드 항목 하나로 저장하고, 끌던 요소들의 기하를
**드래그 시작값으로 되돌려야 한다**(복사이지 이동이 아니다).

**WHEN** 되돌림이 일어나면 **THEN** 그 쓰기는 **`patchNodeGeometry` 를 지나야 한다** — 두 번째
쓰기 통로를 만들지 않아야 한다.

**WHEN** 사용자가 도크의 "선택 항목 저장" 단추를 누르면 **THEN** 시스템은 끌기와 **같은 결과**를
내야 한다(WCAG 2.2 SC 2.5.7 — 끌기로만 되는 조작을 두지 않는다).

**WHEN** 항목이 저장되면 **THEN** 시스템은 그 묶음의 **좌상단(캔버스 단위)** 을 함께 저장해야
한다 — 되놓을 때 요소 사이의 상대 배치를 그대로 살리기 위해서다.

**WHEN** 선택이 비어 있으면 **THEN** 저장 단추는 **쓸 수 없어야** 하고, 드롭은 항목을 만들지
않아야 한다.

### REQ-04 — 스크래치패드에서 놓는다 (Event-Driven)

**WHEN** 사용자가 스크래치패드 항목을 캔버스 위로 끌어 손을 떼면 **THEN** 시스템은 저장된
요소들의 사본을 **놓인 지점을 좌상단으로** 하는 델타만큼 옮겨 `elements[]` 끝에 **순서대로**
덧붙여야 한다.

**WHEN** 격자 붙임이 켜져 있으면 **THEN** 놓는 자리는 **기존 붙임 계산(`snapDelta`)** 을 써야
한다 — 두 번째 붙임 규칙을 만들지 않아야 한다.

**WHEN** 사용자가 항목의 "놓기" 단추를 누르면 **THEN** 시스템은 **계단 오프셋**(`seedOffset`)
자리에 같은 방식으로 놓아야 한다(SC 2.5.7 등가물).

**WHEN** 놓기가 끝나면 **THEN** 시스템은 **새로 만들어진 요소 id 전부를 선택으로 세워야 한다** —
그래야 놓자마자 한 덩어리로 끌린다.

**WHEN** 항목을 놓으면 **THEN** 요소 id 는 **현재 배열 안에서 새로 발급되어야 한다**(저장된 id
를 그대로 쓰면 중복이 생기고, 파서는 중복 id 를 먼저 온 것으로 접는다).

### REQ-05 — 저장 자리와 예산 (State-Driven)

**IF** 스크래치패드 항목이 저장되면 **THEN** 그 자료는 **기기 지역 저장소**(전용 `persist` 키)
에 놓여야 하며, 패널 `config` · 대시보드 snapshot · 서버 어디에도 놓이지 **않아야 한다**.

**IF** 항목 수가 **50** 을 넘거나 총 바이트가 **256KB** 를 넘으면 **THEN** 시스템은 저장을
**거절하고 그 사실을 화면에 말해야 한다** — 오래된 항목을 몰래 지우거나 조용히 실패하지
않아야 한다.

**IF** 저장소에 쓸 수 없으면(시크릿 창 · 용량 초과 · 접근 불가) **THEN** 시스템은 예외를 밖으로
던지지 않고 그 사실을 화면에 말해야 하며, **캔버스의 그림과 편집은 그대로 동작해야 한다**.

**IF** 저장된 자료가 손상되었으면 **THEN** 관용 파서가 **읽을 수 있는 항목만** 살리고 예외를
던지지 않아야 한다(001 파서 계약과 같은 규율).

**IF** 스크래치패드 항목이 하나도 없으면 **THEN** 도크는 안내 문구 하나만 보여야 하고, 캔버스
표면에는 **아무것도 더 그리지 않아야 한다**.

### REQ-06 — 묶음 · 이름 · 미리보기 (Optional)

가능하면 시스템은 팔레트의 카탈로그 묶음을 **접고 펼 수 있게** 하고, 그 접힘 상태를 기기 지역
에 기억해야 한다. 기억하지 못해도 기능은 성립해야 한다.

가능하면 시스템은 스크래치패드 항목의 **이름을 사용자가 고칠 수 있게** 해야 한다. 이름이
없으면 자동 이름을 보여야 한다.

가능하면 시스템은 스크래치패드가 **기기 지역 저장**임을 화면에서 알려야 한다 — 다른 기기로
따라가지 않는다는 사실은 사용자가 알아야 되돌릴 수 있는 성질이다.

가능하면 시스템은 항목 미리보기를 **실제 렌더 경로**(`drawElements`)로 그려야 한다.

### REQ-07 — 견고성과 금지 조항 (Unwanted)

시스템은 `DrawContext2D` 에 **비동기 멤버를 두지 않아야 한다** — 001 REQ-05 의 유휴 정지가
그 금지의 근거이며, 본 SPEC 은 그 금지에 손대지 않는다.

시스템은 경로 명령 목록을 **기하 쓰기 통로(`patchNodeGeometry`)로 쓰지 않아야 한다**.

시스템은 **두 번째 좌표 공간 변환 함수를 만들지 않아야 한다** — 놓임 판정은 **클라이언트 좌표
containment** 이며 `projection`·`stage` 를 보지 않아야 한다.

시스템은 경로 히트 판정을 **바운딩 박스로 두지 않아야 한다**.

시스템은 `CanvasProjection` 을 **세 칸으로 넓히지 않아야 한다**.

시스템은 스크래치패드 때문에 **캔버스 표면에 새 표시 층을 그리지 않아야 한다** — 드래그 강조는
드롭 존 자신이 입는다(I23).

시스템은 경로 명령 수를 **상한(`MAX_PATH_COMMANDS`)으로 죄어야 한다** — 손상되거나 거대한
목록 하나가 한 프레임을 삼키지 않아야 한다.

시스템은 손상된 경로 요소를 **버리지 않아야 한다** — 명령 목록이 성립하지 않으면 **씨앗 경로**
(단위 사각형)로 대체해 사용자가 화면에서 보고 고칠 수 있게 해야 한다(001 의 기하 손상 정책과
같은 규율: 버리는 것은 정체성이 없을 때뿐이다).

시스템은 `path` 를 **종류 바꾸기 선택지에 넣지 않아야 한다**(무엇으로부터 경로를 지어낼지에
대한 답이 없다). 경로에서 다른 종류로 바꾸는 길은 남아야 한다.

시스템은 `PanelSettingsDialog.tsx` 를 **자라게 하지 않아야 한다**(006 불변식 I7).

### REQ-08 — 후속 SPEC 전방 호환 (Ubiquitous)

시스템은 **항상** 스크래치패드 항목의 몸체를 `CanvasElement[]` 로 두어, **004 의
`GroupElement.parts` 와 같은 타입**이 되게 해야 한다 — 004 가 착륙하면 "그룹으로 놓기" 가
저장 형상을 바꾸지 않고 더해질 수 있어야 한다.

시스템은 **항상** 경로 명령 목록을 **config 안의 값**으로 두어, 009(정점 편집기)가 참조를 떼어
내는 일부터 시작하지 않아도 되게 해야 한다.

시스템은 **항상** `CanvasHit` 의 `partId` 자리를 **비워 두어야 한다**(004 의 몫).

시스템은 **항상** 경로 요소가 **출력 영역 밖에도 놓일 수 있게** 해야 한다(006 이 다른 노드에
대해 못박은 그 성질과 같다).

## 명세 (Specifications)

### 자료 모델 — `canvasConfig.ts` 가 넓어지는 만큼만

```
// 001 그대로 — 이름·형상 불변.
RectElement | EllipseElement | LineElement | TextElement

// 008 이 더하는 것.
PathCommand =
  | { c: 'M'; x: number; y: number }
  | { c: 'L'; x: number; y: number }
  | { c: 'C'; x1: number; y1: number; x2: number; y2: number; x: number; y: number }
  | { c: 'Z' }

PathElement extends CanvasElementBase {
  kind: 'path'
  geometry: BoxGeometry          // 정수 캔버스 단위. rect 와 **같은** 형상이다.
  path: PathCommand[]            // 요소 상자 로컬 정수(공칭 0..PATH_LOCAL_EXTENT). clamp 없음.
  catalog_id?: string            // 표시·감사용. 렌더는 읽지 않는다.
}

CanvasElement = RectElement | EllipseElement | LineElement | TextElement | PathElement

// 상수
PATH_LOCAL_EXTENT  = 10000   // 로컬 격자. 상자 한 변이 이 값에 대응한다.
MAX_PATH_COMMANDS  = 256     // 한 요소의 명령 상한.
DEFAULT_PATH: PathCommand[]  // 씨앗 경로 = 단위 사각형(M·L·L·L·Z).
```

**`geometry` 가 `BoxGeometry` 인 것이 이 모델의 절반이다.** 그래서 8핸들 크기 조절 · 정렬 ·
붙임 · 무리 이동 · 방향키 미세 이동이 **한 줄도 바뀌지 않고** 경로에 적용된다 — 그 전부가
`BoxGeometry` 위에 이미 서 있기 때문이다.

### 파서 — 001 의 규율을 그대로 물려받는다

- `parseElement` 의 `kind` 화이트리스트에 `'path'` 를 **더한다**(이 한 줄이 없으면 저장된 경로
  요소가 **읽을 때 조용히 사라진다** — 008 에서 가장 나쁜 실패이며, 그래서 이 줄이 시험 규율
  D1 의 첫 표적이다).
- `path` 배열이 아니면 → **씨앗 경로**. 유효 명령이 하나도 남지 않아도 → **씨앗 경로**.
  첫 유효 명령이 `M` 이 아니면 → 앞에 `M(0,0)` 을 **세우지 않고** 씨앗 경로로 떨어뜨린다(반쯤
  성립하는 경로를 지어내면 화면에 정체 모를 형상이 나온다).
- 명령 좌표는 **`coordinate()` 재사용**(유한하면 반올림, 아니면 그 명령을 버린다). 새 수치
  규율을 만들지 않는다.
- 명령 수가 `MAX_PATH_COMMANDS` 를 넘으면 **앞에서부터 상한까지만** 살린다(전부 버리면 도형이
  사라진다).
- 모르는 명령 문자는 **그 명령만** 버린다.
- `catalog_id` 는 `optionalString` 재사용. 결측·손상은 미지정이다.
- **상위 호환**: 001~006 이 쓴 config 에는 `path` 노드가 없으므로 아무 변화 없이 읽힌다.
- **하향 호환**: 008 이 쓴 config 를 옛 파서가 읽으면 경로 요소는 **조용히 버려지고** 나머지는
  정상 렌더된다. 앱과 파서가 함께 배포되므로 실사용 경로는 아니지만 성질로서 명시한다.

### 투영 — 한 함수, 두 소비자

```
projectPathPoints(path: readonly PathCommand[], box: PxBox): readonly PxPathCommand[]
```

- `box` 는 `projectBox(el.geometry, proj)` 의 결과다 — **경로가 스테이지를 다시 재지 않는다.**
- 로컬 → px: `px = box.x + local.x × box.w ÷ PATH_LOCAL_EXTENT`(y 도 같다). 나눗셈이 나타나는
  자리는 **이 함수 하나**여야 한다(불변식 J3).
- 음수 크기 상자(001 이 읽기 경로의 견고성으로 허용한다)는 그대로 통과한다 — 좌표가 뒤집힐
  뿐 NaN 이 되지 않는다.
- **할당 비용을 숨기지 않는다.** 요소당 프레임당 배열 하나 + 점 N개를 만든다(오늘
  `projectBox` 가 요소당 상자 하나를 만드는 것의 N배). 받아들이는 근거는 둘이다: 단일 출처가
  미세 최적화보다 무겁고, **유휴 정지 때문에 이 비용은 트윈·드래그 중에만 발생한다**(001
  REQ-05). 이 성질이 깨지면 비용 논거도 함께 깨지므로 AC-E4 가 유휴 정지를 다시 잰다.

### 렌더 — `drawElement.ts` 에 갈래 하나

```
case 'path': {
  const box = projectBox(el.geometry, proj);
  ctx.beginPath();
  for (const cmd of projectPathPoints(el.path, box)) {
    switch (cmd.c) {
      case 'M': ctx.moveTo(cmd.x, cmd.y); break;
      case 'L': ctx.lineTo(cmd.x, cmd.y); break;
      case 'C': ctx.bezierCurveTo(cmd.x1, cmd.y1, cmd.x2, cmd.y2, cmd.x, cmd.y); break;
      case 'Z': ctx.closePath(); break;
    }
  }
  paintFill(ctx, style);
  paintStroke(ctx, style);
  break;
}
```

`paintFill`/`paintStroke` 는 **한 글자도 바뀌지 않는다** — 색 없는 요소를 그리지 않는 규율,
두께 0 을 선 없음으로 읽는 규율이 경로에도 그대로 걸린다. 라벨도 그대로 붙는다(`labelAnchor`
가 경로에 대해 **상자의 중심**을 돌려주도록 갈래를 더한다 — 오늘의 `default:` 는 상자를
기준점으로 읽어 라벨을 **좌상단**에 앉힌다. 시험 규율 D1 의 표적 가운데 하나).

### 히트 테스트 — 평탄화 후 판정

`canvasHitTest.ts` 에 갈래 하나와 순수 도우미 둘을 더한다. **DOM 무의존은 그대로다.**

```
flattenPath(cmds: readonly PxPathCommand[], tol: number): readonly PxPoint[][]
   // 3차 베지어를 재귀 이등분으로 잘게 나눈다. 평탄도 판정은 제어점의 직선 이탈 거리.
   // 부분 경로(subpath)마다 배열 하나. 'Z' 는 그 부분 경로를 닫는다.

hitsPath(subpaths, point, strokeWidth, pad): boolean
   // (nonzero winding 으로 내부인가) 또는 (어느 변까지 거리 ≤ max(strokeWidth/2, pad))
```

- `FLATTEN_TOLERANCE_PX = 0.5`. `HIT_TOLERANCE_PX = 6` 의 **1/12**.
- **열린 경로도 잡힌다** — 내부 판정은 실패하지만 변까지의 거리 판정이 잡는다. 곡선 화살표처럼
  닫히지 않은 도형이 여기에 해당한다.
- **퇴화 처리**: 점이 하나뿐인 부분 경로는 점 거리로 떨어진다(오늘 `distanceToSegment` 가
  길이 0 선분에 대해 하는 그대로다).
- **오목이 곧 이 결정의 시험이다.** 별의 안쪽 각을 누르면 **잡히지 않아야** 하며, 바운딩 박스
  판정은 정확히 그 지점에서만 갈라진다(시험 규율 D6).

### 스크래치패드 — 저장 형상과 사는 곳

```
ScratchpadEntry {
  id: string                 // 기기 안에서 유일. 발급은 저장소의 몫.
  name: string               // 사용자가 고칠 수 있다. 기본은 자동 이름.
  created: number            // epoch ms (프로젝트 규약 — 시각은 언제나 epoch millis)
  origin: { x: number; y: number }   // 저장 시점 묶음의 좌상단(정수 캔버스 단위)
  elements: CanvasElement[]  // 사본. 004 의 GroupElement.parts 와 **같은 타입**(REQ-08)
}
```

- 저장소: 전용 zustand `persist` store, 키 **`xflow-canvas-scratchpad`**.
  `uiStore` 에 얹지 않는 이유는 §스크래치패드는 어디에 사는가.
- 읽기는 **도크가 열릴 때**다(부팅 경로에 얹지 않는다).
- 상한: 항목 **50**, 총 **256KB**. 넘으면 **거절 + 화면 문구**.
- 파서: `parseScratchpad(raw)` 는 예외를 던지지 않는다. 항목 단위로 살리고, 요소는 **001 의
  `parseElements` 를 그대로 재사용한다** — 스크래치패드가 두 번째 요소 파서를 갖지 않는다.

### 저장 · 놓기의 기구

**저장(끌기).** 오버레이의 `pointerup` 안:

1. 드롭 존 노드의 `getBoundingClientRect()` 를 얻는다(노드는 컨텍스트로 받는다 — `dockHost`
   와 같은 방향의 해법이며, 없으면 `null` 이고 그때 이 갈래는 아예 돌지 않는다).
2. `clientX/Y` 가 그 상자 안인가 — **containment 판정. 스테이지 산술 없음**(불변식 J7).
3. 안이면: 선택된 요소들의 **사본**과 그 묶음의 좌상단을 저장소에 넣고, `drag.bases` 로
   **기하를 되돌린다**(`patchNodeGeometry` 경유).
4. 밖이면: 오늘의 확정 경로 그대로.

**저장(단추).** 같은 저장 함수를 부른다. 되돌릴 기하가 없으므로 3 의 뒷줄은 돌지 않는다.
**저장 경로는 하나여야 한다** — 둘이면 "끌어 넣은 것과 단추로 넣은 것이 다르다" 가 생긴다.

**놓기(끌기).** 스크래치패드 항목에서 시작한 포인터는 그 항목이 잡는다. `pointerup` 에서
오버레이 루트의 상자를 얻어 **`stagePoint` 로** 스테이지 좌표를 구하고(같은 함수, 두 번째
호출 자리 — 두 번째 **함수**가 아니다), `unprojectPoint` 로 캔버스 단위로 되돌린 뒤 붙임을
적용한다.

**놓기(단추).** `seedOffset(elements.length)` 자리에 놓는다.

**공통 뒷줄.** id 재발급(`nextElementId` 를 반복 적용) → `elements[]` 끝에 순서대로 덧붙임 →
**만들어진 id 전부를 선택으로**.
