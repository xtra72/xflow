## 기술 스택 (Tech Stack)

- React 19(표면·오버레이는 client 컴포넌트), TypeScript 5.9

- 신규 의존성 **0**, 백엔드 변경 **0**, config 스키마 변경 **0**

## 작업 분해 (Task Decomposition)

### Primary Goal (1차 목표) — 상자 둘과 원점

우선순위 High. 이 단계가 끝나면 **출력 영역 밖의 요소가 화면에 실제로 그려진다** — 사용자
요구 ③ 의 절반(작업)이 여기서 선다.

- **M1. `canvasWorkspace.ts`(신규, TDD 핵심)**: `PANEL_REGION_FIT_RATIO` · `CanvasWorkspaceBox` ·
  `workspaceBox(outer, canvas, step, workspace)`. **DOM 무의존**이므로 jsdom 없이 전량 단위
  시험한다. 두 갈래(편집 꺼짐/켜짐)를 **한 함수가 소유**하며, 꺼짐 갈래는 `stageLattice` 결과를
  그대로 옮겨 담아 오늘의 값과 **완전히 같다**. 원점 정수화 · 가운데 정렬 · 퇴화 전파를 여기서
  못박는다.
- **M2. `CanvasSurface.tsx` 수정(DDD, 행위 보존)**: `workspace?: boolean` prop **하나**
  (기본 `false`). `stageLattice` 직접 호출을 `workspaceBox` 로 갈고, 작업 영역 상자를 지어
  `<canvas>` 를 그 안으로 올리고, `computeBackingSize` 에 작업 영역을 넘기고, `setTransform` 에
  원점을 싣고, 컨테이너에 `overflow-hidden` 을 둔다. **`workspace` 를 넘기지 않으면 002 와
  동작이 완전히 같다** — 이 무동작 보장을 시험으로 **먼저** 못박고 시작한다.
- **M3. `canvasStageGrid.ts` 수정**: `CanvasStageGrid` 에 `origin: StageCell` · `box: StageSize`
  추가. 표면이 채우고, `null` 인 자리(오버레이 단독 렌더)는 `origin = {0,0}` ·
  `box = projection.stage` 로 떨어져 오늘과 같다.
- **M4. `CanvasPanel.tsx` 수정**: `workspace={edit.active}` 한 줄. 자동 맞춤 · 빈 상태 안내 ·
  오버레이 마운트는 **한 글자도 건드리지 않는다.**

### Secondary Goal (2차 목표) — 출력 영역의 표시

우선순위 High. 이 단계가 끝나면 사용자 요구 ③ 이 **전부** 화면에 있다 — 넓은 데서 저술하고,
어디가 패널에 나올지 눈으로 본다.

- **M5. `PanelEditGrid.tsx` 수정(DDD, 행위 보존)**: `offsetX`/`offsetY` 덧붙임 prop(기본 0) →
  `backgroundPosition`. **다섯 패널 무변경**을 문자열 가드로 못박는다.
- **M6. `CanvasEditOverlay.tsx` 수정**: 작업 영역 격자 상자(음수 인셋) + 흐림 + 출력 영역 경계.
  셋 다 `pointer-events-none`. 포인터 · 히트 · 드래그 · 핸들 · 방향키 경로는 **손대지 않는다** —
  이 밀레스톤에서 그 함수들이 한 줄이라도 바뀌면 설계가 틀린 것이다.
- **M7. i18n 과 보조기기**: 키보드 안내문(`keyboardHint`)에 "출력 영역 밖에도 놓을 수 있고 그
  밖은 패널에 보이지 않는다" 한 줄, 경계·흐림의 뜻을 알리는 문구. `ko.json`/`en.json` **양쪽**,
  키 이름에 점 없음. 경계·흐림 자체는 장식이므로 `aria-hidden`.

### Final Goal (최종 목표) — 견고성과 품질 게이트

우선순위 Medium.

- **M8. 견고성**: 퇴화 크기(잰 상자 0 · 한 칸 1px 미만 · 극단 종횡비)에서 NaN 도 예외도 없고
  그리는 영역이 사라지지 않음. 편집 토글 왕복에 config 패치 0 건. 프레임 요청 계수 회귀
  (선택 · 호버 · 격자 토글 0 건).
- **M9. 회귀 게이트**: **SPEC-CANVAS-001 · 002 의 시험 스위트가 한 건도 수정되지 않은 채 전량
  green.** 수정이 필요해지면 그것은 "런타임 렌더를 바꾸지 않는다"(I9) 또는 "`projection` 은 두
  칸이다"(I2)가 깨진 신호이므로 설계를 되짚는다. 축척 0.5 포인터 시험을 **고정 입력 그대로**
  다시 돌린다(I11). 신규 코드 85%+ 커버리지(순수 모듈 95%+), LSP 0.

## 아키텍처 설계 방향

- **상자를 산술이 아니라 DOM 으로 짓는다.** 0.9.0 이 같은 이유로 같은 결정을 했다 — 오버레이는
  포인터를 제 `getBoundingClientRect()` 로 받으므로, 그 상자가 투영이 쓰는 상자와 다른 순간
  모든 좌표에 조용한 오프셋이 실린다. 상자를 실제로 지어 두면 그 오프셋이 **존재할 수 없다.**
- **`projection` 을 지키는 것이 설계 전체의 축이다.** 원점을 `projection` 에 실었다면 히트
  테스트 · 핸들 · 정렬 · 붙임 · 글자 원점이 전부 새 계약 위에 다시 서야 했다. 상자를 둘로
  나누고 오버레이를 안쪽 상자에 그대로 두는 대가로, **그 위에 선 것이 한 줄도 바뀌지 않는다.**
- **비율로 줄이고 절대 px 로 줄이지 않는다.** 두 축 같은 비율이라야 축척이 하나로 남고(I6),
  "패널 비율에 맞춤" 이 계속 옳다. 절대 px 여백은 둘 다 조용히 깬다.
- **순수 산술을 한 모듈에 모은다.** 004 · 005 · 007 이 모두 이 상자 위에 서므로, 산술이
  컴포넌트 안에 흩어지면 셋이 각자 다시 파생한다(REQ-06).
- **덧붙임의 기본값이 종전 동작이다.** `CanvasSurface.workspace`, `PanelEditGrid.offsetX/offsetY`,
  `CanvasStageGrid.origin/box` 셋 다 그렇다. 002 의 `overlay` 슬롯이 세운 규율 그대로다.
- **새 토글을 만들지 않는다.** 작업 영역은 편집 게이팅에 얹힌다 — 세 겹 게이팅이 이미 "지금
  편집 중인가" 를 소유하고 있고, 넷째 개념이 생기면 사용자가 패널마다 다른 규칙을 배운다.

## 후속 SPEC 로드맵 (006 이 보는 그림)

- **SPEC-CANVAS-004 — 설비 심볼 라이브러리 (= 사용자의 ①)**: "팔레트에 다양한 모형들과 종류별
  그룹" 은 **이 SPEC 의 주제 그 자체**다(코드 내장 심볼 카탈로그 · `group` 노드 · 스탬핑 배치 ·
  겉모습 캐스케이드). 새 번호를 따지 않는다. 006 이 비워 둔 자리는 없다 — 006 은 상자만 바꾸고
  노드를 건드리지 않으므로, 004 가 얹힐 자리는 002 가 REQ-06 으로 비워 둔 그대로다. 다만 006 이
  하나를 못박는다: **그룹도 출력 영역 밖에 놓일 수 있다.**
- **SPEC-CANVAS-007 — 벡터 이미지 가져오기 (= 사용자의 ②, 신설 예약)**: 005 와 **다른 축**이다.
  005 는 도면·사진을 **배경**에 까는 일이라 그림이 선택 대상이 아니지만, ② 는 벡터를 **요소**로
  들이는 일이라 선택·이동·크기 조절·바인딩의 대상이 된다. 그래서 007 이 답해야 할 질문은 005 의
  것과 다르다 — 가져온 벡터를 원시형으로 풀 것인가 통째로 그릴 것인가(004 가 심볼에 대해 이미
  같은 질문에 답했다), 인라인 SVG 를 금지하는 `svgAsset.ts` 규율을 어떻게 지킬 것인가,
  `DrawContext2D` 에 `drawImage` 를 들이지 않는 금지 조항(001 REQ-05 · 004 REQ-05)을 어떻게
  지킬 것인가. 006 이 못박는 것 하나: **가져온 벡터는 요소이므로 출력 영역 밖에도 놓이고, 그
  좌표는 다른 요소와 같은 정수 캔버스 단위다.**
- **SPEC-CANVAS-005 — 배경 에셋 레이어**: 006 이 규칙 하나를 앞당겨 못박는다 — **배경은 출력
  영역에 맞춰 깔리며 작업 영역을 덮지 않는다.** 배경이 작업 영역까지 덮으면 "여기까지가 패널에
  나온다" 는 표시가 곧바로 뜻을 잃는다. 005 가 캔버스 뒤에 `<img>` 층을 까는 안을 고른다면 그
  층의 상자는 `canvas-stage` 이지 `canvas-workspace` 가 아니다.
- **SPEC-CANVAS-003 — 애니메이션 전량 + 요소 복제**: 006 과 접점이 거의 없다. 다만 복제가
  계단식 오프셋으로 자리를 옮기므로, 006 이 준 넓은 저술 공간에서 복제본이 출력 영역 밖으로
  나가도 **보인다** — 006 이 003 에게 주는 부수 이득이다.

이 넷은 본 SPEC 이 정의한 상자 산술(`canvasWorkspace.ts`)과 표시 층을 확장 지점으로 쓰며,
**본 SPEC 에서는 파일을 생성하지 않는다**(로드맵 기록만).
