## 시험 규율 (이 문서 전체에 걸린다)

**이 저장소는 기본값 모양의 고정 입력에 다섯 번 물렸다.** 그 다섯을 여기 다시 적는 이유는
006 의 시험이 같은 함정을 여섯 번째로 밟기 **가장 쉬운** 위치에 있기 때문이다 — 006 이 바꾸는
것이 바로 그 다섯이 살던 층(상자 · 축척 · 좌표 기준)이다.

| 앞선 결함 | 무엇을 감췄던 기본값인가 | 006 이 그 자리에서 요구하는 것 |
|-----------|--------------------------|-------------------------------|
| 0.2.0 결함 B(포인터 축척) | **축척 1** — `rect.width / stage.width === 1` 이면 나눗셈이 항등이라 결함이 보이지 않는다 | 포인터를 재는 모든 시험은 **비단위 축척**(0.5)을 쓴다. 006 은 좌표 기준을 건드리므로 이 게이트를 **고정 입력 그대로** 다시 돌린다(AC-E3) |
| 0.3.0 결함 D(키 공간) | **참조 수 = 컬럼 수(1:1)** — 두 공간이 우연히 같아진다 | 006 의 범위 밖이지만, "두 값이 우연히 같아지는 형상" 이 결함을 감춘다는 규율은 아래 전부에 적용된다 |
| 0.4.0 결함 E(편집기↔렌더 이음매) | **한 층만 세운 시험** — 편집기만 보면 통과, 렌더만 보면 통과 | 006 의 상자·원점은 **표면이 짓고 오버레이가 쓴다.** 원점·격자 위상·좌표 기준을 재는 시험은 **표면과 진짜 오버레이를 함께** 세운다. 어느 한쪽만 세우면 이음매가 통째로 빠져 결함이 통과한다 |
| 0.8.0 (O)(격자 칸 수) | **정사각형 스테이지** — 두 축의 종횡비 차이에서 살던 결함이 보이지 않는다 | 상자를 재는 모든 시험은 **정사각형도 아니고 캔버스와 비율도 다른** 상자를 쓴다. 사용자가 반 칸을 실제로 본 **1749×796** 을 고정 입력에 넣는다 |
| 0.9.0 (R)(온전한 픽셀) | **나누어떨어지는 크기** — 한 칸이 이미 정수라 시험이 실패할 수 없다 | 선 자리를 재는 시험은 **나누어떨어지지 않는** 크기를 쓴다 |
| 0.10.0 (V)(단일 축척) | **비율이 같은 상자** — 두 축척이 이미 같아 시험이 실패할 수 없다 | 축척을 재는 시험은 **5:4 캔버스 × 1749×796 상자**를 쓴다 |

**006 이 새로 더하는 함정 넷.** 아래 넷은 006 에만 있는 것이며, 각각 어떤 기본값이 그것을
감추는지 이름으로 적는다.

| # | 감추는 고정 입력 | 그것이 통과시키는 결함 | 시험이 반드시 갖춰야 할 형상 |
|---|------------------|------------------------|------------------------------|
| D1 | **`workspace` 를 켜지 않은 시험** | 006 의 전부. 켜지 않으면 오늘의 경로만 돌아 새 코드가 한 줄도 실행되지 않는다 | 작업 영역을 재는 시험은 `workspace` 를 **켠다**. 그리고 **끈 시험도 따로** 두어 오늘과 같음을 단언한다 — 둘 다 있어야 갈래 둘이 모두 덮인다 |
| D2 | **요소가 전부 출력 영역 **안**에 있는 고정 입력** | 006 의 존재 이유. 안쪽 요소만으로는 "밖의 것이 보인다 · 골라진다 · 끌린다" 를 잴 수 없고, 심지어 원점 이동이 아예 없어도 통과한다 | 고정 입력은 **완전히 밖에 있는 요소**(음수 좌표)와 **경계에 걸친 요소**를 **각각** 포함한다 |
| D3 | **원점이 격자 칸의 배수인 고정 입력** | 격자를 작업 영역의 왼쪽 위에 앉힌 결함(위험 R3). 원점이 칸의 배수면 두 앉힘이 같은 자리라 어긋남이 나타나지 않는다 | 격자 위상을 재는 시험은 **`origin.x % cell.x !== 0`** 인 조합을 쓰고, 그 사실을 시험 파일에 **수로 적는다** |
| D4 | **출력 영역과 작업 영역이 같은 크기인 고정 입력**(축소 비율 1.0) | 원점 · 흐림 · 경계 · 격자 위상 전부. 두 상자가 같으면 006 이 하는 일이 사라진다 | 상수를 시험에서 갈아 끼우지 않는다. `PANEL_REGION_FIT_RATIO` 를 그대로 쓰고, 두 상자의 크기가 **실제로 다름**을 먼저 단언한 뒤 나머지를 잰다 |

**가드가 정말로 지키는지 확인한다.** 새로 세우는 가드(격자 원점 · 기본값 0 · 무동작 보장)는
**깨 보아 실패하는지**를 확인한다. 원점을 0 으로 바꾸면 격자 시험이 실패해야 하고, `offsetX`
기본값을 1 로 바꾸면 다섯 패널 가드가 실패해야 하며, `workspace` 기본값을 `true` 로 바꾸면
무동작 게이트가 실패해야 한다. **실패하지 않는 가드는 다음 사람에게 거짓말한다.**

**꺼져 있어서 통과하는 초록은 초록이 아니다.** 편집이 꺼진 상태로 잰 "작업 영역 시험", 격자가
꺼진 상태로 잰 "격자 시험", 요소가 0개인 상태로 잰 "밖의 요소 시험" 은 전부 **틀린 이유로**
통과한다. 각 시나리오는 자기가 재려는 것이 **켜져 있음을 먼저 단언**한다.

**진짜 번역 문구로 잰다.** 키를 그대로 돌려주는 i18n 대체 아래에서는 치환자(`{...}`)가 빈
자리를 만드는 결함이 드러나지 않는다(AC-E22 가 이미 같은 규율을 세웠다).

## 시나리오 (Given / When / Then)

### AC-01 — 상자가 둘이고, 안쪽이 패널 출력 영역이다 (REQ-01)

```gherkin
Given 캔버스 패널이 1749 × 796 상자에 놓이고 캔버스 크기가 500 × 400 일 때
      (정사각형도 아니고 캔버스와 비율도 다른 고정 입력이어야 한다 — 비율이 같은 상자에서는
       자투리가 0 이라 여백의 성질을 잴 수 없다)
When 편집이 켜지면
Then 표면은 상자를 **둘** 짓는다 — 잰 상자를 덮는 **작업 영역**과 그 안의 **패널 출력 영역**
  And 두 상자의 크기가 **실제로 다르다**(같으면 이 SPEC 이 아무 일도 하지 않은 것이다)
  And `<canvas>` 는 **작업 영역**을 덮는다(그래야 그 밖의 그림이 비트맵 안에 들어온다)
  And 편집 오버레이는 **출력 영역** 상자 안에 산다(오늘 그대로)
  And 오버레이가 받는 `projection.stage` 는 **출력 영역**의 CSS px 크기다
  And `projection` 은 여전히 두 칸(`stage` · `canvas`)이며 원점을 싣지 않는다
Given 같은 상태일 때
Then 출력 영역이 작업 영역 안에서 **가운데**에 서고, 그 자리(캔버스 좌표 원점)가 **정수 CSS px** 다
  And 축소는 두 축에 **같은 비율**로 걸린다 — 출력 영역의 종횡비가 캔버스의 종횡비와 같다
```

### AC-02 — 출력 영역 밖의 요소가 보이고, 골라지고, 끌린다 (REQ-03)

```gherkin
Given 편집이 켜진 캔버스에 요소 셋이 있을 때
      (고정 입력은 **안에 하나 · 완전히 밖에 하나(음수 좌표) · 경계에 걸친 하나** 여야 한다 —
       전부 안에 있는 고정 입력은 원점 이동이 아예 없어도 통과한다)
When 프레임이 그려지면
Then 세 요소가 **모두** 비트맵 안에 그려진다(밖의 것도 사라지지 않는다)
When 완전히 밖에 있는 요소의 한가운데를 누르면
Then 그 요소가 골라진다 — 안쪽 요소와 **같은 경로**(`hitTest`)를 지나며 밖을 위한 분기가 없다
  And 히트 결과는 여전히 `{ nodeId }` 레코드이고 `partId` 는 채워지지 않는다
When 그 요소를 끌면
Then 좌표가 손을 따라오고 **clamp 되지 않으며**, 놓는 순간 마지막 유효 위치가 그대로 확정된다
  And 저장되는 값은 여전히 정수이고, 그 정수화는 `patchNodeGeometry` **한 곳**에서만 일어난다
When 그 요소가 골라진 채 방향키를 누르면
Then 1 캔버스 단위(Shift 는 한 격자 칸) 옮겨지고 이벤트가 소비된다 — 안쪽과 같다
Given 그 요소가 골라져 있을 때
Then 윤곽선과 손잡이가 **출력 영역 밖에** 그려지고, 잘리는 자리는 비트맵이 잘리는 자리와 **같다**
```

### AC-03 — 어디가 패널에 나오는지 보인다 (REQ-02)

```gherkin
Given 편집이 켜진 캔버스일 때
Then 출력 영역의 **경계**가 그려지고, 그 **밖**이 흐리게 덮인다(안쪽이 아니다)
  And 경계와 흐림은 **DOM 층**이며 캔버스에 칠해지지 않는다
  And 둘 다 포인터를 **소비하지 않는다**(`pointer-events-none`) — 그 위에서 도형을 고르고 끌 수 있다
  And 색상은 편집 보조선이 이미 쓰는 중간 회색 계열이고 **불투명도만** 다르다
  And **파랑이 아니다** — 이 화면에서 파랑은 이미 "고른 것"(선택 윤곽선)과 "가운데"(격자 중심 표식)를
      뜻하므로, 출력 영역이 파랑이면 아무것도 고르지 않았는데 골라진 것처럼 읽힌다
  And 흐림은 사각형 넷을 좌표로 두르지 않는다 — 같은 상자를 네 번 다시 파생하는 일이다
Given 요소가 하나도 없을 때
Then 경계와 흐림은 그대로 있다(첫 도형을 놓기 전에 어디에 놓을지 보는 것이 이 표시의 쓸모다)
  And 빈 상태 안내는 여전히 **출력 영역 안**에 서고 포인터를 먹지 않는다(AC-E10 유지)
Given 밝은 테마와 어두운 테마에서 각각 볼 때
Then 안팎의 단차가 **양쪽 모두**에서 읽힌다 — 한 테마에서만 읽히는 표시는 절반의 사용자에게
      표시가 없는 것과 같다
```

### AC-04 — 격자가 출력 영역의 원점에 앉는다 (REQ-04 · 위험 R3)

```gherkin
Given 편집과 격자 붙임이 켜져 있고, 원점이 격자 한 칸의 **배수가 아닌** 조합일 때
      (`origin.x % cell.x !== 0` — 배수인 고정 입력에서는 두 앉힘이 같은 자리라 이 시험이
       실패할 수 없다. 쓴 수를 시험 파일에 그대로 적는다)
Then 격자는 **작업 영역 전체**에 그려지되 선이 **출력 영역의 원점**에서 시작한다
  And 그 사실이 `backgroundPosition` 이 원점과 **같은 값**이라는 것으로 확인된다
  And 그려질 선 자리가 모두 **정수 CSS px** 이고 이웃한 선 사이 간격이 전부 같다(AC-E19 (R) 유지)
  And 한 칸의 CSS px 는 **두 축 모두 같은 정수**다 — 칸이 정사각형이다(AC-E20 (V) 유지)
When 요소를 끌어 격자에 붙이면
Then 붙은 요소의 중심을 **화면으로 투영한 px** 가 그려진 선 위다
  And 그 성질이 **출력 영역 밖에서도** 성립한다(밖에서만 어긋나는 결함을 안쪽 시험은 통과시킨다)
  And Shift+방향키 한 칸도 같은 정수를 쓴다 — 그림 · 붙임 · Shift 가 여전히 한 값에서 나온다
Given 격자의 중심 표식(`+`)을 볼 때
Then 그것은 **출력 영역의 중심**에 선다(작업 영역의 중심이 아니다)
  And 그 성질은 출력 영역이 작업 영역 안에서 가운데 정렬된다는 사실에 기대므로, 자리 계산을
      바꾸면 이 단언이 함께 실패해야 한다
Given 격자 붙임이 꺼져 있을 때
Then 격자가 그려지지 않고, 경계와 흐림은 그대로다(둘은 다른 축이다)
```

### AC-05 — 정렬 · 붙임 · 맞춤의 기준은 출력 영역이다 (REQ-04)

```gherkin
Given 편집이 켜진 캔버스에 요소 둘이 있고 **하나가 출력 영역 밖**에 있을 때
When 왼쪽 맞춤을 누르면
Then 기준은 **출력 영역**이다(작업 영역이 아니다) — 맞추려는 대상은 실제로 보일 자리다
  And 그 성질은 `alignDeltas` 가 `proj.stage` 를 기준 상자로 쓰기 때문에 **코드 수정 없이** 성립한다
Given 캔버스 크기를 패널 비율에 맞추는 단추를 볼 때
When 그것을 누르면
Then 계산은 잰 **바깥** 상자의 비율을 쓰며 006 이 있으나 없으나 **같은 값**을 낸다
  And 폭은 그대로이고 높이만 다시 계산되며, 요소 좌표는 함께 가지 않는다(AC-E20 (X) 유지)
Then 맞춤 뒤 저술 여백이 **사방에 고르게** 남는다(축마다 1px 이내로 같다)
Given 요소가 0개 · 기본 크기 · 편집 중인 새 패널일 때
When 표면이 패널 크기를 처음 재면
Then 한 번뿐인 자동 맞춤이 **006 이전과 똑같이** 일어난다(조건 넷도 그대로다)
  And 그 뒤로는 리사이즈가 몇 번 오든 다시 맞추지 않는다
```

### AC-06 — 편집을 끄면 오늘과 같다 (REQ-05 · 위험 R7)

```gherkin
Given 001 · 002 가 저장한 캔버스 패널 config 가 있을 때
When 대시보드에서 편집이 꺼진 채로 그것을 열면
Then 그리는 결과가 SPEC-CANVAS-002 와 **한 픽셀도 다르지 않다**
  And 작업 영역 · 경계 · 흐림이 **하나도 만들어지지 않는다**
  And 마이그레이션도, 호환 경로도, 옛 config 에 대한 특별 취급도 없다
When 편집을 켰다가 다시 끄면
Then config 패치가 **한 건도 나가지 않는다** — 바뀌는 것은 투영 축척뿐이고 좌표는 그대로다
  And `parseCanvasConfig` 왕복에 값이 한 글자도 달라지지 않는다
  And 다시 끈 뒤의 그림이 켜기 전과 **같다**
```

## 엣지 케이스 (Edge Cases)

### AC-E3 — 축소된 미리보기에서도 포인터가 도형과 같은 공간에 있다 (AC-E9 계승)

### AC-E4 — 유휴 정지가 작업 영역 때문에 깨지지 않는다 (REQ-05 · SPEC-CANVAS-001 REQ-05)

```gherkin

  And 그 프레임 뒤에 진행 중 트윈이 없으면 루프는 다시 유휴로 돌아간다

```

### AC-E5 — 퇴화한 크기에서도 그림이 사라지지 않는다 (AC-E19 (T) · AC-E20 (Y) 계승)

```gherkin

```

### AC-E6 — 몸짓의 소유권은 그대로다 (REQ-03 · AC-E3 · AC-E21 (AA) 계승)
