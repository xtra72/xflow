# SPEC-CANVAS-014 — 구현 계획

## 구현 전략

### 순서를 이렇게 잡는 이유

**"보이는데 못 잡는" 구간을 만들지 않는다.** 그리기(M4)를 먼저 배달하고 잡기(M5)를 뒤에
두면, 그 사이에 사용자는 **보이는 도형을 눌러도 잡지 못하고 빈 곳을 눌러 엉뚱한 것을
잡는다** — 002 가 위험 R1 로 이름 적어 둔 그 실패가 두 커밋 사이에 실재한다. 그래서 둘은
**한 커밋**으로 간다.

그 앞에는 값으로만 검증되는 순수 층을 둔다(M1 · M2 · M3). 이 SPEC 의 위험은 배선이 아니라
**두 상자가 갈라지는 것**이고, 그것은 렌더 없이 값으로 잴 수 있다.

**같은 수법을 두 자리에 쓴다** — 잡기도 크기 조절도 "점/델타를 역회전한 뒤 기존 산술" 이다
(§결정 3 · §결정 4). 그 재사용이 이 SPEC 이 7,600 줄을 감당하는 방법이므로, M5 를 먼저 하고
M7 이 그 수법을 이어받게 한다.

몸짓(M9)은 맨 뒤다. 각도를 바꾸는 길이 없어도 저장된 각도가 **올바르게 보이고 잡히는지**를
앞에서 전부 잴 수 있고, 그 순서라야 몸짓 시험이 실패했을 때 원인이 몸짓 하나로 좁혀진다.

### 핵심 설계 결정

| # | 결정 | 근거 |
|---|------|------|
| D1 | 정수 도 `[0, 360)` | spec §결정 1 — 90° 배수가 정확해야 013 의 K1 이 산다 |
| D2 | `outlineBox` 가 OBB 를 내고 AABB 는 파생 | spec §결정 2 — 상자는 한 번 나온다(AC-33) |
| D3 | 잡기·크기조절은 **역회전 한 줄** | spec §결정 3 · §결정 4 — 다섯 갈래가 열이 되지 않는다 |
| D4 | `translate`·`rotate` 는 **선택적** 멤버 | spec §결정 5 — 012 의 선례. 스텁 공장 아홉이 무사하다 |
| D5 | 각도 0 이면 키가 없다 | spec §결정 7 — 014 이전 저장이 바이트 동일하게 왕복한다 |
| D6 | `line` 에는 필드가 서지 않는다 | 좌표로 표현되므로. `anchors` 의 A11 과 같은 규율 |

## 마일스톤

### M1 — 회전 축 (REQ-01 · REQ-08 · §결정 1 · §결정 7)

- 새 잎 모듈 `canvasRotation.ts` — 정규화 · 도↔라디안 · 점 회전/역회전
- `CanvasElementBase.rotation?: number` + `GroupElement.rotation?: number`
- 파서: 유한하지 않으면 키를 버린다. **0 은 키를 만들지 않는다**(D5)
- `line` 갈래에서는 붙이지 않는다(D6) — `anchors` 가 상자형에만 서는 그 자리와 같다
- 시험: 왕복 · 정규화(−90 → 270, 450 → 90) · **014 이전 저장의 바이트 동일**

### M2 — 방향 상자와 축-나란 상자 (REQ-04 · REQ-06 · §결정 2)

- `outlineBox` 가 각도를 함께 낸다(OBB)
- `aabbOf(obb)` — 네 모서리를 돌려 덮는 상자
- **각도 0 이면 둘이 같은 수**임을 시험이 못박는다(K3)
- 소비자 일곱을 둘 가운데 **어느 쪽을 읽는지** 갈라 적는다

### M3 — 그리기 축 (REQ-01 · §결정 5)

- `DrawContext2D` 에 선택적 `translate`·`rotate`
- `drawElement` 가 `save` → `translate(중심)` → `rotate(라디안)` → `translate(−중심)` 로 감싼다
- 스텁이 그 둘을 갖추는 것부터 못박는 시험

### M4+M5 — **한 커밋** — 보이는 자리와 잡히는 자리 (REQ-03 · §결정 3)

- 그리기가 각도를 읽는다(M3 의 배선을 실제 요소에 건다)
- `canvasHitTest` 가 점을 역회전한 뒤 **기존 다섯 판정**을 그대로 부른다
- 시험: 돌아간 도형의 **잉크 위 점은 잡히고 빈 모서리는 잡히지 않는다**
- 층을 건너는 시험: 그린 좌표와 잡히는 좌표가 같은 각도를 본다(K1)

**둘을 가르지 않는다** — 가르면 R1 이 두 커밋 사이에 실재한다(§순서).

### M6 — 손잡이와 앵커 (REQ-04)

- `handlePositions` 가 OBB 모서리에 여덟을 세운다
- `anchors.anchorPoints` 는 `outlineBox` 를 지나므로 **저절로 따라온다** — 그 사실을
  시험이 못박는다(두 번째 산술이 생기지 않았다는 증거다)

### M7 — 크기 조절 (REQ-05 · §결정 4)

- 드래그 델타를 역회전해 기존 리사이즈 산술에 넣는다(M5 와 **같은 수법**)
- 시험: 90° 돌아간 요소의 오른쪽 핸들을 끌면 **세로**가 바뀐다

### M8 — 마키와 정렬 (REQ-06)

- 둘 다 AABB 를 읽는다
- 시험: 45° 돌아간 긴 막대가 제 AABB 안에서 마키에 잡힌다

### M9 — 회전 손잡이 (REQ-02)

- 상자 위쪽에 손잡이 하나. 끌면 각도가 따라온다
- Shift 로 15° 눈금 — 격자 붙임과 **다른 축**임을 주석이 적는다
- i18n: 손잡이 이름 (ko · en)

### M10 — 013 의 변환이 각도를 안다 (REQ-07 · §결정 6)

- `canvasTransformNodes` 가 각도도 바꾼다(표는 spec §결정 6)
- **013 의 좌표 산술은 한 줄도 바뀌지 않는다** — 각도가 그 위에 얹힐 뿐이다
- 시험: 013 의 K1 · K1' 을 **각도가 0 이 아닌 요소**에 대해 다시 돌린다

## 시험 전략

### 각도 0 을 **모든 층에서** 다시 잰다

014 의 가장 큰 위험은 새 기능이 아니라 **옛 그림이 흔들리는 것**이다. 각도 0 에서 OBB 와
AABB 가 같은 수인지(K3), 저장이 바이트 동일한지, 기존 시험 4,074 건이 한 건도 바뀌지 않는지를
각 마일스톤에서 확인한다.

### 두 상자가 갈라지지 않는 것을 값으로 잰다

"손잡이가 마키의 상자에 선다" 는 화면에서만 보이는 결함이다. OBB 와 AABB 를 **같은 함수
하나**에서 파생시키고, 그 사실을 소스 판정으로 고정한다(두 번째 측정이 생기면 운다).

### 뮤테이션으로 확인한다

역회전의 **부호**는 뒤집혀도 대부분의 단언을 통과한다(대칭 도형·정사각형). 비대칭 도형과
비직각 각도를 고정 입력에 넣고, 부호를 뒤집는 뮤테이션이 실제로 무는지 값으로 확인한다.
