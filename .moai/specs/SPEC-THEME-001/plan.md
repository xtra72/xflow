## 이 계획이 먼저 정하는 것 — 순서가 곧 위험 관리다

이 작업의 위험은 **색이 조용히 달라지는 것**이다. 111자리를 갈아 끼우는 동안 한 자리만
잘못된 토큰으로 보내면, 그 화면은 여전히 그려지고 시험도 통과하며 다만 색이 다르다.
DOM 을 보는 시험은 클래스 이름이 바뀐 것을 회귀로 읽지 못한다.

그래서 순서를 이렇게 둔다:

1. **오늘의 색을 먼저 못 박는다.** 111자리 각각이 day/night 에서 실제로 무슨 색으로
   그려지는지를 계산해 고정한다. 이것이 없으면 §M3 의 "색이 안 바뀌었다"를 **주장만**
   할 수 있고 잴 수 없다.
2. **토큰을 늘린다**(3개). 값은 1단계가 잰 그 값이다.
3. **111자리를 옮긴다.** 1단계의 고정과 비교한다.
4. **미리보기를 만든다.** 토큰화가 끝난 뒤라야 미리보기가 진짜 화면과 같은 토큰을 쓴다.

미리보기를 **마지막**에 두는 이유는, 먼저 만들면 미리보기가 아직 토큰이 아닌 색을
흉내 내게 되어 **미리보기와 실제가 다른 채로 초록**이 되기 때문이다.

## 작업 분해 (Task Decomposition)

### Primary Goal (1차 목표) — 오늘의 색을 못 박고 토큰을 늘린다

**M1. 111자리의 오늘 색을 특성화로 고정한다**

- `web/src/components/flow/` 10파일에서 중립색 클래스를 뽑아, 각 클래스가 day/night 에서
  내는 실제 색을 표로 만든다(Tailwind 기본 팔레트 값 — `zinc-400` = `#a1a1aa` 등).
- 시험: 클래스 → 색 표를 스냅샷으로 고정. **M3 이 이 표와 대조한다.**
- **여기서 끝나야 할 것**: "무엇이 무슨 색인가"가 짐작이 아니라 파일에 적힌다.

**M2. 토큰 셋 + `flow` 카테고리**

- `tokens.ts` 에 `--color-flow-canvas` · `--color-flow-edge` · `--color-flow-area` 추가.
  `DAY_PRESET` · `NIGHT_PRESET` 에 M1 이 잰 값.
- `index.css` 의 `@theme` · `:root` · `[data-theme="night"]` 세 곳에 같은 값
  (`tokens.cssParity.test.ts` 가 어긋남을 잡는다).
- `TOKEN_CATEGORIES` 에 `flow` 카테고리. i18n 라벨·힌트 **두 로케일**.
- 시험: 카테고리 수 · 토큰 수 · cssParity · 두 로케일 키 존재.

### Secondary Goal (2차 목표) — 111자리 교체

**M3. 파일별 교체 — 큰 것부터가 아니라 위험한 것부터**

순서: `CustomNode`(29) → `FlowAreaNode`(4) · `CustomEdge`(2) · `NodeHandle`(1) →
`FlowBoundaryNode`(6) · `LinkIndicator`(6) → `FlowPortPanel`(22) ·
`LinkListPopover`(12) → `EditorToolbar`(27) → `NodeContextMenu`(2)

`CustomNode` 가 먼저인 것은 사용자가 신고한 자리이고, 새 토큰 셋 중 둘
(`flow-edge` · `flow-area`)이 그 주변에서 처음 쓰이기 때문이다.

- 각 파일 교체 후 M1 표와 대조 — **색이 달라지면 그 자리를 되돌린다**(예외: 노드 부제).
- 노드 부제(`CustomNode.tsx:476`)는 `--color-text-muted` 로 보내고, **대비를 실제로
  계산해** day/night 양쪽 4.5:1 을 확인한다(REQ-03).
- grep 가드(I1) 추가.

**M4. 커버리지 허용목록** — 신규 파일이 생기면 **같은 커밋에** 넣는다(기존 교훈 R7).

### Final Goal (최종 목표) — 미리보기

**M5. `ThemePreview` 컴포넌트**

- 가짜 마크업 7조각(플로우 노드 · 연결선 · 캔버스 바탕 · 패널 · 표 · 단추 · 상태).
- 컨테이너에 `resolveTokens(target, overrides)` 를 인라인 CSS 변수로.
- `target === 'night'` 이면 컨테이너에 `.dark` 를 붙인다(I4).
- 시험: 편집 중 프리셋을 그리는가(I3) · `.dark` 조건부(I4) ·
  `ReactFlowProvider` 없이 렌더되는가(I7) · 24토큰이 최소 한 번씩 나타나는가.

**M6. 양방향 강조**

- 표 행 선택 → 미리보기 조각 윤곽선.
- 미리보기 조각 클릭 → 표 행 강조·스크롤.
- 조각 ↔ 토큰 대응표를 **한 곳**에 둔다 — 양방향이 각자 표를 들면 어긋난다.

**M7. i18n** — 두 로케일. 기본 로케일이 `ko` 라 en 누락이 초록으로 통과하는 함정
(기존 교훈)을 두 로케일 전수 시험으로 막는다.

**M8. 게이트** — 전체 시험 · 타입 · 린트 · grep 가드(I1) · 대비 계산(REQ-03) ·
acceptance.md AC 전수.

## 커밋 분할 시 주의 (기존 교훈)

경로 휴리스틱과 import grep 만으로는 중간 커밋의 빌드를 보장하지 못한다. M2 가 M3 보다
**반드시 먼저** 커밋되어야 한다 — 토큰이 없는 상태에서 `bg-(--color-flow-canvas)` 를
쓰면 `index.tokens.test.ts` 가드가 붉어지고, 화면은 **아무 배경도 없이** 그려진다.

M5 의 미리보기는 M3 이 끝난 뒤 커밋한다. 먼저 커밋하면 미리보기가 실제 화면과 다른
색을 보여 주는 기간이 생기고, 그 기간에 누군가 미리보기를 믿고 색을 고른다.

## 아키텍처 설계 방향

**토큰의 뜻은 카테고리가 정한다.** `flow` 카테고리를 새로 만드는 것은 색이 세 개
늘어서가 아니라, §결정 3 의 미리보기가 **카테고리를 구획으로** 쓰기 때문이다.

**미리보기는 실물이 아니라 같은 토큰을 쓰는 축소본이다.** 실물을 끌어오면 편집기 전체가
설정 화면에 적재된다(I7). 같은 것은 색이고 다른 것은 구조다.

**미리보기의 진실은 컨테이너 안에서만 다르다.** CSS 변수 상속으로 국소화하므로 바깥
화면이 흔들리지 않는다(I3).

**색을 옮기는 일과 색을 고르는 일을 같은 커밋에 두지 않는다.** 그래야 회귀가
재배색에 묻히지 않는다(I5).
