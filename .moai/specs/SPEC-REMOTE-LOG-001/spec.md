## 개요 — "마지막 수신" 이 수신 시각이 아니었다

화면의 `마지막 수신` 은 DB 의 `last_seen` 을 그대로 보여준다. 그런데 그 칸에 쓰는 자리는
**연결·끊김·청소기뿐**이었다. keep-alive 가 도착할 때 부르는 `touch()` 는 **메모리만**
고치고, 하트비트 처리기는 `updated_at` 만 건드린다.

그래서 3일 전에 붙어 30초마다 하트비트를 보내는 멀쩡한 노드의 "마지막 수신" 이 3일 전으로
굳어 있었다. 그 값은 사실상 "마지막 접속" 에 가까웠고, 정작 수신 시각은 어디에도 영속되지
않았다.

로그 쪽은 뼈대만 있었다. append-only 감사 표와 `GET /remote/audit` 은 있었지만 **프론트에서
그 엔드포인트를 부르는 곳이 0건**이었고, 등록·삭제·연결·끊어짐·원격 접속은 기록되지 않았다.

## 요구사항 (Requirements — EARS)

### REQ-01 — 수신은 keep-alive 가 남긴다 (Event-Driven)

**When** 노드의 heartbeat 를 받으면, 서버는 `last_seen` 을 DB 에 갱신한다. 영속은 하트비트
에서만 한다 — 스트림 데이터 같은 고빈도 메시지 자리에서 DB 를 때리면 쓰기가 폭주한다.
노드별로 최소 간격(15초)을 둔다.

### REQ-02 — 접속은 사람이 남긴다 (Event-Driven)

**When** 관리자가 노드를 원격 관리하면(상세 조회·명령·질의 프록시), 서버는
`last_access_at`/`last_access_by` 를 기록한다. **주체가 없는 내부 호출은 기록하지 않는다** —
사람이 한 일이 아닌 것을 "마지막 접속" 으로 적으면 그 칸의 뜻이 무너진다.

### REQ-03 — 접속 기록은 관리자 소유다 (Ubiquitous)

`last_access_*` 는 `group_name` 과 같은 관리자 소유 메타데이터이며, 노드의 register/heartbeat
upsert 가 절대 덮어쓰지 않는다.

### REQ-04 — 사건을 남긴다 (Event-Driven)

등록 요청(pending 큐잉) · 연결 · 끊어짐 · 노드 삭제 · 원격 접속을 감사 표에 기록한다.
연결·끊어짐·등록의 주체는 `system`(서버가 관측한 사실), 삭제·접속의 주체는 관리자다.

### REQ-05 — 로그는 기간으로 지운다 (State-Driven)

**While** 보존 기간(`remote_management.audit_retention`, 기본 720h)이 설정되어 있는 동안,
서버는 한 시간마다 그보다 오래된 기록을 지운다. **0 이면 지우지 않는다** — "미설정" 을
"전부 삭제" 로 읽으면 설정 실수 한 번이 감사 기록을 통째로 날린다.

### REQ-06 — 정렬·필터·건수는 서버가 맡는다 (Ubiquitous)

조회는 노드·사건·수행자 필터와 정렬 기준/방향을 받고, **필터를 적용한 전체 건수**를 함께
반환한다. 정렬 기준은 화이트리스트를 지나며 그 밖의 값은 기본(최신순)으로 떨어진다.

## 명세 (Specifications)

### 결정 1 — 한 표에 운영 사건과 관리자 변경을 함께 담는다

승인·거부·폐기·명령이 "관리자가 무엇을 바꿨는가" 라면, 연결·끊어짐·등록·접속은 "노드에 무슨
일이 있었는가" 다. 두 가지를 나눠 놓으면 "언제 끊겼고 그때 누가 무엇을 했는가" 를 읽으려고
두 목록을 손으로 맞춰 봐야 한다.

### 결정 2 — 접속 기록에는 창(window)이 둘이다

노드 화면은 5초마다 상세를 다시 조회한다. 그 요청을 그대로 받아 적으면 창을 열어 둔 30분이
로그 360줄이 된다. 시각 갱신은 30초 간격, 로그 한 줄은 10분 창으로 묶는다 — 한 번 들어와
머무는 동안은 한 줄이고, 자리를 뜨고 한참 뒤 다시 들어오면 새 줄이 생긴다.

### 결정 3 — 이미지 업데이트에 새 액션을 만들지 않는다

업데이트 지시는 기존 명령 디스패치를 그대로 타므로 `command` + `system`/`update` 로 이미
1행이 남는다(성공·실패·타임아웃 모두). 같은 사건에 행을 둘 만들면 한 번의 지시가 두 번
일어난 것처럼 읽힌다. 화면이 그 조합만 집어 "이미지 업데이트" 로 읽는다.

### 결정 4 — 정렬에 2차 키로 id 를 붙인다

같은 밀리초에 여러 사건이 생기면(연결 직후 인벤토리 수신) 순서가 요청마다 달라져, 쪽을
넘길 때 같은 줄이 두 번 보이거나 한 줄이 통째로 건너뛰어진다.

### 결정 5 — append-only 의 예외는 나이뿐이다

기록을 골라 지우는 API 는 두지 않는다(감사 무결성). 다만 연결/끊어짐까지 남기면 불안정한
노드 하나가 표를 빠르게 불리므로, 나이로 지우는 문 하나는 필요하다.

## 불변식 (Invariants)

- `last_seen` 은 노드가 살아 있다는 신호, `last_access_at` 은 사람이 들여다본 시각 — 두
  질문에 각각 답할 수 있다.
- 노드의 보고가 관리자 소유 칸을 덮지 않는다.
- 화면이 보는 정렬 결과는 전체를 대표한다(쪽 안에서만 정렬하지 않는다).

## 범위 밖 (Non-Goals)

1. **보존 기간의 UI 설정** — 서버 설정 파일 항목이다.
2. **노드 탭의 정렬·필터** — 로그 페이지에만 둔다.
3. **사건 종류 목록의 서버 제공** — 필터 후보는 프론트 상수다.
4. **미러에 쌓인 과거 유령 데이터 정리** — 별건.

## 잔여 위험

접속 창(30초/10분)의 값이 실제 운용에서 적절한지는 써 봐야 안다. 보존 정리 고루틴은
시험하지 않았다(시계를 주입할 자리가 필요해 이번 범위에서 뺐다).
