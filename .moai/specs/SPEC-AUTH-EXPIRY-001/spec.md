# SPEC-AUTH-EXPIRY-001: 401 이 갱신 인터셉터에 닿지 않았다

## HISTORY

| 버전 | 날짜 | 작성자 | 변경 내용 |
|------|------|--------|----------|
| 0.1.0 | 2026-09-20 | xtra | 최초 작성 + 구현 — 사용자 신고("세션 만료 후 연결시 로그인 화면으로") |

## 개요 — 있어야 할 것이 다 있는데 한 번도 불리지 않았다

`interceptors.ts` 에는 401 을 받아 토큰을 갱신하고, 갱신이 실패하면 로그아웃 후 로그인
화면으로 보내는 장치가 처음부터 있었다. **그 handler 가 한 번도 불리지 않았다.**

axios 응답 인터셉터는 **등록 순서대로** 돈다. `client.ts` 의 봉투 인터셉터가 모듈 적재
시점에 먼저 등록되어 실패 응답을 `APIError` 로 바꿔 던지는데, `APIError` 에는 `response`
도 `config` 도 없다. 갱신 인터셉터의 문턱은 `error.response?.status !== 401` 이므로 언제나
참이 되어 그대로 다시 던진다. 갱신 인터셉터는 `main.tsx` 가 앱 시작 시 붙였으므로 항상
봉투보다 **뒤**였다.

이 한 줄의 순서가 세 가지를 동시에 죽였다.

1. **자동 토큰 갱신** — 24시간 액세스 토큰이 만료되면 그걸로 끝. 7일짜리 리프레시 토큰은
   쓰이지 않았고 사용자는 매일 다시 로그인했다.
2. **만료 시 로그아웃** — 아무도 `logout()` 을 부르지 않으므로 `isAuthenticated` 가 참으로
   남고, 열어 둔 탭은 패널마다 에러만 뿌린 채 **로그인 화면으로 가지 않았다.**
3. **리다이렉트** — 갱신 실패 경로의 `window.location.href = '/login'` 에 도달할 수 없었다.

## 요구사항 (Requirements — EARS)

### REQ-01 — 401 은 갱신을 부른다 (Event-Driven)

**When** 인증이 필요한 요청이 401 을 받으면, 클라이언트는 리프레시 토큰으로 갱신을 시도하고
성공하면 원 요청을 새 토큰으로 재시도한다.

### REQ-02 — 갱신이 실패하면 세션을 정리한다 (Event-Driven)

**When** 갱신이 실패하거나 리프레시 토큰이 없으면, 클라이언트는 `logout()` 으로 세션을
정리한다. 모든 앱 라우트가 AuthGuard 아래에 있으므로 그 한 줄이 로그인 화면 전이를 만든다.

### REQ-03 — 동시 401 에 갱신은 한 번만 (State-Driven)

**While** 갱신이 진행 중인 동안 들어온 401 들은 큐에 들어가고, 갱신 완료 후 새 토큰으로
함께 재시도된다.

### REQ-04 — 갱신 요청 자신의 401 은 되받지 않는다 (Unwanted)

`/auth/refresh` 가 401 을 반환하면 그것으로 갱신을 다시 부르지 않는다 — 갱신이 갱신을
부르는 재귀가 된다.

### REQ-05 — WS 인증 실패는 확인 후 판정한다 (Event-Driven)

**When** WebSocket 이 인증 실패 정황(`1006` + 비정상 종료 + onopen 미발생)으로 끊기면,
`/auth/me` 로 세션이 정말 끝났는지 확인한다. 401 이면 로그아웃하고, 401 이 아니면(서버
다운·오프라인) 세션을 건드리지 않는다.

## 명세 (Specifications)

### 결정 1 — 등록을 client.ts 로 옮겨 순서를 코드가 보장하게 한다

문턱만 고치면 같은 함정이 다시 생긴다(호출 지점이 옮겨 다니면 순서가 뒤집힌다). 등록을
`client.ts` 의 모듈 적재 시점으로 옮겨 봉투 인터셉터 **바로 위**에 두었다. 두 등록이 한
자리에 순서대로 있으므로 순서가 코드로 드러난다. `setupInterceptors` 는 멱등하다.

### 결정 2 — 리다이렉트는 `logout()` 하나로 한다

종전의 `window.location.href = '/login'` 은 전체 새로고침이라 SPA 상태를 통째로 버렸다.
모든 앱 라우트가 AuthGuard 아래이므로 `logout()` 이 곧 전이다.

### 결정 3 — 재시도 응답에 "이미 벗김" 표식을 찍는다

갱신 후 재시도한 요청은 자기 체인에서 봉투가 이미 벗겨진다. 그런데 거부 핸들러가 값을
반환하면 axios 는 **원 요청의** 체인을 이어 돌리므로 봉투 인터셉터가 한 번 더 벗기려 들어
payload 를 봉투로 오인하고 `APIError('UNKNOWN')` 를 던진다. `ALREADY_UNWRAPPED` 심볼로 그
두 번째 통과를 건너뛴다. **순서만 고치고 시험을 안 썼다면 갱신은 살아나되 모든 재시도가
실패했을 자리다.**

### 결정 4 — WS 의 정황은 근거가 아니다

`1006 + 비정상 종료 + onopen 미발생` 은 서버 다운·프록시 거부·오프라인에서도 만들어진다.
그 정황만으로 로그아웃하면 네트워크가 잠깐 끊긴 사용자를 로그인 화면으로 내쫓는다 —
고치려는 것보다 나쁜 결함이다. 그래서 REST 로 확인한 뒤 판정한다.

## 불변식 (Invariants)

- 갱신 인터셉터는 봉투 인터셉터보다 **먼저** 등록된다.
- 401 응답 하나가 세션 정리로 이어지는 경로가 항상 열려 있다.
- 봉투는 응답 하나당 정확히 한 번 벗겨진다.

## 범위 밖 (Non-Goals)

1. **선제 만료 감지** — `expires_at` 을 보고 만료 전에 미리 갱신하거나 탭 복귀 시 확인하는
   일은 하지 않는다.
2. **WS 오탐 뒤 재연결** — 인증 실패 정황이 오탐이었을 때 WS 를 다시 붙이는 정책은 이
   결함과 별개다(섣불리 붙이면 연결 실패 루프가 된다).
3. **리프레시 토큰 폐기** — 서버는 제시된 액세스 토큰만 블랙리스트에 넣는다.

### 가드가 무는지 — 세 자리를 뒤집어 확인

등록 순서를 원래대로 되돌리면 인터셉터 시험 5/5 가, 봉투 중복 해제 표식을 지우면 3/5 가,
WS 의 401 판정을 무조건 참으로 만들면 "401 이 아닌 실패로는 세션을 끊지 않는다" 가 실패한다.
