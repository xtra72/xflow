## 개요 (Overview)

SPEC-CANVAS-001 은 구현이 끝났고 대시보드에 `canvas` 패널이 실제로 떠 있다. 001 은 두 가지를 의도적으로
이연했다.

- **가정 A4** — 요소의 기하(위치·크기)를 **수치로** 저술한다. 캔버스 위 드래그 배치는 002 다.
- **가정 A7** — 001 은 **렌더 전용**이다. 요소 클릭·요소별 툴팁은 Canvas 에서 좌표 역산 히트 테스트이며
  시각 편집기와 함께 002 에서 다룬다.

사용자는 그 패널을 실제로 써 본 뒤 정확히 그 이연분을 요구했다: **"도형 팔레트를 두고, 도형을 드래그 및
리사이즈. 컴포넌트 클릭하여 속성 설정."** 본 SPEC 의 중심은 이 세 문장이며, 나머지는 그 셋을 성립시키기
위해 필요한 만큼만 담는다.

001 출시 이후 이미 고친 사용성 결함 둘(새로 더한 요소가 아무것도 그리지 않던 문제 — 보이는 기본 스타일과
계단식 오프셋을 심어 해결, 요소 설정이 모두 펼쳐져 있어 복잡하던 문제 — 행을 접이식으로 바꿔 해결)은
마찰을 줄였을 뿐 **배치가 여전히 타이핑된 숫자라는 사실을 바꾸지 않았다**. 두 번째 수정은 본 SPEC 에
직접적인 제약을 남긴다: 캔버스 선택이 속성 편집으로 이어질 때 **"모두 펼침" 상태를 되살리면 안 된다**
(아래 §명세 §선택과 속성 편집의 연결).

### 순서 — 004 의 권고를 사용자 지시가 덮어썼다

SPEC-CANVAS-004(설비 심볼 라이브러리)는 §순서 절에서 **"004 가 002·003 보다 먼저다"** 를 권고했다. 근거는
둘이었다: (1) 사용자가 보고한 결핍은 불편이 아니라 "놓을 것이 없다" 였고, (2) 004 의 `group` 노드가 002 에게
드래그·히트 테스트의 자연스러운 단위를 선물한다는 것. **사용자가 002 를 먼저 하도록 지시했으므로 그 순서
권고는 무효화되었다.** 이 SPEC 은 그 사실을 감추지 않고, 004 가 이겼을 근거 (2) 를 **전방 호환 의무**로
바꾸어 갚는다(REQ-06) — 히트 결과를 레코드로 돌려주고, 기하 쓰기를 한 함수로 모으고, 선택 키를 최상위
노드 id 로 두어, 004 가 `group` 을 얹을 때 002 의 계층을 다시 짜지 않게 한다.

004 문서의 §순서 절과 "그림이 필요한 자리는 002 가 이미 맡고 있다" 는 문장은 본 SPEC 의 결정(순서 역전,
배경 에셋 005 분리)과 어긋나므로 **후속 편집이 필요하다. 본 SPEC 은 004 의 문서를 수정하지 않는다.**

### 001 §위험 R5 는 해소되었다

001 은 "002 착수는 SPEC-CHART-004/005 의 편집 툴킷 API 가 안정된 뒤로 둔다" 는 선행 조건을 걸어 두었다.
**SPEC-CHART-004/005 는 main 에 머지되어 `status: completed` 이며, 따라서 R5 는 해소되었다.** 002 는 그
툴킷의 **순수 모듈 두 개**(`panelEditAlign.ts` · `panelEditSelection.ts`)를 재사용한다.

### 재사용의 경계 — DOM 드래그 층은 재사용할 수 없다

정찰로 확인한 사실이며 추정이 아니다.

- **`PanelDragLayer.tsx` 는 캔버스에 재사용할 수 없다.** 이 층은 `data-panel-drag` / `data-panel-resize`
  속성을 단 **DOM 노드**를 잡는다. 캔버스 요소는 잡을 DOM 노드가 없는 **칠해진 픽셀**이다. 게다가 그
  파일의 헤더 주석이 스스로 못박은 좌표 규약이 다르다 — **자리는 기준 상자(`data-panel-bounds`) 대비
  백분율, 크기는 절대 px**. 캔버스는 `heatmap/stage.ts` 규약의 **정규화 0..1** 이다. 같은 이유로
  `usePanelElementEdit.tsx` 도 쓸 수 없다(정렬 대상을 `querySelector('[data-panel-drag=...]')` 로 찾는다).
- **순수 모듈 둘은 재사용할 수 있다.** `panelEditAlign.ts`(`GRID_STEP_PERCENT` · `Box` ·
  `PanelElementBox<K>` · `AlignAxis` · `AlignMode` · `snapOffsetToGrid` · `computeAlignPatches<K>`)와
  `panelEditSelection.ts`(`PanelSelection<K>` · `EMPTY_SELECTION` · `nextSelection<K>` ·
  `clampGroupDelta` · `GroupMember`)는 DOM 무의존이고 `K extends string` 제네릭이다. 요소 id 가 문자열이므로
  제네릭 인자만 갈아 끼우면 그대로 들어간다. **백분율 ↔ 정규화 변환 비용은 ×100 한 번**이며, 그 대가는
  §명세 §스냅·정렬 재사용의 대가에 정확히 적는다.
- **`PanelEditGrid.tsx` 도 그대로 쓴다.** 격자를 DOM 요소가 아니라 `repeating-linear-gradient` 로 그리고
  `absolute inset-0` + `pointer-events-none` 이라, 좌표 변환이 아예 필요 없다.

### 오버레이 선례 — 히트맵이 이미 같은 문제를 풀었다

캔버스 2D 표면 위에 편집 손잡이를 얹는 문제는 이 코드베이스에서 처음이 아니다.
`heatmap/SensorPlacementOverlay.tsx`(z-24, 포인터 드래그로 정규화 좌표 갱신)와
`heatmap/FloorPlanTransformOverlay.tsx`(z-22, 네 모서리 크기 조절 핸들)가 **DOM 오버레이**로 그 일을 하고,
좌표 변환은 순수 모듈 `heatmap/placement.ts` 가 맡는다. 002 는 그 갈래를 따른다(§명세 §선택 오버레이).

### 범위 분할 (5개 SPEC 로 확장)

- SPEC-CANVAS-001 (완료): 패널 등록 + 도형 모델 + Canvas 2D 렌더러 + 데이터 바인딩 + 조건 규칙 표 + 설정 UI + 상태 전이 트위닝.
- **SPEC-CANVAS-002 (본 SPEC)**: 캔버스 내 시각 편집기 — 히트 테스트, 선택, 도형 팔레트, 드래그 이동, 크기 조절, 클릭 → 속성 편집 연동, 그리드 스냅, 정렬, z-order 조작.
- SPEC-CANVAS-003 (후속): 애니메이션 전량(반복 효과 + 값 구동), 고급 표현식 형태, 요소 복제.
- SPEC-CANVAS-004 (후속): 설비 심볼 라이브러리 — 코드 내장 카탈로그, `group` 노드, 스탬핑 배치, 겉모습 캐스케이드.
- **SPEC-CANVAS-005 (신설, 후속)**: 배경 에셋 레이어 — 도면·사진 배경. 001 로드맵이 002 에 배정했으나 본 SPEC 이 분리한다(근거는 아래).

### 배경 에셋을 002 에서 덜어내는 이유

001 의 로드맵은 배경 에셋을 002 에 배정했다. **본 SPEC 은 그것을 SPEC-CANVAS-005 로 옮긴다.** 이유는
편의가 아니라 축이 다르기 때문이다.

1. **비동기 이미지 로드가 rAF 루프 안으로 들어온다.** 001 REQ-05 는 "애니메이션할 것이 없는데 프레임을
   예약하지 않는다" 를 **금지 조항**으로 못박았다. 이미지 로드·디코드·캐시 수명주기는 그 루프 안에서
   완료 시점을 만들고, 그 시점마다 루프를 깨워야 한다. 004 는 같은 이유로 심볼을 이미지로 만드는 안(B)을
   기각하면서 **"`DrawContext2D` 에 `drawImage` 를 추가하지 않는다"** 를 자기 REQ-05 의 금지 조항으로
   삼았다. 002 가 배경을 위해 `drawImage` 를 들이면 그 금지 조항이 002 에서 깨진다.
2. **인증된 자산 왕복이 붙는다.** 자산은 인증 헤더가 필요해 `<img src>` 직접 참조가 불가능하고 JSON 으로
   받아 data-URL 로 바꿔 쓴다(`useFloorPlanSources.ts`). `POST/GET /api/v1/dashboard-assets` 를 쓰게 되므로
   **백엔드 접점이 생긴다** — 002 의 "백엔드 변경 0" 이 무너지지는 않지만(기존 엔드포인트다) 성격이 다른 축이
   한 SPEC 에 섞인다.
3. **`svgAsset.ts` 의 규율을 통째로 물려받는다.** 업로드 SVG 는 **인라인 금지, data-URL `<img>` 로만**
   그린다(스크립트 격리). SVG 문서의 `preserveAspectRatio` 가 CSS 를 이기고, sizeless SVG 의
   `naturalWidth/Height` 는 원본 크기가 아니다. 이것들은 그 자체로 SPEC 한 편 분량의 함정이다.
4. **저장 예산.** 대시보드 snapshot PUT 은 256KB 이고 그 예산을 대시보드 전체가 공유한다. 자산 API 가
   분리된 이유가 바로 그것이며, 배경을 다루는 SPEC 은 그 축을 정면으로 다뤄야 한다.

**이 분리는 004 의 (B) 기각을 약화시키지 않는다.** 004 가 이미지 심볼을 기각한 결정적 근거는 "규칙이 심볼
내부 부품을 지목할 수 없다" 이며, 그것은 배경 에셋이 002 에 있든 005 에 있든 그대로다. 다만 004 문서의
"그림이 필요한 자리는 002 가 이미 맡고 있다" 는 문장은 005 를 가리키도록 후속 편집이 필요하다.

### 그룹을 002 에서 덜어내는 이유

001 의 로드맵은 "그룹" 도 002 에 배정했다. 그러나 **004 가 `group` 노드를 자기 스키마의 중심으로 이미
설계했다**(부품이 로컬 좌표에 사는 1단 중첩, 복합 프레임 키, 겉모습 캐스케이드 4단 법칙). 002 가 별도의
영속 그룹 개념을 발명하면 같은 패널에 그룹이 둘이 된다. 그래서 002 의 "그룹" 은 **저장되지 않는 다중 선택
+ 무리 이동**뿐이며(선택은 런타임 상태다 — `panelEditSelection.ts` 헤더가 이미 그 규율을 적어 두었다),
영속 그룹은 004 의 몫이다.

### 백엔드 변경 0

패널 `config` 는 Go 쪽에서 불투명 JSON(`json.RawMessage`)으로 저장된다. 002 는 **기존 요소의 기하·스타일
필드를 다른 수단으로 쓸 뿐 스키마를 넓히지 않으므로** 신규 엔드포인트도, 스키마 변경도, 전송 계층 변경도
없다. 배경 에셋(자산 API 접점)을 005 로 뺀 것이 이 성질을 지킨다.

## 환경 (Environment)

- 플랫폼: 웹 프론트엔드(React 19 + TypeScript 5.9, Vite 6/Vitest, Tailwind v4). 백엔드 변경 없음.
- 확장 대상(SPEC-CANVAS-001 산출물, `web/src/pages/dashboard/panels/canvas/`):
  - `canvasConfig.ts` — `kind` 로 판별하는 `CanvasElement` 유니온(`rect`/`ellipse`/`line`/`text`), 정규화(0..1) 기하이며 **clamp 하지 않는다**(스테이지 밖 저술이 합법이다), 예외를 던지지 않는 관용 파서 `parseCanvasConfig`. `ElementStyle.fontSize` 는 스타일이지 기하가 아니다.
  - `canvasGeometry.ts` — `projectBox`/`projectLine`/`projectPoint`(정규화 → CSS px), `ellipseParams`(좌상단+크기 → 중심+반지름, 반지름은 절대값), `resolveTextOrigin(point, align, measuredWidth)`(정렬 기준점 + 실측 폭 → **좌측 끝 원점**), `toCanvasTextAlign`, `labelAnchor`(rect/ellipse 는 중심, line 은 중점, text 는 자기 기준점), `computeBackingSize`(DPR). **본 SPEC 의 히트 테스트는 이 투영의 역산이다.**
  - `drawElement.ts` — 최소 context 인터페이스 `DrawContext2D` 위의 얇은 층. `TEXT_BASELINE = 'middle'`, `textAlign` 은 `'left'` 고정, 글자 폭은 렌더 층이 `measureText` 로 재어 넘긴다. **`drawImage` 는 없다.**
  - `CanvasSurface.tsx` — `<canvas>` + DPR 백킹 버퍼 + `ResizeObserver` + 트윈 장부 + rAF 루프. 규율 셋: **유휴 정지**(진행 중 트윈이 없으면 다음 프레임 미예약) · **가시성 게이팅**(`VisibilitySource`) · **props 가 그대로면 아무것도 그리지 않음**(폴링 실패 시 마지막 프레임 보존). `scheduleFrame` 은 이미 예약된 프레임이 있으면 즉시 반환한다(프레임 내 합류).

## 요구사항 (Requirements — EARS)

EARS 5개 유형(Ubiquitous / Event-Driven / State-Driven / Optional / Unwanted)을 6개 모듈에 표현한다.

### REQ-01 — 편집 모드 게이팅 · 도형 팔레트 · 접근성 (Ubiquitous)

시스템은 **항상** 캔버스 편집을 기존 `usePanelEditMode` 의 **세 겹 게이팅**으로 켜고 꺼야 한다:
(1) `canEdit` — `onConfigChange` 가 있는가, (2) `dashboardEditMode` — 대시보드 편집모드인가,
(3) `forced` — 설정 미리보기처럼 항상 편집인 자리인가(그때 토글은 감춘다). 새 게이팅 개념을 만들지
않아야 한다.
시스템은 **항상** 편집이 꺼져 있으면 캔버스를 **표시 전용**으로 두어야 한다 — 선택되지 않고, 핸들이
없으며, 포인터를 가로채지 않는다(`PanelDragLayer` 의 "대시보드에 놓인 패널은 편집이 꺼져 있으면 표시만
남고 끌리지 않는다" 와 같은 규칙).
시스템은 **항상** 도형 팔레트를 두어야 하며, 팔레트의 각 항목은 목록 편집기의 추가 버튼과 **같은 생성
경로**(같은 씨앗 기하·같은 계단식 오프셋·같은 자동 펼침)를 호출해야 한다. 팔레트는 목록 버튼을
**대체하지 않는다** — 둘 다 남는다.
시스템은 **항상** 드래그가 **유일한 수단이 되지 않도록** 해야 한다. 기하·크기의 수치 입력은 그대로
남아야 하며, 선택 이동·크기 조절·순서 변경·요소 추가에는 각각 키보드로 도달 가능한 등가 수단이 있어야
한다(핸들은 초점을 받을 수 있는 요소이고 `aria-label` 을 가진다).
시스템은 **항상** 신규 i18n 키를 `ko.json` 과 `en.json` **양쪽**에 추가하고, 키 이름 안에 점을 넣지
않아야 한다.
시스템은 **항상** 신규 컴포넌트를 `web/src/pages/dashboard/panels/canvas/` 아래에 배치해야 한다.

### REQ-02 — 히트 테스트와 선택 (State-Driven)

**IF** 편집이 켜진 상태에서 캔버스에 포인터가 눌리면 **THEN** 시스템은 그 지점을 스테이지 CSS px 좌표로
바꾸고 요소 목록을 **배열 역순(뒤 = 위)으로 훑어 처음 맞은 요소 하나**를 골라야 한다 — 배열 순서가 001 의
유일한 z-order 이므로 뒤에 있는 것이 위에 있고, 위에 있는 것이 이긴다.
**IF** 요소가 `rect` 이면 **THEN** 투영된 px 박스를 양수 범위로 정규화한 뒤 집기 여유만큼 부풀려
점 포함으로 판정해야 한다.
**IF** 요소가 `ellipse` 이면 **THEN** `ellipseParams` 의 중심·반지름으로 타원 방정식 판정을 해야 하며,
반지름이 0 인 퇴화 도형은 여유 크기의 점 판정으로 폴백해야 한다(크기 0 요소가 영영 선택 불가가 되어
화면에서 되살릴 수 없게 되는 것을 막는다).
**IF** 요소가 `line` 이면 **THEN** 점–선분 거리로 판정하고, 임계는 `max(선 두께 / 2, 집기 여유)` 여야
한다 — 두께 1px 선은 여유 없이는 사실상 누를 수 없기 때문이다.
**IF** 요소가 `text` 이면 **THEN** `resolveTextOrigin` 이 낸 좌측 끝 원점과 실측 폭, 그리고
`textBaseline='middle'` 을 반영한 상자(세로 중심이 기준점)로 판정해야 한다. 실측 폭이 없으면 기준점
둘레의 여유 크기 상자로 폴백해야 한다.
**IF** 도형에 라벨이 붙어 있으면 **THEN** 시스템은 라벨에 **별도의 히트 영역을 주지 않아야 한다** —
라벨은 자기 기하가 없고(`labelAnchor` 로 파생된다) 따라서 따로 골라도 옮길 수 없기 때문이다. 라벨 위를
눌러도 그 요소가 선택된다. `kind:'text'` 는 글자가 곧 기하이므로 예외가 아니다.
**IF** 아무 요소도 맞지 않으면 **THEN** 시스템은 선택을 비우되 포인터 이벤트를 **가로채지 않아야 한다**
(미리보기의 휠 확대·패널 크기 조절이 종전대로 동작해야 한다).
**IF** 보조키(Shift/Ctrl/Cmd)와 함께 눌리면 **THEN** `nextSelection` 규칙으로 선택을 더하거나 빼야 한다.
**IF** 편집이 꺼지면 **THEN** 선택을 비워야 한다.

### REQ-03 — 드래그 이동과 크기 조절 (Event-Driven)

**WHEN** 선택된 요소 위에서 포인터가 눌리면 **THEN** 시스템은 Pointer Events(`pointerdown`/`pointermove`/
`pointerup`)와 `setPointerCapture` 로 드래그를 시작하고, 브라우저 기본 동작·상위 제스처와 겹치지 않도록
그 이벤트만 소비해야 한다.
**WHEN** 포인터가 움직이면 **THEN** 시스템은 이동량을 정규화 델타로 바꿔 선택된 **모든** 요소의 기하에
같은 값을 더하고, **끄는 동안 계속** `onConfigChange` 로 반영해 그림이 손을 따라오게 해야 한다
(`PanelDragLayer` 의 "미리보기가 즉시 따라와야 어디에 놓일지 보인다" 와 같은 계약).
**WHEN** 요소가 스테이지 밖으로 나가면 **THEN** 시스템은 좌표를 **clamp 하지 않아야 한다**(가정 A5).
**WHEN** `rect`/`ellipse` 의 8개 핸들(모서리 4 + 변 4) 중 하나가 끌리면 **THEN** 해당 모서리·변만 움직여
박스를 다시 잡아야 하며, 반대 변을 넘어서면 박스를 **정규화**해(`x = min`, `w = |w|`) 잡은 핸들이 커서
아래 남도록 해야 한다.
**WHEN** `line` 의 끝점 핸들 2개 중 하나가 끌리면 **THEN** 그 끝점만 움직여야 하고, 선 몸통이 끌리면 두
끝점이 함께 움직여야 한다.
**WHEN** `text` 의 글자 크기 핸들이 끌리면 **THEN** `style.fontSize` 를 파서가 허용하는 범위 안에서
바꿔야 한다 — text 요소에는 폭·높이가 없으므로 **박스 핸들을 만들지 않는다**(`PanelDragLayer` 가 이미
같은 비대칭을 같은 방식으로 해결했다).
**WHEN** Shift 가 눌린 채 모서리 핸들이 끌리면 **THEN** 종횡비를 유지해야 하고, Shift 가 눌린 채 선
끝점이 끌리면 0°/45°/90° 로 죄어야 한다.
**WHEN** `pointerup` 또는 `pointercancel` 이 오면 **THEN** 드래그를 끝내고 **마지막 유효 위치를 그대로
확정**해야 한다 — 되돌리면 사용자가 한 일이 소리 없이 사라진다.

### REQ-04 — 스냅 · 정렬 · z-order · 속성 편집 연동 (Optional)

**Where** 격자 붙임이 켜져 있으면 시스템은 `panelEditAlign.snapOffsetToGrid` 를 재사용해 드래그 델타를
격자에 맞춰야 하며, 그때 오프셋 상한을 **무한대로 넘겨** 이 모듈의 기본 상한(±40)이 캔버스 드래그를
스테이지의 40% 지점에 조용히 붙잡는 일이 없게 해야 한다.
**Where** 격자를 보여 줄 자리가 있으면 시스템은 `PanelEditGrid` 를 그대로 재사용해야 한다(신규 격자
컴포넌트를 만들지 않는다).
**Where** 요소가 2개 이상 선택되면 시스템은 `panelEditAlign.computeAlignPatches` 를 재사용해 가로·세로
6가지 정렬을 제공할 수 있다.
**Where** 요소가 선택된 상태에서 z-order 조작이 요청되면 시스템은 목록 편집기가 이미 쓰는 **배열 순서
이동과 같은 연산**을 호출해야 한다 — 001 의 z-order 수단은 배열 순서 하나뿐이므로 두 번째 수단을 만들지
않는다.
**Where** 캔버스에서 요소 하나가 선택되면 시스템은 목록 편집기에서 **그 요소의 행 하나만** 펼치고 시야로
스크롤해야 한다. 캔버스가 펼친 행은 다음 선택 때 도로 접어야 하며, **사용자가 손으로 펼친 행은 접지
않아야 한다**. 요소가 둘 이상 선택되면 **아무 행도 자동으로 펼치지 않아야 한다**(펼침이 쌓이면 이미 고친
"설정이 모두 펼쳐져 복잡하다" 로 되돌아간다).
**Where** 목록 편집기가 마운트되지 않은 자리(대시보드에 놓인 패널)라면 선택은 오버레이만 움직이면 된다.
**Where** 키보드로 조작하면 시스템은 방향키로 선택을 미세 이동하고 Shift+방향키로 한 격자 칸을 이동하게
할 수 있다.

### REQ-06 — SPEC-CANVAS-004 전방 호환 (Ubiquitous)

004 가 뒤에 오므로, 002 는 004 의 `group` 노드가 얹힐 자리를 미리 비워 두어야 한다. **004 의 기능을
구현하지 않되, 004 가 002 의 계층을 다시 짜지 않아도 되게 한다.**

시스템은 **항상** 히트 테스트 결과를 벌거벗은 문자열이 아니라 **레코드**로 돌려주어야 한다:
`{ nodeId: string; partId?: string }`. 002 는 `partId` 를 절대 채우지 않으며, 004 가 채운다. 이로써 004 는
호출부의 시그니처를 바꾸지 않는다.
시스템은 **항상** 선택·오버레이를 **최상위 배열 원소의 id**(`nodeId`)로 키잉해야 한다 — 004 는 부품에
복합 키(`groupId/partId`)를 쓰되 최상위 키는 001·002 와 같게 유지하기로 이미 설계되어 있다.
시스템은 **항상** 기하 쓰기를 **한 함수**(`patchNodeGeometry(elements, nodeId, geometry)`)로 모아야 한다 —
004 가 그룹 분기를 더할 지점이 한 곳이 되게 한다.
시스템은 **항상** 그룹이 존재하게 되는 시점의 규칙을 지금 밝혀 두어야 한다: **드래그·선택의 단위는
그룹이며 부품이 아니다.** 부품 단위 선택(그룹 안으로 들어가기)은 004 의 몫이다. 002 는 이 규칙을 문서로
못박되 구현하지 않는다.
시스템은 **항상** 배열 위치(index)를 비동기 경계 너머로 들고 다니지 **않아야 한다** — 드래그 중 요소가
재정렬되면 index 는 다른 것을 가리킨다. 식별은 언제나 `nodeId` 다.

## 명세 (Specifications)

### 히트 테스트 — 역산이 아니라 순방향 투영 후 px 판정

001 은 "요소 선택·툴팁은 DOM 이벤트가 아니라 **좌표 역산 히트 테스트**다" 라고 적었다. 002 는 그 문제를
풀되 **역산을 하지 않는다.** 대신 요소를 `canvasGeometry` 의 기존 함수로 **순방향 투영**한 뒤, 포인터를
스테이지 로컬 px 로 옮겨 px 공간에서 판정한다. 포인터 → 스테이지 로컬은 컨테이너 원점을 빼는 뺄셈
하나이며(히트맵 `placement.toNormalized` 가 하는 일에서 나눗셈을 뺀 것이다), 도형별 역산은 존재하지 않는다.

이 선택의 이유는 하나다: **집기 여유는 화면 양이다.** `HIT_TOLERANCE_PX = 6` 은 패널이 크든 작든 6px 여야
한다. 정규화 공간에서 여유를 주면 같은 숫자가 큰 패널에서는 헐거워지고 작은 패널에서는 좁아진다. 부수
효과로 투영 구현이 하나로 유지된다 — 렌더와 히트 테스트가 **같은 함수**를 쓰므로 둘이 갈라질 수 없다.

`canvasHitTest.ts`(신규, DOM 무의존):

```
HIT_TOLERANCE_PX = 6          // 집기 여유(CSS px). 두께 1px 선을 누를 수 있게 하는 값이다.

CanvasHit { nodeId: string; partId?: string }   // partId 는 004 자리(REQ-06). 002 는 채우지 않는다.

hitTest(
  elements: readonly CanvasElement[],
  point:    PxPoint,                       // 스테이지 로컬 CSS px
  stage:    StageSize,
  textWidths: Record<string, number>,      // 렌더 층이 잰 폭. DOM 무의존을 지키는 축이다.
): CanvasHit | undefined
```

- 순회는 **배열 역순**이다. 배열 순서 = 그리기 순서(뒤가 위)이므로 역순의 첫 일치가 곧 최상위다.
- `style.visible === false` 인 요소는 건너뛴다 — 보이지 않는 것을 잡을 수는 없다.
- 도형별 판정:

| kind | 판정 | 여유 | 퇴화 처리 |
|------|------|------|-----------|
| `rect` | 정규화(양수 범위) px 박스에 점 포함 | 사방 `+6px` | 폭·높이 0 → 여유 상자로 판정 |
| `ellipse` | `((px-cx)/rx)² + ((py-cy)/ry)² ≤ 1` | `rx`, `ry` 각각 `+6px` | `rx` 또는 `ry` 가 0 → 여유 반지름의 점 판정 |
| `line` | 점–선분 거리 ≤ `max(strokeWidth/2, 6)` | 위 식에 포함 | 두 끝점이 같음 → 점 판정 |
| `text` | 원점 상자에 점 포함 | 사방 `+6px` | 실측 폭 없음 → 기준점 둘레 여유 상자 |

- **`text` 상자의 수직 기준이 이 명세에서 가장 틀리기 쉬운 지점이다.** `drawElement.TEXT_BASELINE` 이
  `'middle'` 이므로 기준점 `y` 는 상자의 **세로 중심**이다. 상자는
  `{ x: origin.x, y: origin.y - fontSize/2, w: measuredWidth, h: fontSize }` 이며, `origin` 은
  `resolveTextOrigin(projectPoint(geo, stage), align, measuredWidth)` 다. 상단으로 착각하면 글자 위쪽
  절반을 눌러도 잡히지 않고, 아래쪽을 누르면 아무것도 없는데 잡힌다.
- **라벨은 히트 테스트에 따로 참여하지 않는다.** 도형의 라벨은 `labelAnchor` 에서 파생되는 위치를 가질
  뿐 자기 기하가 없다. 따로 고를 수 있게 만들면 사용자는 **고를 수는 있으나 옮길 수 없는 것**을 손에
  쥐게 된다. 라벨 위를 눌러도 그 도형이 선택된다.

**실측 폭의 출처.** `drawElements` 는 이미 프레임마다 모든 텍스트·라벨에 `measureText` 를 부른다. 002 는
그 반환 타입만 `void → Record<string, number>` 로 넓혀(요소 id → 잰 폭) 표면이 오버레이에 넘기게 한다.
**인자는 바뀌지 않으며**, 반환값을 무시하는 기존 호출부는 영향이 없고, 측정은 여전히 프레임당 1회다.
두 번째 측정원을 만들지 않는다는 REQ-05 금지 조항이 이것으로 지켜진다. 폭은 **직전에 그린 프레임**의
값이므로 최악의 지연은 한 프레임이며, 그 지연이 틀리게 할 수 있는 것은 텍스트 상자의 폭뿐이다(도형은
투영만으로 정해진다).

### 어디서 편집하는가 — 둘 다, 기존 세 겹 게이팅으로

**설정 다이얼로그의 라이브 미리보기와 대시보드에 놓인 패널 양쪽에서 편집한다.** 새 게이팅을 만들지 않고
기존 `usePanelEditMode` 를 쓴다.

| 자리 | `canEdit` | `dashboardEditMode` | `forced` | 결과 |
|------|-----------|---------------------|----------|------|
| 설정 미리보기 | true | 무관 | **true** | 항상 편집, 토글 감춤 |
| 대시보드 · 편집모드 · 토글 켜짐 | true | true | false | 편집 |
| 대시보드 · 편집모드 · 토글 꺼짐 | true | true | false | 표시 전용 + 토글 버튼 |
| 대시보드 · 읽기 전용 뷰 | false 또는 편집모드 아님 | false | false | 표시 전용, 토글 없음 |

이는 `PanelDragLayer` 가 "대시보드에 놓인 패널은 편집이 꺼져 있으면 표시만 남고 끌리지 않는다" 로 정한
규칙과 같고, 히트맵·게이지·통계·바·파이가 전부 따르는 규칙이다. 캔버스만 다르게 두면 사용자가 패널마다
다른 규칙을 배워야 한다.

**미리보기의 다른 조작과 부딪히지 않는 방법.** 미리보기 래퍼에는 이미 `onWheel={handlePreviewWheel}`
(휠 확대)이 걸려 있고 패널 크기 조절도 있다. `PanelDragLayer` 헤더는 바로 이 이유로 "그 밖을 잡으면
아무 일도 없다" 를 규칙으로 삼았다. 캔버스도 같다 — **아무 데나 잡아서 끌리지 않는다.**

- `pointerdown` 은 **오버레이 루트**가 받는다(0.2.0 에서 확정 — HISTORY). 히트가 **있으면** 선택·드래그를
  시작하고 그 이벤트를 소비한다(`stopPropagation` + `preventDefault`).
- 히트가 **없으면** 선택만 비우고 **이벤트를 소비하지 않는다.** 상위의 휠 확대·크기 조절이 종전대로
  동작한다. **어느 노드가 받는가는 이 규칙과 무관하다** — 중요한 것은 소비 여부뿐이다.
- 핸들·팔레트는 같은 DOM 오버레이 안에 있고 스스로 이벤트를 끊으므로, 핸들을 잡은 포인터는 몸통 히트
  테스트에 닿지 않는다.

### 선택 오버레이 — 캔버스에 칠하지 않고 DOM 층으로 둔다

두 안을 저울질했고 **DOM 오버레이**를 채택한다.

**채택 근거 셋.**

1. **이 코드베이스가 이미 그 답을 골랐다.** `heatmap/SensorPlacementOverlay.tsx`(마커 드래그, z-24)와
   `heatmap/FloorPlanTransformOverlay.tsx`(네 모서리 핸들, z-22)가 Canvas 2D 표면 위에 DOM 으로 겹친다.
   같은 대시보드 안에서 같은 문제에 두 개의 답을 두는 비용을 치를 사람이 없다.
2. **핸들이 진짜 요소가 되어 키보드·접근성이 따라온다.** 핸들은 초점을 받는 버튼이고 `aria-label` 을
   가지며 호버가 CSS 다. 칠한 핸들은 이 전부를 손으로 다시 만들어야 하고, 그것은 REQ-01 의 접근성
   요구와 정면으로 부딪힌다.
3. **유휴 정지 보장을 건드리지 않는다 — 이것이 결정적이다.** 오버레이를 rAF 루프 안에 칠하면 선택·호버·
   드래그 같은 **편집기 상태가 001 이 유휴로 만들려고 지은 그 루프 안으로 들어온다.** 호버 한 번에
   프레임을 깨워야 하고, "트윈이 없으면 프레임을 예약하지 않는다"(REQ-05 금지 조항, AC-E6)에 예외가
   생긴다. 예외가 하나 생기면 그 조항은 더 이상 기계적으로 검증되지 않는다.

**대가는 정확히 이것이다: 투영이 DOM 좌표에 한 번 더 필요하다.** 이 대가를 중복이 아니게 만드는 장치가
둘이다.

- 오버레이는 `projectBox`/`projectLine`/`projectPoint`/`ellipseParams` — **같은 함수**를 쓴다. 투영
  구현은 여전히 하나다.
- 오버레이는 스테이지 크기를 **스스로 재지 않는다.** `CanvasSurface` 가 `ResizeObserver` 로 이미 잰
  `StageSize` 를 그대로 넘겨받는다(아래 §표면의 오버레이 슬롯). 측정원이 하나이므로 핸들이 도형에서
  미끄러질 수 없다.

**기각한 안(캔버스에 칠하기)의 유일한 장점**은 "그림의 출처가 하나" 라는 것이다. 그러나 위 3번이 그
장점의 값보다 크다. 유휴 정지는 001 이 기능이 아니라 **금지 조항**으로 못박은 성질이고, 그것을 편집기
편의를 위해 무르는 것은 대시보드 전체의 발열·배터리를 담보로 잡는 일이다.

**표면의 오버레이 슬롯.** `CanvasSurface` 에 선택 prop **하나**를 더한다.

```
overlay?: (ctx: { stage: StageSize; textWidths: Record<string, number> }) => React.ReactNode
```

미지정이면 **001 과 동작이 완전히 같다**(오버레이 없음, 추가 DOM 노드 없음, 추가 프레임 없음). 무동작
보장이 여기서도 성립한다.

**포인터 통과 슬롯(`onCanvasPointerDown`/`Move`/`Up`/`Cancel`)은 두지 않는다.** 0.1.0 은 `<canvas>` 가
포인터를 받는 형상을 그렸고 T3 이 그대로 구현했으나, 오버레이가 서면서 포인터는 **오버레이 루트**가
받는 것으로 확정되었다(HISTORY 0.2.0). 그 넷은 호출부가 하나도 없는 API 로 남았고, 부르는 곳이 없는
통과 슬롯은 이 파일을 다시 고칠 004 에게 거짓말이 된다(위험 R4). 표면은 포인터 리스너를 **아예 달지
않으므로** "표면은 포인터로 아무것도 하지 않는다" 는 무조건적 보장이 되었다.

### 도형 팔레트

- 자리: 편집이 켜졌을 때 스테이지 모서리에 뜨는 **떠 있는 작은 띠**(오버레이 안, `pointer-events-auto`).
  4종(`rect`/`ellipse`/`line`/`text`) 버튼과 격자 붙임 토글, 정렬 버튼이 함께 산다.
- **목록 편집기의 추가 버튼을 대체하지 않는다.** 그 버튼들은 포인터를 쓰지 않는 경로이자 이미 테스트에
  묶여 있는 표면이다(`canvas-element-add-<kind>`). 팔레트는 **같은 컨트롤을 캔버스 옆으로 한 벌 더 낸
  것**이며, 둘은 같은 함수를 부른다.
- **클릭해서 놓기**이며 팔레트에서 끌어다 놓기가 아니다. 끌어다 놓기는 드래그 고스트·드롭 좌표·취소
  경로가 필요한 **두 번째 드래그 기구**인데, 그것이 주는 이득은 클릭 배치가 이미 준다 — 놓인 요소가
  **즉시 선택되므로 사용자의 바로 다음 동작이 배치 드래그**다.
- **어디에 놓이는가**: 목록 편집기의 `addElement(kind)` 와 **같은 경로**를 부르므로 같은 씨앗 기하와
  같은 계단식 오프셋이 적용된다(연속으로 놓아도 겹쳐 쌓이지 않는다). 팔레트가 추가로 하는 일은
  **새 요소를 선택 상태로 만드는 것** 하나다. 배치 규칙을 둘로 두지 않기 위한 결정이다(가정 A7).

### 크기 조절 — 종류마다 다르고, 그 비대칭을 감추지 않는다

| kind | 핸들 | 무엇이 바뀌는가 | Shift |
|------|------|-----------------|-------|
| `rect` · `ellipse` | **8개** — 모서리 4 + 변 4 | `geometry.{x,y,w,h}` | 모서리 드래그에서 종횡비 유지 |
| `line` | **2개** — 끝점 2 | `geometry.{x1,y1}` 또는 `{x2,y2}` | 0°/45°/90° 로 죔 |
| `text` | **1개** — 글자 크기 | `style.fontSize` (기하가 아니다) | 없음 |

- **`text` 에 박스 핸들을 만들지 않는다.** text 요소의 기하는 정렬 기준점 하나이고 크기는 `fontSize` 라는
  **스타일**이다. 없는 폭·높이를 편집기가 발명하면 그 값은 config 에 저장할 곳이 없다.
  `PanelDragLayer` 가 이미 같은 비대칭을 같은 방식으로 풀어 두었다 — "`data-panel-resize` 를 잡으면 그
  요소의 **글자 크기**가 바뀐다."
- 박스 뒤집힘: 핸들이 반대 변을 넘어가면 쓰는 쪽이 박스를 **정규화**한다(`x = min(x, x+w)`, `w = |w|`).
  001 이 음수 크기 박스를 그릴 수 있게 해 둔 것은 **읽기 경로의 견고성**이지 편집기가 만들어야 할 값이
  아니다. 정규화하지 않으면 뒤집는 순간 잡은 핸들이 커서에서 떨어져 나간다.
- 핸들 크기·색은 `FloorPlanTransformOverlay` 의 모서리 핸들 어휘를 따른다(같은 대시보드 안에서 손잡이가
  두 모양이 되지 않게 한다).

### 클릭 → 속성 편집: 선택과 목록 편집기의 연결

**떠 있는 별도 속성 패널을 만들지 않는다.** 그것은 목록 편집기의 모든 컨트롤을 한 벌 더 만드는 일이고,
두 곳이 갈라질 자리를 만든다. 대신 **캔버스 선택이 기존 목록 편집기를 조종한다.**

- 요소 하나가 선택되면 그 행을 펼치고 시야로 스크롤한다.
- **캔버스가 펼친 행은 최대 하나다.** 다음 선택 때 이전 것을 접는다.
- **사용자가 손으로 펼친 행은 접지 않는다.** 그래서 편집기는 `expandedIds` 옆에 "캔버스가 펼친 id"
  한 개를 따로 들고, 그것만 회수한다.
- **둘 이상 선택되면 아무 행도 자동으로 펼치지 않는다.** 선택된 행에는 표시만 남긴다. 이 규칙이 없으면
  다중 선택 한 번에 화면이 다시 "설정이 모두 펼쳐진" 상태가 되고, 그것은 이미 고친 결함이다.

**선택 상태를 어디에 두는가.** 미리보기(`CanvasPanel`)와 요소 편집기(`CanvasElementsEditor`)는
`PanelSettingsDialog.tsx` 안의 서로 다른 자리에 마운트된다. 그 파일(8,000행+)에 상태를 더하는 것은 001
§위험 R4 를 되살리는 일이므로, **작은 provider 를 `canvas/` 안에 두고** 다이얼로그에는 두 마운트 지점을
감싸는 줄만 더한다. 대시보드에 놓인 패널에는 목록 편집기가 없으므로 provider 없이도 동작해야 한다
(context 기본값 = 로컬 선택).

### 드래그 기구

- **Pointer Events + `setPointerCapture`.** 마우스 이벤트가 아니라 포인터 이벤트인 이유는 터치·펜이 같은
  코드로 동작하기 때문이고, capture 를 쓰는 이유는 포인터가 스테이지를 벗어나도 이벤트가 계속 오기
  때문이다. `SensorPlacementOverlay` 는 capture 대신 루트를 `pointer-events-auto` 로 되돌리는 수법을
  쓰는데, 그것은 **누른 대상이 드래그 도중 언마운트되기 때문**이다(팔레트 칩이 마커가 된다). 캔버스에는
  그런 언마운트가 없으므로 capture 가 더 단순하고 정확하다.
- `pointercancel` 은 브라우저·OS 가 끊은 경우다. **마지막 유효 위치를 확정**하고 끝낸다(되돌리면 사용자가
  한 일이 사라진다).
- **스테이지 밖으로 나가도 clamp 하지 않는다**(가정 A5). 히트맵 `placement.toNormalized` 는 반대로
  clamp 하는데, 도면 밖 센서는 뜻이 없기 때문이다. 캔버스에서 반쯤 걸친 도형은 뜻이 있는 저술이다.
  전부 나간 요소의 회수 경로는 **목록 편집기의 수치 입력**이며, 그 입력이 항상 남아 있어야 하는 이유
  중 하나가 이것이다(REQ-01).
- **다중 선택과 무리 이동**: `panelEditSelection.ts` 의 `PanelSelection<string>` · `EMPTY_SELECTION` ·
  `nextSelection` 을 그대로 쓴다(요소 id 가 문자열이므로 제네릭이 그대로 맞는다). 무리 이동은 같은 정규화
  델타를 선택된 모든 요소에 더한다.
- **`clampGroupDelta` 는 쓰지 않는다.** 그 함수는 무리 중 하나가 오프셋 상한에 닿으면 무리 전체를
  멈추는 계산인데, 캔버스에는 상한이 없다(clamp 하지 않는다). 상한이 없는데 죄는 함수를 부르면 하는 일이
  없고, **아무 일도 하지 않는 호출은 읽는 사람에게 상한이 있다고 거짓말한다.**
- 마퀴(고무줄) 선택은 **범위 밖**이다 — 점 포함이 아니라 상자 교차라는 다른 판정이 필요하고, 빈 캔버스
  드래그라는 제스처를 써야 하는데 그 제스처는 지금 미리보기의 상위 조작으로 흘려보내기로 했다.

### 스냅·정렬 재사용의 대가

정규화(0..1)와 백분율 오프셋 사이의 변환은 **×100** 하나다. 그래서 두 순수 모듈을 그대로 쓸 수 있지만,
공짜는 아니며 대가가 셋이다. 여기에 남겨 두어야 나중에 원인 모를 동작으로 나타나지 않는다.

1. **상한을 무한대로 넘겨야 한다.** `snapOffsetToGrid` 와 `computeAlignPatches` 는 결과를
   `clampPercentOffset(value, limit)` 로 죄고 기본 `limit` 이 `PANEL_OFFSET_LIMIT = 40` 이다. 그 기본값을
   그대로 두면 **캔버스 드래그가 스테이지의 40% 지점에 조용히 붙잡힌다.** `Number.POSITIVE_INFINITY` 를
   넘기면 `Math.min(Math.max(v, -Inf), Inf) === v` 이므로 무동작이다.
2. **스냅 기준은 요소의 중심이다.** `snapOffsetToGrid` 는 중심을 격자에 맞춘다(다른 패널의 `+` 표식과
   같은 기준). 캔버스에서도 그 어휘를 그대로 쓴다 — 여기서만 좌상단을 맞추면 같은 대시보드 안에서
   격자가 두 뜻을 갖는다.
3. **`base.offset` 은 언제나 0 이다.** 그 모듈은 "흐름상 시작 자리 + 오프셋" 모델이라 잡는 순간의 오프셋을
   되짚는다. 캔버스에는 흐름이 없고 **저장된 값이 곧 절대 자리**이므로 `base = { offset: 0, rectStart: 잡는
   순간의 px 시작, rectLen: px 길이 }`, `bounds = { start: 0, len: 스테이지 축 길이 }` 로 넣는다.

격자 간격은 `GRID_STEP_PERCENT`(10%, 축당 10칸)를 그대로 쓴다. 캔버스 전용 격자 상수를 만들지 않는다 —
격자 어휘가 둘이 되는 비용이 더 크다. 더 고운 격자가 필요해지면 그 함수의 `step` 인자가 이미 있으므로
한 줄 변경이며 새 모듈이 아니다.

정렬은 `computeAlignPatches` 에 **투영된 px 상자**를 `rect` 로, `offsetX/offsetY = 0`,
`limit = Infinity`, `bounds = { left: 0, top: 0, width, height } = 스테이지` 로 넣고, 돌려받은 백분율
오프셋을 ÷100 하여 정규화 델타로 쓴다.

### 렌더 루프를 깨우는 시점 (유휴 정지 보존)

001 REQ-05 는 "애니메이션할 것이 없는데 프레임을 계속 예약하지 않는다" 를 금지 조항으로 두었다. 편집기는
프레임을 요구한다. 두 문장이 부딪히지 않는 이유를 정확히 적는다.

- **새 깨우기 경로를 만들지 않는다.** `CanvasSurface` 는 이미
  `[elements, targetStyles, texts, panelTween, background, display]` 가 바뀌면 프레임을 요청한다. 드래그가
  루프를 깨우는 이유는 그것이 `elements` 를 바꾸기 때문이며, 이는 설정 다이얼로그에서 수치를 고칠 때
  **오늘도 일어나는 그 경로**다.
- **선택·호버·핸들·팔레트는 루프를 깨우지 않는다.** 전부 DOM/CSS 이며 캔버스 props 를 건드리지 않는다.
- **프레임 안에서 `pointermove` 가 합류한다.** `scheduleFrame` 은 이미 예약된 프레임이 있으면 즉시
  반환하므로, 한 프레임 사이에 이벤트가 열 번 와도 그림은 한 번 그려진다.
- **드래그가 끝나면 루프는 유휴로 돌아간다.** 마지막 쓰기가 한 프레임을 예약하고, 그 프레임에서 진행 중
  트윈이 없으면 `drawFrame` 이 `allDone === true` 를 돌려주어 다음 프레임이 예약되지 않는다. **편집기
  전용 정리 코드가 필요 없다.**
- **기하는 트윈되지 않는다.** 트윈 장부는 `ResolvedStyle` 만 담고 기하를 담지 않으므로 드래그는 즉시
  반영된다(가정 A6). 끄는 손과 그림 사이에 300ms 가 끼면 조작이 성립하지 않으므로 이것은 필요한 성질이다.
- 보이지 않을 때 프레임을 예약하지 않는다는 규율도 그대로다 — 편집 오버레이는 보이지 않는 패널에
  마운트되지 않는다.

### SPEC-CANVAS-004 와의 접점 (전방 호환 최소분)

004 는 `group` 노드를 도입해 부품이 **그룹 로컬 좌표**에 살게 하고, 프레임 상태를 복합 키
(`groupId/partId`)로 든다. 002 가 먼저 오므로 002 가 갚아야 할 최소분은 넷이며, **그 이상은 하지 않는다.**

1. **히트 결과는 레코드다** — `{ nodeId, partId? }`. 002 는 `partId` 를 채우지 않는다. 004 가 채울 때
   호출부 시그니처가 바뀌지 않는다.
2. **선택 키는 최상위 노드 id 다.** 004 도 최상위 원시형에 대해서는 001·002 와 같은 평평한 키를 유지하기로
   설계되어 있으므로, 002 가 그 키를 쓰면 004 에서 다시 키를 갈아 끼울 일이 없다.
3. **기하 쓰기는 한 함수를 지난다** — `patchNodeGeometry(elements, nodeId, geometry)`. 004 는 여기에 그룹
   분기를 더한다. 드래그 층은 배열 index 를 비동기 경계 너머로 들고 다니지 않는다.
4. **단위 규칙을 지금 밝힌다** — 그룹이 생기면 **드래그·선택의 단위는 그룹이고 부품이 아니다.** 004 의
   §순서 절이 "004 의 `group` 노드는 002 에게 드래그·히트 테스트의 자연스러운 단위를 선물한다" 고 적은
   그 단위이며, 순서가 뒤집혔으므로 002 가 그 규칙을 먼저 문서로 확정한다. 부품 단위 선택(그룹 안으로
   들어가기)은 004 의 몫이며 002 는 구현하지 않는다.

002 는 `kind: 'group'` 을 도입하지 않고, 004 의 캐스케이드·복합 키·중첩 투영을 구현하지 않는다.
