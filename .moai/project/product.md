# xflow - 프로덕트 정의서

## 프로젝트 개요

**프로젝트명**: xflow
**태그라인**: IoT 데이터 스트림을 처리하기 위한 Flow Based Programming 플랫폼

## 비전 및 목표

xflow는 IoT 환경에서 발생하는 대량의 데이터 스트림을 효율적으로 수집, 처리, 시각화하기 위한 경량 Flow Based Programming(FBP) 플랫폼이다. Node-RED의 직관적인 비주얼 프로그래밍 개념을 계승하면서도, Go 언어 기반의 고성능 런타임 엔진과 엔터프라이즈급 보안 체계를 결합하여 프로덕션 환경에서 신뢰할 수 있는 데이터 파이프라인 플랫폼을 제공하는 것을 목표로 한다.

### 핵심 목표

- **고성능 스트림 처리**: Go 기반 FBP 엔진으로 높은 동시성과 낮은 지연시간 달성
- **직관적 시각적 편집**: 드래그 앤 드롭 방식의 웹 기반 플로우 에디터 제공
- **프로토콜 다양성**: MQTT, HTTP, WebSocket, gRPC 등 주요 IoT 프로토콜 네이티브 지원
- **확장 가능한 아키텍처**: Go 플러그인 및 WASM 기반 커스텀 노드 확장 시스템
- **CLI/Web 동등한 기능**: xflow(CLI)와 웹 대시보드 모두 xflowd(데몬 서버)의 REST API를 통한 원격 접속 클라이언트로 동작
- **보안 최우선**: 인증/인가, 데이터 암호화, 감사 로깅 등 엔터프라이즈급 보안
- **구성 요소별 관찰성**: 모든 시스템 구성 요소가 개별적으로 동작 상태 추적 및 디버깅 가능
- **런타임 생명주기 제어**: 플로우, 노드, 에이전트 등 모든 구성 요소를 동작 중 초기화/멈춤/재개 가능, 설정 변경도 런타임에 반영

## 대상 사용자

### 1. IoT 개발자 및 시스템 엔지니어

- IoT 디바이스에서 수집되는 센서 데이터를 실시간으로 처리해야 하는 개발자
- 다양한 프로토콜(MQTT, HTTP, WebSocket)을 통해 디바이스와 통신하는 시스템 엔지니어
- 비주얼 플로우 에디터를 통해 데이터 파이프라인을 빠르게 프로토타이핑하려는 엔지니어

### 2. 데이터 파이프라인 관리자

- 다수의 데이터 소스에서 들어오는 스트림을 변환, 필터링, 라우팅하는 데이터 엔지니어
- ETL/ELT 파이프라인을 시각적으로 구성하고 모니터링하는 관리자
- 데이터 품질 검증 및 이상 감지 파이프라인을 운영하는 담당자

### 3. DevOps/인프라 엔지니어

- CLI 도구를 통해 플로우 배포와 관리를 자동화하려는 DevOps 엔지니어
- 컨테이너 환경(Docker, Kubernetes)에서 xflow를 운영하는 인프라 엔지니어
- CI/CD 파이프라인에 xflow 배포를 통합하려는 SRE

## 설계 원칙: 구성 요소별 관찰성 (Observability)

시스템을 구성하는 모든 요소는 개별적으로 디버깅을 위한 동작 상태 추적이 가능해야 한다.

- **컴포넌트별 로그 분리**: Flow Engine, Agent, Node, Script, Plugin 각각이 독립된 로그 스트림 생성
- **로그 레벨 개별 설정**: 컴포넌트별로 DEBUG/INFO/WARN/ERROR 레벨을 독립적으로 설정 가능
- **런타임 로그 레벨 변경**: 재시작 없이 실행 중 특정 컴포넌트의 로그 레벨을 동적으로 변경
- **구조화된 로깅**: 모든 로그에 컴포넌트 ID, 타임스탬프, 컨텍스트 정보 포함 (slog 기반)
- **메트릭 수집**: 컴포넌트별 처리량, 지연시간, 에러율, 리소스 사용량 개별 추적
- **트레이싱**: 데이터가 플로우를 통과하는 경로를 추적하여 병목 지점 식별

적용 대상:

| 구성 요소 | 추적 항목 |
|-----------|----------|
| Flow Engine | 플로우 상태 전이, 스케줄링 결정, 백프레셔 이벤트 |
| Agent | 연결 상태, 프로토콜 파싱 결과, 수신/송신 메시지, 헬스 체크 |
| Node | 입력/출력 메시지, 처리 시간, 에러 발생, 드롭된 메시지 |
| Script Engine | 스크립트 실행 시간, 메모리 사용량, 런타임 에러, 핫 리로드 이벤트 |
| Plugin | 로드/언로드 이벤트, 실행 시간, 리소스 사용량 |
| API Server | 요청/응답 로깅, 인증 이벤트, 레이트 리밋 |

## 설계 원칙: 런타임 생명주기 제어 (Runtime Lifecycle Control)

플로우, 노드, 에이전트 등 시스템을 구성하는 모든 요소는 동작 중에 초기화, 멈춤, 재개가 가능해야 하며, 설정 또한 런타임에 변경 가능해야 한다.

### 생명주기 상태 머신

모든 구성 요소는 다음의 공통 상태 전이를 따른다:

```
Created → Initializing → Running ⇄ Paused → Stopping → Stopped
                            │                              │
                            └── Error ─── (자동 복구) ──────┘
```

- **초기화(Init)**: 구성 요소 생성 및 리소스 할당
- **시작(Start)**: 실행 시작, 데이터 처리 가능 상태
- **일시정지(Pause)**: 데이터 처리 중단, 상태와 연결은 유지
- **재개(Resume)**: 일시정지 상태에서 데이터 처리 재개
- **중지(Stop)**: 정상 종료, 리소스 해제
- **에러(Error)**: 오류 발생, 설정에 따라 자동 복구 또는 중지

### 에이전트 자동 시작 제어 (Enable/Disable)

런타임 상태 전이(Start/Stop)와는 **독립적**으로, 에이전트는 **영속 설정**
인 `Enabled` 플래그를 가진다. 이는 데몬 재시작 시 자동 시작 여부를
제어하는 설정 값으로, 런타임 상태에는 영향을 주지 않는다 (SPEC-AGENT-005).

- **Disabled 에이전트**: 데몬 재시작 시 자동 시작에서 제외된다. 매니저에
  는 여전히 등록되어 목록/상세 API 에 노출되며, 수동 Start API 로
  일시 기동할 수 있다.
- **Disable 호출**: 현재 실행 중인 에이전트를 강제 정지하지 않는다
  (설정과 런타임의 완전 분리).
- **Enable 호출**: 현재 정지된 에이전트를 자동 Start 하지 않는다
  (API 레벨). Web UI 는 사용자 편의를 위해 Enable 성공 후 정지 상태인
  에이전트에 한해 Start 를 연쇄 호출한다.
- **플로우 배포 검증**: `DeployFlow` 는 Disabled 에이전트를 참조하는
  플로우의 배포를 거부하여 런타임 nil 참조를 방지한다.
- 용도: 점검 중인 에이전트의 자동 시작 방지, 장애 격리, 단계적 배포 등

### 구성 요소별 생명주기

| 구성 요소 | 상태 전이 | 일시정지 시 동작 | 재개 시 동작 |
|-----------|----------|----------------|-------------|
| Flow | Running ⇄ Paused | 노드 실행 중단, 채널 유지 | 채널 큐 데이터부터 처리 재개 |
| Node | Running ⇄ Paused | 메시지 수신 중단, 내부 상태 유지 | 큐잉된 메시지부터 처리 재개 |
| Agent | Running ⇄ Paused | 외부 연결 유지, 수신 버퍼링 | 버퍼링된 데이터 처리 시작 |
| Script Engine | Running ⇄ Paused | VM 풀 유지, 새 실행 중단 | 풀 재활성화 |
| Plugin | Running ⇄ Paused | 플러그인 호출 중단 | 호출 재개 |

### 런타임 설정 변경 (Hot Configuration)

구성 요소의 설정을 재시작 없이 런타임에 변경할 수 있다.

- **플로우 설정**: 백프레셔 임계값, 실행 정책 등을 동작 중 변경
- **노드 설정**: 필터 조건, 변환 규칙, 집계 윈도우 등을 동작 중 변경
- **Agent 설정**: 연결 주소, 인증 정보, 프로토콜 파라미터 등을 동작 중 변경
- **스크립트**: Lua 스크립트 내용을 실행 중 교체 (핫 리로드)
- **로그 레벨**: 컴포넌트별 로그 레벨 런타임 변경 (관찰성 기능과 연계)

설정 변경은 API를 통해 수행하며, CLI와 Web Dashboard 모두에서 접근 가능하다.

## 설계 원칙: 메시지 가변성 및 변경 이력 (Mutable Messages)

에이전트와 노드 간에 주고받는 메시지는 데이터 추가/변경/삭제가 가능해야 하며, 필요에 따라 변경 이력을 추적할 수 있어야 한다.

### 메시지 구조

```
┌─────────────────────────────────┐
│           Message               │
├─────────────────────────────────┤
│  ID          (고유 식별자)       │
│  Payload     (가변 데이터 맵)    │
│  Metadata    (시스템 메타정보)    │
│  History[]   (변경 이력, 선택)    │
│  Timestamp   (생성 시각)         │
└─────────────────────────────────┘
```

### 데이터 조작

- **추가(Add)**: 메시지의 Payload에 새로운 키-값 쌍 추가
- **변경(Set)**: 기존 키의 값을 새 값으로 교체
- **삭제(Delete)**: Payload에서 특정 키 제거
- **조회(Get)**: 키 기반 데이터 조회, JSONPath 지원

### 변경 이력 추적

메시지 단위로 변경 이력 추적을 활성화/비활성화할 수 있다.

| 항목 | 설명 |
|------|------|
| 이력 기록 대상 | Add, Set, Delete 연산 |
| 기록 내용 | 연산 유형, 키, 이전 값, 새 값, 변경 노드, 타임스탬프 |
| 활성화 방식 | 플로우 설정 또는 노드 설정에서 선택적 활성화 |
| 성능 고려 | 비활성화 시 오버헤드 없음, 활성화 시에도 최소 메모리 사용 |
| 활용 | 디버깅, 감사 추적, 데이터 파이프라인 검증 |

## 설계 원칙: 에러 및 폐기 메시지 처리 (Error & Dead Letter)

에이전트, 노드 등에서 폐기되는 메시지나 동작 중 발생하는 에러 메시지를 별도의 노드에서 수신할 수 있어야 한다. 이러한 수신 노드가 연결되지 않은 경우, 에러/폐기 메시지는 자동으로 폐기된다.

### 에러 출력 포트

모든 노드는 기본 출력 포트 외에 **에러 출력 포트**를 가진다.

- 노드 처리 중 발생한 에러는 에러 출력 포트로 전달
- 에러 포트에 연결된 노드가 없으면 자동 폐기 (로그에는 기록)
- 에러 메시지에는 원본 메시지, 에러 원인, 발생 노드 정보가 포함

### 전용 수신 노드

| 노드 | 용도 | 수신 대상 |
|------|------|----------|
| Catch | 에러 메시지 수신 | 플로우 내 노드에서 발생한 에러 |
| Status | 상태 변경 수신 | Agent/Node의 상태 전이 이벤트 |
| Dead Letter | 폐기 메시지 수신 | 백프레셔 드롭, 필터 제외, 타임아웃 등으로 폐기된 메시지 |

### 자동 폐기 정책

- 에러/폐기 메시지를 수신하는 노드가 연결되지 않은 경우, 해당 메시지는 자동으로 폐기
- 폐기 시에도 관찰성 시스템에 카운터/로그 기록 (메트릭으로 추적 가능)
- 과도한 에러/폐기 발생 시 알림 트리거 설정 가능

## 핵심 기능

### 1. Flow Engine (FBP 런타임 엔진)

- **노드 그래프 실행**: 방향성 비순환 그래프(DAG) 기반 플로우 실행 엔진
- **데이터 스트림 라우팅**: 노드 간 데이터 패킷 전달 및 분기 처리
- **백프레셔 처리**: 하류 노드 과부하 시 상류 노드 속도 자동 조절
- **플로우 상태 관리**: 플로우 시작, 중지, 일시정지, 재시작 등 생명주기 관리
- **동시성 제어**: Go 고루틴 기반 노드 병렬 실행 및 채널 기반 통신
- **Wire 시스템**: 노드 간 연결선(Wire)은 바이패스 기본, 선택적 버퍼링 및 메시지 TTL 지원

#### Wire (연결선)

Wire는 노드 간 메시지를 전달하는 연결선이다. 기본적으로 바이패스(즉시 전달) 방식이지만, 설정에 따라 일정 수량의 메시지를 버퍼링할 수 있다.

- **바이패스 모드(기본)**: 메시지가 즉시 다음 노드로 전달, 버퍼 없음
- **버퍼 모드**: 설정된 수량만큼 메시지를 Wire에 저장, 수신 노드가 준비되면 순차 전달
- **메시지 TTL(유효시간)**: 메시지에 유효시간을 설정 가능, 유효시간 내 전송되지 못한 메시지는 자동 폐기
- **수신 노드 상태 확인**: 송신 노드는 수신 노드의 상태(Running/Paused/Stopped)를 확인하여 전송 여부 결정
- **폐기 정책**: TTL 만료 메시지는 Dead Letter 노드가 연결되어 있으면 전달, 없으면 자동 폐기 및 메트릭 기록

| 모드 | 버퍼 크기 | 수신 노드 Paused 시 | TTL 만료 시 |
|------|----------|-------------------|------------|
| 바이패스 | 0 | 송신 차단 (백프레셔) | N/A |
| 버퍼 | 1~N | 버퍼에 저장 | 폐기 (Dead Letter 연결 시 전달) |

### 2. Agent (설정 기반 프로토콜 파싱 서비스)

Agent는 플로우와 독립적으로 실행되는 서비스 단위이다. 사용자가 프로토콜 구조를 설정하면 이에 맞게 데이터를 파싱하며, 통신 인터페이스(Serial, TCP 등)를 선택할 수 있다. 여러 플로우에서 공유하여 사용할 수 있다.

- **설정 기반 프로토콜 파싱**: 사용자가 프로토콜 구조(메시지 포맷, 헤더, 페이로드, 체크섬 등)를 정의하면 Agent가 이에 맞게 파싱/직렬화
- **인터페이스 선택**: Serial(RS-485/RS-232), TCP, UDP 등 통신 인터페이스를 선택하여 Agent에 바인딩
- **플로우 독립 실행**: 플로우 생명주기와 무관하게 독립적으로 실행
- **다중 플로우 공유**: 하나의 Agent 인스턴스를 여러 플로우에서 참조하여 공유
- **커넥션 풀링**: 외부 연결을 Agent가 관리하여 리소스 효율화, 플로우 재배포 시에도 연결 유지
- **독립 생명주기**: Agent별 시작/중지/재시작 가능, 헬스 체크 및 자동 복구

```
┌─────────────────────────────────────┐
│            Agent Instance           │
├──────────────┬──────────────────────┤
│  Transport   │  Protocol Definition │
│  Interface   │  (사용자 설정)        │
│              │                      │
│  - Serial    │  - 메시지 포맷       │
│  - TCP       │  - 필드 정의         │

```

#### System Agent (시스템 내장 에이전트)

시스템 에이전트는 별도의 연결 설정 없이 노드나 다른 에이전트에서 바로 사용할 수 있는 내장 서비스이다. 시스템 시작 시 자동으로 활성화되며, Bridge Node 없이도 직접 참조 가능하다.

| System Agent | 용도 | 제공 기능 |
|-------------|------|----------|
| Event | 시스템 이벤트 발행/구독 | 플로우 상태 변경, Agent 연결/해제, 에러 발생 등 내부 이벤트 |
| Logger | 로그 관리 | 컴포넌트별 로그 작성, 로그 레벨 제어, 로그 스트림 구독 |
| File | 파일 시스템 접근 | 로컬 파일 읽기/쓰기, 디렉토리 감시, 파일 변경 이벤트 |
| Timer | 타이머/스케줄러 | 주기적 실행, cron 스케줄, 지연 실행, 반복 실행 |
| Store | 키-값 저장소 | 플로우 간 공유 데이터 저장/조회, 영속적/휘발성 선택 |

시스템 에이전트의 특징:
- **자동 활성화**: 시스템 시작 시 자동으로 생성, 별도 등록 불필요
- **설정 불필요**: 외부 연결이 없으므로 Transport/Protocol 설정 불필요
- **직접 참조**: Bridge Node를 통하지 않고 노드에서 직접 API 호출 가능
- **전역 접근**: 모든 플로우와 에이전트에서 공유 접근

#### Bridge Node (Agent-Flow 연결)

Bridge Node는 Agent와 플로우를 연결하는 전용 노드이다. 각 Agent는 하나 이상의 Bridge Node와 연결 가능하며, 메시지 방향과 응답 처리 방식을 설정할 수 있다.

```
┌──────────┐     ┌──────────────┐     ┌──────────┐
│  Agent   │◄───▶│  Bridge Node │◄───▶│  Flow    │
│ (MQTT)   │     │  (양방향)     │     │  Nodes   │
└──────────┘     └──────────────┘     └──────────┘

┌──────────┐     ┌──────────────┐     ┌──────────┐
│  Agent   │────▶│  Bridge Node │────▶│  Flow    │
│ (NASA)   │     │  (단방향 수신) │     │  Nodes   │
└──────────┘     └──────────────┘     └──────────┘
```

- **단방향 수신(In)**: Agent → Bridge → Flow (Agent에서 데이터 수신만)
- **단방향 송신(Out)**: Flow → Bridge → Agent (Agent로 데이터 전송만)
- **양방향(InOut)**: Agent ⇄ Bridge ⇄ Flow (수신 + 송신 모두)
- **요청/응답(Request-Reply)**: Flow → Bridge → Agent → Bridge → 요청 노드 또는 지정 노드로 응답 전달

요청/응답 패턴에서 응답 메시지는 요청을 보낸 노드로 자동 반환되거나, 설정에 따라 지정된 다른 노드로 라우팅할 수 있다.

#### MODBUS RW Node (MODBUS 읽기/쓰기 노드)

MODBUS RW Node(`modbus`)는 MODBUS Agent(Client/Server)의 레지스터를 플로우 내에서 직접 읽기/쓰기할 수 있는 전용 처리 노드이다. Bridge Node가 Agent 전체 데이터 수신에 특화되어 있다면, MODBUS RW Node는 특정 레지스터 주소를 지정하여 개별 읽기/쓰기 연산을 수행한다.

- **단일 노드 설계**: operation 설정(read/write)에 따라 읽기 또는 쓰기로 동작
- **Server/Client Agent 자동 감지**: 연결된 Agent 타입을 자동으로 감지하여 적절한 Process() 명령을 선택
- **4개 레지스터 영역 지원**: Coils, Discrete Inputs, Holding Registers, Input Registers
- **다중 데이터 타입**: uint16, int16, float32, uint32, int32 타입 변환 지원
- **payload 보존**: 읽기/쓰기 결과를 원본 메시지의 payload에 병합하여 데이터 흐름을 유지
- **에러 포트**: 타임아웃, Agent 상태 이상, 패닉 등의 에러를 에러 포트로 안전하게 전달

### 3. Script Engine (Lua 스크립트 엔진)

Lua 기반 실시간 스크립트 엔진으로, 플로우 실행 중에도 로직을 수정하고 즉시 반영할 수 있다.

- **실시간 프로그래밍**: 플로우 실행 중 Lua 스크립트 수정 및 핫 리로드 (재배포 불필요)
- **Script 노드**: 플로우 내 Lua 스크립트를 실행하는 Function 노드 (Node-RED의 Function 노드에 대응)
- **데이터 변환**: 수신 데이터를 Lua 스크립트로 자유롭게 가공, 필터링, 매핑
- **조건 로직**: 복잡한 조건 분기, 비즈니스 룰, 임계값 판단을 스크립트로 정의
- **Agent 연동**: Agent가 수신한 원시 데이터의 커스텀 파싱/변환 로직 작성
- **샌드박스 실행**: 스크립트 실행 환경이 격리되어 시스템 안전성 보장, 메모리/CPU 제한 설정 가능
- **내장 라이브러리**: JSON 파싱, 수학 함수, 문자열 처리, 시간 함수 등 제공

### 4. Web Dashboard (웹 대시보드)

- **플로우 에디터**: React Flow 기반 드래그 앤 드롭 노드 구성 인터페이스
- **실시간 데이터 시각화**: 차트, 게이지, 테이블 등 다양한 위젯으로 데이터 표시
- **스크립트 에디터**: 웹 기반 Lua 코드 에디터 (구문 강조, 자동 완성, 실시간 디버깅)
- **시스템 모니터링**: 플로우 실행 상태, 노드 처리량, 에러율 등 실시간 메트릭
- **사용자 관리**: 역할 기반 접근 제어(RBAC), 사용자 초대 및 권한 설정
- **Import/Export**: 플로우 및 에이전트를 JSON/YAML 형식으로 내보내기/가져오기, 드래그 앤 드롭 지원, CLI 호환 포맷
- **지하철 시설물 관리 대시보드 패널** (SPEC-FACILITY-DASHBOARD-001): 지하철 역사 시설물(첫 디바이스: 설비)을 라인(호선)→역사(station)→기기(device) 계층으로 조망·제어하는 3종 패널. 라인 패널(라인도 + 역사별 상태 요약 + 라인 통계 + 라인 일괄 제어), 역사 패널(역사 통계 + 기기별 상태 목록 + 역사 일괄 제어), 기기 패널(단일 기기 상태 + 응답 대기 제어). 신규 백엔드 없이 xsfm 에이전트의 exec 표면을 클라이언트에서 집계·제어

### 5. Plugin System (플러그인 시스템)

- **Go 플러그인**: Go plugin 패키지 기반 네이티브 플러그인 로딩
- **WASM 확장**: Wazero 런타임을 통한 WebAssembly 기반 다국어 플러그인 지원
- **플러그인 레지스트리**: 플러그인 검색, 설치, 업데이트 관리
- **커스텀 노드 타입**: 플러그인을 통한 새로운 노드 타입 정의 및 등록

### 6. CLI Tool - xflow (커맨드라인 도구)

- **원격 API 클라이언트**: REST API를 통해 xflowd 데몬 서버에 원격 접속하여 관리
- **플로우 관리**: 플로우 생성, 배포, 시작, 중지, 삭제
- **노드 관리**: 사용 가능한 노드 타입 조회, 플러그인 설치/제거
- **모니터링**: 플로우 상태 조회, 로그 조회, 메트릭 출력
- **설정 관리**: 서버 연결 설정, 인증 토큰 관리
- **내보내기/가져오기**: 플로우 정의를 JSON/YAML 형식으로 내보내기 및 가져오기

### 7. API Service - xflowd (데몬 서버)

- **데몬 서버**: xflowd는 데몬 프로세스로 백그라운드 실행
- **통합 API 게이트웨이**: xflow(CLI)와 Web UI 모두 동일한 REST API를 통해 원격 접속
- **플로우 CRUD API**: 플로우 생성, 조회, 수정, 삭제 엔드포인트
- **노드 카탈로그 API**: 등록된 노드 타입 목록 및 상세 정보 조회
- **실행 제어 API**: 플로우 시작/중지/재시작, 노드별 디버깅
- **모니터링 API**: 메트릭, 로그, 이벤트 스트림 제공
- **인증 API**: JWT 기반 인증, API 키 관리, OAuth2 연동

## 사용 시나리오 (Use Cases)

### 시나리오 1: 스마트 팩토리 센서 데이터 수집 및 이상 감지

제조 공장의 수백 개 센서에서 MQTT 프로토콜로 전송되는 온도, 진동, 습도 데이터를 xflow가 실시간으로 수집한다. 수집된 데이터는 플로우 엔진에서 필터링, 정규화, 집계 과정을 거친 후, 임계값 초과 시 알림 노드를 통해 Slack/이메일로 경고를 발송한다. 동시에 웹 대시보드에서 라인별 센서 상태를 실시간 모니터링할 수 있다.

**관련 기능**: MQTT Client Agent(공유 커넥션), Flow Engine(백프레셔 처리), Web Dashboard(실시간 시각화)

### 시나리오 2: 멀티 프로토콜 IoT 게이트웨이

다양한 IoT 프로토콜(MQTT, HTTP, WebSocket)을 사용하는 이기종 디바이스들의 데이터를 프로토콜별 Agent(MQTT Client, HTTP Client/Server, WebSocket Client/Server)가 통합 수집한다. 각 Agent는 독립 실행되며 여러 플로우에서 공유된다. Agent가 수집한 데이터를 표준 메시지 포맷으로 변환하고, 변환된 데이터를 목적지(데이터베이스, 클라우드 서비스, 분석 엔진)에 따라 라우팅한다. DevOps 엔지니어는 CLI를 통해 게이트웨이 플로우를 관리하고, 새로운 디바이스 유형 추가 시 WASM 플러그인으로 커스텀 파서 노드를 배포한다.

**관련 기능**: Agent(멀티 프로토콜), Plugin System(WASM 확장), CLI Tool(배포 자동화)

### 시나리오 3: 에지 컴퓨팅 환경의 데이터 전처리 파이프라인

리소스가 제한된 에지 서버에서 경량 에이전트(xflow-agent)가 동작하며, 로컬 센서 데이터를 전처리한다. 에지에서 필터링과 집계를 수행한 후, 요약된 데이터만 중앙 서버로 전송하여 네트워크 대역폭을 절약한다. 중앙 서버의 xflowd 인스턴스는 여러 에지 에이전트의 데이터를 통합하여 글로벌 뷰를 제공한다.

**관련 기능**: xflow-agent(경량 에이전트), Flow Engine(로컬 처리), API Service(중앙 통합)

### 시나리오 4: 실시간 대시보드 기반 운영 관제

운영 관제 센터에서 xflow 웹 대시보드를 통해 전사 IoT 인프라를 모니터링한다. 플로우 에디터에서 새로운 데이터 수집 파이프라인을 드래그 앤 드롭으로 구성하고, 즉시 배포하여 테스트할 수 있다. 대시보드의 커스텀 위젯으로 KPI 지표를 실시간 추적하며, 이상 발생 시 자동 대응 플로우가 트리거된다.

**관련 기능**: Web Dashboard(플로우 에디터, 시각화), Flow Engine(자동 대응), API Service(실시간 메트릭)

| 성능 | JavaScript GC 오버헤드 | Go의 효율적인 메모리 관리 |
| 배포 | npm 의존성 관리 필요 | 단일 바이너리 배포 |
| CLI 지원 | 제한적 (Admin API 직접 호출) | 풀기능 CLI 도구 기본 제공 |
| 에지 배포 | 리소스 사용량 높음 | 경량 에이전트(xflow-agent) 별도 제공 |
| 플러그인 | JavaScript 모듈 | Go 플러그인 + WASM(다국어 지원) |
| 보안 | 기본적인 인증 | RBAC, JWT, OAuth2, 감사 로깅 |
| 백프레셔 | 미지원 | 네이티브 백프레셔 메커니즘 |

### Apache NiFi 대비 차별화

| 항목 | Apache NiFi | xflow |
|------|-------------|-------|
| 리소스 요구량 | JVM 기반, 높은 메모리 요구 | Go 기반, 경량 (수십 MB) |
| 설치 복잡도 | Java 환경 설정 필요 | 단일 바이너리, 즉시 실행 |
| 학습 곡선 | 복잡한 UI, 수백 개 프로세서 | 직관적 UI, 핵심 노드 중심 |
| 에지 배포 | MiNiFi (별도 프로젝트) | xflow-agent (통합 프로젝트) |
| IoT 특화 | 범용 데이터 처리 | IoT 프로토콜 네이티브 지원 |
| 확장성 | Java 프로세서 개발 | Go 플러그인 + WASM |
| 시작 시간 | JVM 워밍업 필요 (수십 초) | 즉시 시작 (밀리초 단위) |
| 컨테이너 적합성 | 이미지 크기 큼 (1GB+) | 최소 이미지 (수십 MB) |

### xflow의 핵심 강점

1. **단일 바이너리 배포**: Go 크로스 컴파일로 OS별 단일 실행 파일 제공
2. **CLI-First 설계**: 자동화와 스크립팅에 최적화된 완전한 CLI 인터페이스
3. **경량 에지 에이전트**: 리소스 제한 환경에 최적화된 별도 에이전트 바이너리
4. **WASM 플러그인 지원**: 언어 무관 플러그인 개발 (Rust, C, AssemblyScript 등)
5. **네이티브 백프레셔**: Go 채널 기반의 자연스러운 흐름 제어
6. **보안 내재화**: 설계 단계부터 인증/인가/암호화/감사 로깅 포함

## 프로젝트 범위

### MVP (최소 기능 제품) 범위

- Flow Engine 코어 (노드 그래프 실행, 기본 백프레셔)
- Agent 프레임워크 (Transport Interface + Protocol Definition, 독립 실행, 다중 플로우 공유)
- MQTT Client Agent, HTTP Client/Server Agent (표준 Agent)
- Custom Protocol Agent (사용자 설정 기반 프로토콜 파싱)
- Lua Script Engine (Script 노드, 핫 리로드, 샌드박스)
- 기본 내장 노드 (필터, 변환, 분기, 로그, MODBUS 읽기/쓰기 등)
- RESTful API 서버
- CLI 기본 명령어 (플로우 CRUD, 실행 제어)
- 기본 웹 대시보드 (플로우 에디터, 상태 모니터링)
- JWT 기반 인증

### 확장 범위

- WebSocket Client/Server Agent, gRPC Client/Server Agent 추가
- Samsung NASA Manager Agent (삼성 시스템 에어컨 제어)
- WASM 플러그인 시스템
- 경량 에이전트 (xflow-agent)
- 고급 대시보드 위젯 (차트, 게이지, 히트맵)
- OAuth2 연동 및 RBAC
- 클러스터 모드 (분산 플로우 실행)
- 플러그인 레지스트리 및 마켓플레이스
